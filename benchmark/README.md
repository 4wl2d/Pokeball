# Architecture benchmark

The same checkout feature runs against one simulated environment with an unreliable payment provider and crashes. It is written in four architectural styles (layered, actors, MVU, outbox plus saga), each twice, and in Ballarch: nine implementations. The *naive* version of each style treats a provider timeout as a failure; the *careful* version handles the uncertainty with the style's own tools. The benchmark measures three things:

- **correctness under faults**, checked against the provider's ground truth, with two providers: scenario A has no idempotency keys, scenario B honours them;
- **structure** of the feature code, using standard coupling, cohesion, complexity and size metrics;
- **change impact**: four change requests, specified before they were implemented, applied to every design as patches; the files, units and lines of code each one touches, and whether every requirement still holds after it ([change requests](changes/README.md)).

It also measures the runtime overhead of a request through Ballarch's reference runtime against a direct call; that number depends on the machine and is kept apart (see [Runtime overhead](#runtime-overhead)).

Results: [`results/RESULTS.md`](results/RESULTS.md); raw data: [`results/results.json`](results/results.json), [`results/changes.json`](results/changes.json) (change requests) and [`results/overhead.json`](results/overhead.json) (runtime overhead).

## Scenario

Every implementation receives the same specification:

- **Stock.** One SKU with 2 units in stock.
- **Orders.** Three orders (`o1`, `o2`, `o3`) of 1 unit each, all sent at time 0. The client is at least once: after a crash and restart it sends again every order that the system has not durably accepted, and never one that it has.
- **Checkout.** Reserve the unit, charge 100 through the payment provider, then complete the order. If the payment is not made, release the reservation and fail the order. Out of stock also fails the order.
- **Terminal states.** `Completed`, `Failed`, or `NeedsAttention`, which hands an unresolved case to an operator.
- **Persistence.** A database with atomic transactions survives crashes; everything else is lost. Ballarch keeps its store in the same simulated database.
- **The provider.** In **scenario A** the provider charges every request that reaches it: it has **no idempotency keys**. In **scenario B** it honours idempotency keys, as payment APIs with an `Idempotency-Key` header do (IETF draft *The Idempotency-Key HTTP Header Field*): a charge whose key already took effect is not charged again, and the answer repeats the first charge's result. A request without a key charges again in both scenarios. In both, a Safe status endpoint reports whether an order was charged, and the provider declares a **delivery horizon** of 1 s: a request that got no answer within 1 s of being sent can no longer take effect. Under the Stress and Mild profiles the simulator guarantees it, since a request reaches the provider within 20 ms or never; the Beyond-horizon profile breaks it. Both scenarios use the same seeds, and the key draws no random number, so the n-th provider request of a run gets the same fate in both. The designs send different requests in scenario B, so runs of A and B are not paired beyond that.

### Requirements (the oracles)

| Violation | Definition |
|---|---|
| DoubleCharge | the provider charged an order more than once |
| FalseFailure | an order reported `Failed` was charged |
| UnpaidCompletion | an order reported `Completed` was not charged |
| Stranded | an accepted order has no terminal state when the run ends |
| StockLeak | an order reported `Failed` still holds stock |
| Oversell | more orders completed than units in stock |
| LostCharge | an order was charged that the system never accepted |

`NeedsAttention` is not a violation: it is the honest answer when the provider cannot be asked. Its frequency is reported as a cost.

### Fault model

- **Provider fates.** Each provider request independently gets one fate:
  - answered in time;
  - answered after 5 s;
  - lost before arrival;
  - processed, answer lost;
  - processed, then connection reset;
  - connection refused (provably not sent);
  - delivered after the horizon: held in the network, it takes effect 5 s after it was sent, and no answer reaches the sender (for example a retransmission released from a queue). The 5 s is the environment's existing delay for late answers.
- **Profiles.**
  - *Stress* makes the first six fates equally likely and never delivers after the horizon.
  - *Mild* answers 90% of requests in time and gives each of the five other horizon-respecting faults 2%.
  - *Beyond horizon* is Mild plus the delivery after the horizon, weighted like each other fault (45:1:1:1:1:1:1, so 88% in time and 2% for each fault). It tests the assumption that the careful and Ballarch designs make about the horizon.

  The seventh fate has weight 0 in Stress and Mild, so their draws, and therefore their crash-free runs, are the same as before it existed.
- **Crashes.** In crash cells every run crashes exactly once, at a virtual time *t*, and restarts at *t* + 50 ms. *t* is drawn uniformly from the whole milliseconds of the **busy period** of the same seed's crash-free run, from 0 until every accepted order has its terminal state. The crash is an event of its own: it comes before every scheduler task due at *t*, and in an idle gap it happens while nothing runs. Scheduler tasks take no virtual time, so a crash never falls between two tasks of the same instant; the sweep below covers those points. Because the run up to *t* is the crash-free run, the crash always happens; the runner checks this and records the number of crashed runs. How many scheduler tasks a design runs does not change where its crashes fall: every design gets the same distribution of crash times relative to its own busy period. In scenario A the four naive designs finish their crash-free runs at the same times, so for each seed they draw the same crash time; so do the four careful designs and `ballarch`.
- **Exhaustive sweep.** As a separate check, the runner crashes each of the first 1,000 crash-cell seeds once immediately before every scheduler task of its crash-free run, including the points between two tasks of the same instant. These points are each design's own tasks, so how many there are, and what share of them violate, depends on how finely a design splits its work into tasks. The share is therefore not comparable across designs. What the sweep shows is which violations a design can reach with one crash, and, for a design meant to be correct, that no point violates.
- **Recovery.** Each implementation recovers in its own way, described in the table below.
- **Run length.** A run ends when no work is left, or after 120 s of simulated time.
- **Seeds.** The simulation is deterministic: the same seed gives the same run, and the published `results.json` is reproduced byte for byte. The code that runs, crashes and judges a run is [`harness`](harness/src/main/kotlin/bench/harness/Dynamic.kt), which the benchmark runner and the change requests' runner share.

## Implementations

All nine are in Kotlin, written by the same author against the specification above. Each follows its style's structural guidance (cited below). None of the cited sources prescribes how to handle an ambiguous provider failure. The four **naive** versions therefore share one policy, chosen by the author: one attempt, and a timeout or I/O error means the payment failed. Akka's documentation warns that an `ask` timeout does not mean the request was not processed ("the receiving actor does not know and may still process it to completion"). Without crashes, the four naive versions behave identically, and their violation rate is fixed by the fault mix: 1−(1−p)² for the two orders that are paid, where p is the probability that a charge takes effect but reads as failed (p = 1/2 under Stress, 0.06 under Mild, so 0.75 and 0.116). Where a style gives no recovery guidance (MVU), the recovery path is the author's choice, and the table says so.

The four **careful** versions handle provider uncertainty with their style's own tools, written by the author with each style's own tools, without the Ballarch kernel or runtime. All four apply the same fault policy, the one the hand-hardened layered version already used and that Section 8.4 of the Ballarch specification describes:

- record durably that a charge may be in flight before sending it;
- send a charge again only after evidence that it never reached the provider (connection refused), at most three requests;
- when the outcome is unknown, wait past the provider's 1 s delivery horizon, then ask the status endpoint, at most three times, then hand the order to an operator (`NeedsAttention`);
- after a restart, reconcile a charge that may have been sent; never send it again.

The budgets (three sends, three status queries, 1 s timeouts) are the same in all five designs that reconcile, Ballarch included.

Code that stands in for a framework sits in a `kit` package (an actor toolkit, an Elm-style runtime, transactional messaging), which the naive and careful versions of a style share. It is excluded from the feature metrics and its size is reported separately; Ballarch's runtime library is excluded in the same way. The careful actors version needed a single timer, so the actor kit gained `scheduleOnce` (Akka's `ActorContext.scheduleOnce` or a `TimerScheduler` single timer); the naive version does not call it. Ballarch's adapters call the provider's callback API (`Provider`), which reports failures as `Reply.Failure` values; the other eight call `ProviderClient`, which throws them.

| Key | Design | What it follows | Handling of provider failures | Recovery |
|---|---|---|---|---|
| `layered` | Layered, naive provider handling | Entities, use-case interactor, output ports, adapters, main component (Martin 2017) | One attempt with a timeout; any exception means the payment failed: release and fail | On start, resume every unfinished order from its persisted status, which sends the charge of an order that was being paid again |
| `hardened` | Layered, careful (hardened by hand) | As `layered`, plus write-ahead status, evidence-based resend and status reconciliation (Section 8.4 of the Ballarch specification, written into the feature) | `CHARGING` is saved before each request; a request is repeated only after connection refused; timeout or reset → wait past the horizon, then query the status | `CHARGING` orders are reconciled, never charged again |
| `actors` | Actors, naive provider handling | Typed actors, `ask` with a timeout, `pipeToSelf`, state persisted before acting (Hewitt et al. 1973; Akka Typed durable state) | A failed `ask` means the payment failed: release (`tell`) and fail | Re-create checkout actors from durable state and re-drive their current stage. This at-least-once re-drive is the author's addition: Akka's durable state runs side effects at most once and does not run them again when the actor is restarted |
| `actors-careful` | Actors, careful | As `actors`, with a typed charge reply (`Charged`, `Declined`, `NotSent`, `Unknown`), a single timer and an acknowledged release | An `ask` timeout or a reset gives `Unknown`: the stage `Reconciling` is persisted, a timer waits past the horizon, and the actor asks the payment actor for the provider's status; `NotSent` → charge again | Re-create checkout actors from durable state; a checkout persisted as `Charging` is reconciled, never charged again, as side effects are not re-run on recovery |
| `mvu` | MVU, naive provider handling | One store; pure `update(model, msg) → (model, commands)` (The Elm Architecture: Czaplicki, Elm guide; `Cmd` since Elm 0.17, 2016). Persisting the model before commands run is this benchmark's addition, because Elm gives no guidance on server-side persistence or recovery | A command's result is a two-valued `Result`; failure releases and fails the order | `init` issues the charge command of every order still paying again (the author's choice) |
| `mvu-careful` | MVU, careful | As `mvu`; command results are a custom type (`Charged`, `Declined`, `NotSent`, `Unknown`), and a `CheckStatus` command waits, then queries | `NotSent` → issue the charge again; `Unknown` → `Reconciling`, with a `CheckStatus` command | `init` issues `CheckStatus`, never `Charge`, for every order still paying or reconciling |
| `saga` | Outbox + saga, naive provider handling | Hexagonal participants; saga orchestrator; outbox written with each state change; at-least-once relay; idempotent consumers keyed by message id (Richardson 2018; Garcia-Molina & Salem 1987) | The payment participant replies `PaymentFailed` on timeout or error, and the saga compensates | The relay redelivers unacknowledged messages, and the participant calls the provider again |
| `saga-careful` | Outbox + saga, careful | As `saga`; the payment participant commits a charge-attempted row before it calls the provider, and can reply `PaymentUnknown`, which parks the saga | Refused → send again; timeout or reset → `PaymentUnknown`; the parked saga sends `CheckPayment`, which the participant answers after waiting past the horizon and querying the status, up to three times, then `NeedsAttention` | A redelivered charge command whose charge-attempted row exists is answered from the provider's status, never charged again |
| `ballarch` | Ballarch Core 2 | Inventory, payment and checkout Balls; ports with effect classes; composition root ([specification](../spec/ballarch-core-2.0.md)) | The runtime classifies outcomes; the payment Ball repeats a charge only after `NotDone` and reconciles `Unknown` | Durable profile of the reference runtime |

The careful versions exist to show that correctness does not require Ballarch: the same reconciliation policy can be written by hand in any of these styles. They show what the author could write in each style, not how independent experts would write it. Comparing them with `ballarch` shows where the fault-handling knowledge lives and what each choice costs.

### Scenario B: how each design uses idempotency keys

Each design is adapted to the provider with keys in the way that design would naturally use them. Every design except Ballarch sends the key `charge-<order id>`: an order is charged at most once, so one key per order is right, and it is the same after a restart. The adaptation of each design lives in a package of its own (`keyed`, and `retry` and `refadapter` for the two designs that run only in scenario B), whose files replace the files at the same paths in the scenario-A design; RESULTS.md counts the lines each one changed.

| Design | Change for idempotency keys |
|---|---|
| The four naive versions | Every charge request carries the key, and a request that got no answer (timeout, reset or refused) is repeated with the same key, up to three requests per incarnation of the process. When they run out, the payment failed, as before. Layered: in the gateway adapter. Actors: the checkout actor asks the payment actor again, as it already does for the inventory. MVU: `update` issues the charge command again, counting the requests in the model; `init` starts the count again after a restart, as the other three start their loops again. Saga: the payment participant repeats the request within its handler. Recovery is unchanged: after a restart, each sends the charge of an order it was paying again, with the same key and a new budget of three requests, and the key keeps it from being charged twice. |
| Layered, same-key retries, then NeedsAttention | Only in scenario B: the naive layered version whose gateway, when the same-key retries run out, reports the payment as uncertain, so that the use case records `NeedsAttention` instead of `Failed`. It tests the observation that with keys a simple layered retry design may close the gap. It keeps the budget of three requests. |
| The four careful versions | Every charge request carries the key, and a request that got no answer (1 s timeout or reset), or was refused, is sent again with the same key, up to three requests. When the budget is spent, the charge is reconciled by status query as before. Recovery is unchanged: a charge that may have been sent before a restart is reconciled, not sent again. |
| Ballarch | The charge port is declared `Idempotent`, and the adapter sends the call identity as the key (as the adapter contract and the reference HTTP adapter in `examples/shop/payments-http` do). The composition gives the port `RetryPolicy(maxAttempts = 3)`, the payment Ball gives a charge call a deadline of 3 s, and the adapter ends each attempt after 1 s: an attempt with no answer by then is reported as failed, and a later answer to it is ignored. The runtime then sends the call again, with the same key, until an attempt is answered, three requests have been sent, or the deadline has passed. A call that ends without an answer is `Unknown`, and the payment Ball reconciles it as in scenario A. The adapter reports a refused request as a failed attempt as well, not as evidence that nothing was applied: the careful versions send a refused request again within the same budget, and this makes the runtime do the same. (Reported as evidence, a refused first attempt would end the call `NotDone`, and the payment Ball would start a new call with three attempts of its own: up to five requests per order. See Threats to validity.) After a restart, the Durable runtime sends a call that may have been sent again, with the same key, if the call has attempts left and its deadline has not passed; otherwise the call ends `Unknown` and is reconciled. |
| Ballarch, reference adapter (attempt timeout = call deadline) | Only in scenario B: the same adaptation with the charge adapter shaped like the reference HTTP adapter, whose attempt has no timeout of its own and ends at the call's deadline. The deadline stays 1 s, as in scenario A, and a refusal is reported as evidence. The runtime then repeats only an attempt that failed before the deadline (a connection reset, or a refusal after an earlier attempt). A request whose answer is lost runs into the deadline, ends `Unknown`, and is reconciled after the horizon, as in scenario A. This is the Ballarch adaptation this benchmark first published for scenario B; it gave Ballarch a smaller retry budget than the careful versions, and is kept to show what the adapter's attempt timeout changes. |

There is no pause between attempts. Three requests (for Ballarch, in a 3 s call) is the author's choice, and it is the same for the careful versions and Ballarch: without crashes, the two send the same requests and reach the same outcomes for every seed, which [`BenchmarkTest`](runner/src/test/kotlin/bench/runner/BenchmarkTest.kt) checks. The sensitivity to the budget is given under Threats to validity.

### Seeded bugs

To check that zero violations is not a blind spot, seven plausible bugs are injected from outside the correct implementations:

- two that misclassify an uncertain charge when it happens: a Ballarch payment Ball that treats an `Unknown` charge as not charged, and a hardened gateway that reports an uncertain charge as not sent;
- five that break crash recovery only, by changing what a restarted process finds in its durable records: a Ballarch store whose possibly-sent charge (phase `Sending`) reads as never sent (`Pending`) after a restart, so the runtime sends it again; a hardened recovery that resumes `CHARGING` orders as `RESERVED`; a careful actors recovery that resumes a `Charging` checkout from `Reserving`; a careful MVU model that has lost, at a restart, the orders that were still paying (with their stock returned), so that the client sends them again and they are charged again instead of being reconciled by `init`; and a careful saga whose payment participant loses its charge-attempted rows at a restart.

Each runs in scenario A under Stress and Mild, where the correct implementations have no violation, with and without crashes. All seven must be detected. The five recovery bugs must be detected in crash cells and in no crash-free run. This shows that, for each of the five designs that reconcile, the crash cells reach the state its recovery path exists for, a charge that may have been sent when the process crashed, and that the zero results depend on that path. The recovery bugs are injected by rewriting the durable records at the restart, not by changing the runtime or the designs.

## Change requests

The suite in [`changes/`](changes/README.md) has four change requests, each written as a specification in prose before any design was changed:

- **CR1**: a customer may cancel a completed order within 30 s of placing it; the order is refunded through the provider, which never refunds more than it charged, and its unit returns to stock.
- **CR2**: every completed order earns loyalty points through a second external service that, like the scenario-A provider, has no idempotency keys, and has a status endpoint and the same delivery horizon.
- **CR3**: a secondary payment provider; an order is charged there when the primary provably did not charge it.
- **CR4**: the inventory is removed (a digital product with unlimited stock).

Each is implemented in every one of the nine designs as a patch against its scenario-A code (`changes/<change request>/<design>.patch`), in the way the design's style would make it, with the policy the change request prescribes for naive and for careful designs. [`changes/measure.py`](changes/measure.py) reports the files, top-level units, code lines, physical lines and tokens each patch touches. [`changes/verify.py`](changes/verify.py) applies the patches of a change request in a temporary copy, builds it, and runs every design under the change request's scenario (its client requests, its external services and its new requirements, besides the seven above), 2,000 runs per cell and the single-crash sweep on 500 seeds. It also runs the unpatched designs, to show that the new requirements catch a design without the change. The scenario-B variants call the scenario-A constructors and use its types, so several of them no longer compile once a patch changes those; `verify.py` records which of their files fail to compile, then removes the scenario-B packages in the copy before it builds and runs. The edits those files would need are not part of the patches or of their counts. Neither the benchmark runner nor any test is built with the patches.

## Runtime overhead

The runner's `overhead` task ([`Overhead.kt`](runner/src/main/kotlin/bench/runner/Overhead.kt)) times one request, a counter increment, in four ways: the decider called directly; `Runtime.request` with its tasks run on the caller's thread (the runtime's own work, without a thread hand-off); `Runtime.request` on `ThreadScheduler`, the production scheduler, with an in-memory store; and the same with the durable `FileStore`. It reports the median, 99th percentile and mean over a fixed number of requests after a warm-up (100,000 after 20,000; 2,000 after 200 for the file store), the bytes allocated per request on the caller's thread, and the JVM, operating system and processor count. Every variant is measured in three rounds in one JVM, each with a fresh runtime and its own warm-up, the rounds taking the variants in turn; the file records every round and, for each statistic, the median of the rounds. These numbers depend on the machine and its load, so they are written to [`results/overhead.json`](results/overhead.json), which CI does not regenerate and which is not part of the byte-for-byte check of `results.json`. RESULTS.md section 14 renders the committed file.

SLOC, the three source counts and the scenario-B line counts come from [`report.py`](report.py); every other structural metric is computed from bytecode by [`Structure.kt`](runner/src/main/kotlin/bench/runner/Structure.kt) and [`Complexity.kt`](runner/src/main/kotlin/bench/runner/Complexity.kt). A *class* is a named class. Compiler-generated classes, such as lambdas, coroutine state machines and `$WhenMappings`, count as part of the class that declares them.

The cohesion and complexity metrics count hand-written methods only. They do not count constructors, synthetic or bridge methods, the members Kotlin generates for data classes and enums, or the accessors of properties with a backing field (`getX` of field `x`, or of field `X` for a PascalCase top-level `val`). Kotlin's name mangling for value classes (`getCall-izTbEP8`) is removed before these names are matched. The bodies of a method's lambdas and local functions, and the methods of the coroutine and anonymous classes it declares, count as part of that method. For cohesion, so do the default-argument and accessor helpers it calls: a call to a data class's `copy` uses every field, and a coroutine or anonymous class that reads a private field through `access$getX$p` uses that field. A class whose only methods are generated is not measured; RESULTS.md lists every measured class.

**Cyclomatic complexity** is counted on the bytecode of each hand-written function, with the decisions of its lambdas, local functions, and coroutine and anonymous classes added to it. As in JaCoCo 0.8.15's Kotlin filters, the branches the compiler generates are not counted:

- the coroutine state machine;
- code inlined from library functions (lines beyond the source file in the SMAP);
- `lateinit` checks;
- the null check of a cast to a non-null type;
- the null check of a `when` over a nullable enum;
- the branch of an exhaustive `when` to `NoWhenBranchMatchedException`.

JaCoCo removes that last branch only when an `IFEQ` or a switch's default leads to it. This count also removes it when another check leads to it: when the last case's check falls through into it, as the compiler emits for a last case that compares with an `object`, and when a last case `null` jumps to it with `IFNONNULL`. Over the 587 bytecode methods that JaCoCo 0.8.15 reports for the scenario-A code of the nine implementations and their toolkits, the count agrees with JaCoCo on 555. Of the other 32, 28 are default-argument helpers and constructors, which are not functions here, and 4 contain those `when` patterns: three in the naive actors, hardened and Ballarch versions (one decision each), and the careful actors' `checkout` handler, whose two `when`s with a last case `null` make JaCoCo count 30 and this count 28. The comparison was repeated on the current code of all nine.

The bytecode definition has consequences. `?.`, `?:`, `as?` and a comparison used as a value each count as a decision. A `catch` clause does not. A branch inside an inlined library function (the loop of `map` or `forEach`) does not count either, except in the standard library's `@InlineOnly` functions: the compiler gives their inlined code the line of the call, so JaCoCo and this count both attribute their branches to the caller. In this feature code that adds one decision per call of `Result.getOrNull`, `Result.getOrDefault`, `Result.fold`, `orEmpty`, `takeIf` and `repeat` (found by listing the standard library's `@InlineOnly` functions whose bytecode has a branch, and checking every call of one of those names in the feature code):

|---|---|---|---|
| Layered, naive | none | 42 | 42 |
| Layered, careful (hardened) | two `repeat` | 56 | 58 |
| Actors, naive | one `fold`, two `getOrNull`, one `orEmpty` | 36 | 40 |
| Actors, careful | one `fold`, one `getOrDefault`, two `getOrNull`, one `orEmpty` | 57 | 62 |
| MVU, naive | one `getOrNull`, one `orEmpty` | 29 | 31 |

## Reading the results

### Correctness, scenario A (no idempotency keys)

- While the provider's delivery horizon holds (Stress and Mild), the five designs that reconcile (the four careful versions and Ballarch) violated no requirement in any cell (0 of 2,000 runs per cell). The exhaustive sweep found no violating crash point either: 0 of 54,695 (Stress) and 29,295 (Mild) for Ballarch, 0 of 34,084 and 14,914 for the careful layered version, 0 of 83,108 and 37,391 for careful actors, 0 of 45,225 and 17,469 for careful MVU, and 0 of 86,032 and 43,192 for the careful saga.
- Without crashes, these five behave identically: for each seed the same outcomes and the same provider requests (under Stress, 0.3075 `NeedsAttention` per order and 0.895 completed orders per run), because they apply the same policy. They differ only after a crash. Under Stress with one crash, `NeedsAttention` per order is 0.269 for the careful layered version, 0.304 for careful actors and MVU, 0.296 for the careful saga and 0.320 for Ballarch.
- The four naive versions violated a requirement in 11.7% of crash-free runs under Mild faults and in 73.4% under Stress. These rates follow from the shared naive policy and the fault mix (1−(1−p)², see Implementations), not from the styles. With one crash, each violated a requirement in 91.9% of runs under Stress (1,837 of 2,000) and 94.3% under Mild (1,885).
- The four naive versions also behave identically with one crash at a time, run for run (the same violations, outcomes and charge requests in every seed): between two instants all four hold the same durable state, and on recovery each sends again the charge of every order it was paying:
  - the layered version resumes from the last persisted status;
  - actors and MVU re-drive or re-issue the charge;
  - the saga's relay redelivers the charge command.

  Their recovery paths differ only when a crash falls between two tasks of the same instant, for example after the actors version has persisted a failure and told the inventory actor to release the unit, but before that actor has processed the fire-and-forget message: the release is lost and the stock leaks. Only the exhaustive sweep reaches those points. It shows which violations each design can reach (StockLeak only for naive actors), but it counts points in each design's own tasks, so it does not rank the four. Earlier versions of this benchmark drew the crash among the tasks of an instant, and so reported crash-cell rates from 67% (saga, Mild) to 95%; that spread came from how many tasks each design runs at an instant, not from its recovery.
- Under Mild, most crash-cell violations of the naive versions are double charges (1,866 of the 1,885 violating runs of each): the crash usually falls while a charge is in flight, and recovery charges again. Under Stress, 1,692 runs have a false failure and 1,136 a double charge.
- **Beyond the horizon.** When about 2% of requests take effect 5 s after they were sent, all five reconciling designs reported charged orders as failed (FalseFailure): in 4.2% of crash-free runs and 3.5% of crash runs each, and at 4.4–5.1% of the swept crash points (careful actors 4.4%, Ballarch 4.6%, careful layered 4.7%, careful MVU 4.9%, careful saga 5.1%). They read a "no charge" status after the declared horizon as final, so their zero rates above hold only while that horizon is right. The four naive versions violated a requirement in 14.8% of crash-free runs and in 94.2% of crash runs under the same profile.
- All seven seeded bugs were detected. The two classification bugs show up without crashes too (Ballarch: 92.3% of crash-free runs under Stress, 12.4% under Mild; hardened: the same). The five recovery bugs show up only in crash cells, in none of the 2,000 crash-free runs per profile: with one crash, the Ballarch runtime bug in 13.3% (Stress) and 85.7% (Mild) of runs, the hardened one in 70.0% and 93.6%, and the careful actors, careful MVU and careful saga ones each in 15.2% and 85.8%.

### Correctness, scenario B (the provider honours idempotency keys)

- No design charged an order twice, in any cell or at any swept crash point.
- **Simple retries do not become correct.** The naive versions, which send a charge up to three times with the same key and then treat the payment as failed, reported charged orders as failed in 80.6% of crash-free runs under Stress, more than without keys (73.4%), and in 70.9% (actors, MVU and saga) and 71.0% (layered) of runs with a crash. With keys a payment fails only when all three requests go unanswered, and then one of them has usually charged: per paid order (5/6)³ − (2/6)³ = 0.54 under Stress, so 1 − (1 − 0.54)² = 0.79 for the two paid orders. Under Mild they come close: 0.1% of crash-free runs (2 of 2,000) and 0.2–0.4% with a crash; under Beyond horizon 0.1–0.3%. Every one of these violations is a FalseFailure.
- **With an honest last step they do.** When the same-key retries end in `NeedsAttention` instead of `Failed`, the simple layered design violated no requirement in any cell, Beyond horizon included, since it reads no status and so assumes no horizon. No swept crash point violated either (0 of 22,312 under Stress, 14,574 under Mild and 14,608 Beyond horizon). Its cost is operator handoffs: under Stress without crashes, 0.394 `NeedsAttention` per order, against 0.221 for the careful versions and Ballarch in the same scenario. Under Mild it is 0.0003 per order. With keys, a simple layered retry design therefore closes the correctness gap; under the adversarial Stress profile it hands more orders to an operator than the reconciling designs.
- The careful versions with keys violated nothing under Stress and Mild, and nothing under Beyond horizon without crashes, because a later request with the same key absorbs a delayed one. With a crash, 3.3% of Beyond-horizon runs had a false failure: their recovery still reconciles by status instead of sending again with the key.
- **Ballarch with the same budget as the careful versions** violated no requirement in any cell, Beyond horizon included. Without crashes it sent the same requests and reached the same outcomes as the careful versions in every run (under Stress, 1.69 charge requests per order, 0.221 `NeedsAttention` per order and 1.304 completed orders per run; under Mild and Beyond horizon, 2.000 completed orders per run). It differs from them after a crash, because its Durable runtime sends a call that may have been sent again with the same key, while the careful versions reconcile by status:
  - Beyond horizon with one crash, no violating run, against 3.3% (66 of 2,000) for each careful version. In the exhaustive sweep, 1 of 1,000 seeds had a violating crash point (5 points, FalseFailure), against 37–38 seeds for each careful version (point counts are not comparable across designs, see RESULTS.md section 5); none under Stress (57,878 points) or Mild (28,785).
  - Under Mild with one crash, 2.000 completed orders per run against 1.954–1.956: after a restart the careful versions reconcile by status and fail an order whose request had not taken effect, where Ballarch sends it again with the key.
  - Under Stress with one crash, 0.239 `NeedsAttention` per order, within the careful versions' range (0.228 for the careful layered version, 0.231 for the careful saga, 0.248 for careful actors and MVU), and 1.250 completed orders per run against 1.158–1.214. It sent more charge requests (1.73 per order against 1.49).
- **With the reference adapter, Ballarch's retry policy does not act on a lost answer.** When the adapter's attempt ends at the call's 1 s deadline, as in the reference HTTP adapter, the runtime repeats only an attempt that failed before the deadline (a reset, or a refusal after an earlier attempt); a request whose answer is lost ends `Unknown` and is reconciled after the horizon, as in scenario A. That row violated nothing under Stress and Mild, but under Stress without crashes it sent 0.98 charge requests per order (against 1.69), handed more orders to an operator (0.291 against 0.221 per order) and completed fewer (0.945 against 1.304 per run). Under Mild it completed 1.957 orders per run against 2.000: it failed about 2% of the orders that the other reconciling designs complete, by reconciling a lost request instead of sending it again. Under Beyond horizon it reported charged orders as failed in 4.2% of crash-free runs and 1.9% of crash runs, and depends on the horizon without a crash, as in scenario A. These are the costs of that adapter, not of the architecture with the same budget; but Ballarch's runtime has no attempt timeout of its own, so an adapter has to provide one for the retry policy to cover lost answers, and the reference adapter does not.
- The adaptation to keys changed the fewest lines in the careful versions (2–10 added or changed) and the most in Ballarch: 29 added or changed and 10 removed or changed in 2 files, 19 of them in the charge adapter, mostly its attempt timer. The naive versions changed 7–12 lines, the layered design that ends in `NeedsAttention` 17 lines in 5 files, and the reference-adapter Ballarch 3 lines (the effect class, the key and the retry policy). See RESULTS.md section 9.

### Structure (scenario A)

Ballarch against the four careful versions, which are the ones as correct as Ballarch while the horizon holds (careful layered, actors, MVU and saga, in that order):

- **Costs:**
  - more SLOC: 279 against 216, 221, 153 and 231 (21% more than the largest, the careful saga), and more bytecode: 3,729 opcodes against 2,854, 3,247, 2,945 and 3,034;
  - 40 framework types against 5, 5, 5 and 8;
  - more classes and functions (35 named classes and 32 functions, against 20–24 classes and 13–26 functions), and a higher total cyclomatic complexity (80 against 58, 62, 56 and 49);
  - lower cohesion than three of them: CAMC 0.40 against 0.66, 0.52, 0.37 and 0.67; mean LCOM4 1.60 (2 of 5 measured classes at 1) against 1.00, 1.67, 1.00 and 1.00;
  - a larger mean distance from the main sequence than two of them when only dependencies between feature packages count (0.44 against 0.35, 0.44, 0.40 and 0.46). When dependencies on libraries and the simulation count too, it is 0.26 against 0.35, 0.13, 0.03 and 0.42.
- **Gains:**
  - a lower maximum cyclomatic complexity per function (8 against 7, 31, 15 and 18) and mean (2.50 against 2.23, 4.77, 3.73 and 3.50; the careful layered version is lower on both);
  - a lower mean CBO than three of them (3.94 against 4.70, 3.67, 5.00 and 4.29) and a lower maximum than two (18 against 16, 23, 21 and 15);
  - 89% of the code in pure classes against 28%, 28%, 66% and 40%;
  - propagation cost: the lowest of the nine per named class (13.1% against 14.8–31.0%) and per top-level class (23.4% against 26.4–41.7%). Per source file it ties with both saga versions at 48.0% (the others 50.0–75.0%); the file graphs have only 2–6 nodes.
- **Failure handling, a difference in kind rather than a cost or a gain:**
  - no exception handler (`catch` or `runCatching`) in Ballarch's feature code, against 5, 3, 5 and 5 in the careful versions; the naive actors and MVU versions have one `runCatching` each;
  - instead, Ballarch makes 6 calls whose failure or timeout the runtime returns as a value (5 `Call`s and 1 `Runtime.request`), the most of the nine; the actors versions make 2 (naive) and 4 (careful) such calls (`ask`), the others none;
  - its two adapters classify provider failures once, as `Reply.Failure` values, because they use the provider's callback API. The careful versions make the same classification in `catch` clauses over the throwing client, and write the write-ahead status and the reconciliation into their own code.
- **What care costs in each style:** each careful version is 47–58 SLOC larger than its naive version (layered +50, actors +58, MVU +57, saga +47) and has a total cyclomatic complexity 12–25 higher (42 → 58, 40 → 62, 31 → 56, 37 → 49).

### Change impact

The four change requests of [`changes/`](changes/README.md), each applied to all nine designs (RESULTS.md section 13). *Code lines* are logical lines (statements, declaration headers and `when` branches, however they are wrapped) added, removed or changed, without `package` and `import` lines; *with imports* adds the import lines added or removed. Physical lines and tokens are given beside them, because the ranking depends on what is counted.

- **No requirement broke.** With each change, the four careful versions and Ballarch violated no requirement, old or new, in any Stress or Mild cell (8,000 runs per design and change request, half of them with a crash) or at any swept crash point (25,305 to 96,455 points per design and change request). Without the change, every design violated the change request's own requirements (for example 5,680–5,806 of 8,000 runs in CR1, where the cancellation of a completed order is ignored), so the new requirements catch a design that lacks the change. Beyond the horizon the reconciling designs still depend on it. In CR2, DoubleAward occurred in 170–187 of 4,000 runs per reconciling design: a late award takes effect after the status said "not awarded" and the award was sent again, which the CR2 policy does where the charge's policy fails the order. In CR3, DoubleCharge occurred in 150–151 runs: the primary charges late, after the failover. The same failover cut FalseFailure from 153 runs without the change to 5. FalseFailure, which the base scenario already has beyond the horizon, stayed at 152–154 runs in CR1 and CR2 and rose to 226 in CR4, where more orders are charged. The naive versions kept their violations.
- **Size: Ballarch's change was the largest of the five reconciling designs in CR1 and CR3, and over the four change requests, by every measure. In CR2 it was the smallest by code lines and physical lines, but not with import lines or by tokens; in CR4 it was within their range by lines and the largest by tokens.**
  - CR1 (refund within a window): 73 code lines in 4 files and 16 units, against 34–43 code lines, 2–5 files and 5–6 units for the careful versions (with imports 87 against 36–45; physical lines 97 against 38–54; tokens 1,140 against 341–553). Ballarch's checkout and payment Balls each had to accept a second kind of request, so both request types became sealed interfaces, and the acceptance time had to be carried through three states of the checkout's state machine.
  - CR2 (loyalty points, a second effect without idempotency keys): 50 code lines against 64–68 for the careful versions, the fewest of the five, and 73 physical lines against 80–94. With its 34 import lines (the careful versions: 7–22) it is 84 against 71–89, and in tokens 899 against 633–974, the fourth smallest of five on both. Every reconciling design, Ballarch included, wrote the award's reconciliation again (Ballarch's new loyalty Ball reconciles as its payment Ball does, and sends the award again after "not awarded"); Ballarch did not write the write-ahead record, the classification of each attempt or the recovery after a restart, which come from its runtime. It touched the most units (9 against 6–8).
  - CR3 (failover): 18 code lines against 11–16, the most of the five (physical lines 23 against 12–20; tokens 249 against 104–179).
  - CR4 (remove the inventory): 38 code lines against 8–48 (MVU 8, where the stock was a field of the model; careful actors 48), the third smallest of five; with imports 51 against 8–53, tied third with the careful saga version; physical lines 58 against 10–59; tokens 720 against 109–584, the most.
  - Over the four change requests: Ballarch 179 code lines, the careful versions 122 (MVU), 152 (layered), 155 (saga) and 173 (actors); the naive versions 77–126. With imports, Ballarch 242 against 131–192; physical lines 251 against 155–220; tokens 3,008 against 1,527–1,954.
  - Ballarch's code has the most tokens per code line in these patches (about 17, against 10–15 for the careful versions): explicit type arguments such as `step<CheckoutState, Unit>` and qualified state names. Its patches also change more import lines (63 over the four change requests, against 9–34 for the careful versions): 21 in its composition root and 26 in the files of the Balls it adds or deletes.
- **Files and units.** Ballarch touched 2–4 files per change request, within the careful versions' 2–5. It touched more top-level units than every careful version in three of the four change requests (16, 9 and 9 against at most 6, 8 and 7), partly because its API file declares each request type as a top-level class. An earlier, unpublished prototype measurement, which earlier versions of the specification and the decision guide cited (cross-feature changes touching more files than single-module baselines in 4 of 5 change requests), is not reproduced here: no change touched more than 5 files in any design, and Ballarch's file counts were within the others' range. Those baselines are not these designs, so this does not refute that measurement; it does not support it either.
- **Left out: the scenario-B variants.** The scenario-B variants call the scenario-A constructors and use its types, and the patches do not touch them. With the patches, 0–2 files per design and change request no longer compile (Ballarch: 2 in CR1, none in CR2 and CR3, 2 in CR4; the MVU variants none); RESULTS.md section 13 lists them. Those edits are not in the counts above.
- **What care costs in a change.** For the second external effect (CR2), the careful versions needed 64–68 code lines against 27–37 for the naive versions. For the other three change requests, the careful version of a style needed between 5 fewer and 13 more code lines than its naive version (most for actors in CR4: 48 against 35).

### Runtime overhead

On the machine recorded in [`results/overhead.json`](results/overhead.json) (a 4-processor Linux VM, OpenJDK 21), a request through the reference runtime on its production scheduler took a median of 46.0 µs (99th percentile 121 µs) against 0.04 µs for a direct call of the same decider; the medians of its three rounds were 45.1–46.0 µs. With its tasks run on the caller's thread, the runtime's own work was a median of 0.68 µs (99th percentile 1.5 µs) and about 1.1 KB allocated per request. Most of the difference is therefore the hand-off from the caller's thread to the runtime's thread and back. The same-thread and direct variants were still getting faster from one round to the next (same-thread medians 1.33, 0.68 and 0.34 µs), so the JIT compiler had not settled after their warm-up, and their numbers are upper bounds of a settled JVM's. With the durable file store, which forces every commit to the device, the median was 1.25 ms. Other machines will differ. Earlier versions of the specification and the decision guide cited an unpublished measurement of 39 µs per request over a direct call, with about 0.5 µs and 1 KB of the runtime's own work; this one can be reproduced, and on this machine the hand-off cost more.

LCOM4 counts a class as split when one method uses none of its fields. Each Ballarch decider keeps its state in a parameter, not a field. `initial` in CheckoutFlow and PaymentBall and `decide` in InventoryBall therefore use no field, and those three classes score 2. The naive MVU file of `init` and `update` scores 2 for the same reason; in the careful MVU file, `init` and `update` share the helper `put`, so it scores 1. Ballarch's message and state types have only generated members and are not measured.

## Threats to validity

- **One author wrote all nine implementations and the scenario-B adaptations**, and that author also designed Ballarch. Each version is one reading of its style. The naive versions share a provider-failure policy that the author chose and that no cited source prescribes, so their violation rates measure that policy and the fault mix, not the styles. The careful versions apply the policy of the hand-hardened version, which is the reconciliation of Section 8.4 of the Ballarch specification, with the same budgets as Ballarch; they were written after the hardened and Ballarch results were known. Ballarch's kernel and runtime are not used in them, but its view of the problem shaped them. The first scenario-B adaptation of Ballarch gave it a smaller retry budget than the careful versions, because its adapter's attempt ended at the call's deadline; a reviewer showed this, and the adaptation was changed to the same budget, while the first one is kept as the reference-adapter row. Independent implementations, ideally written before the results are seen, would make the comparison stronger.
- **One small scenario.** The scenario has three orders, one SKU, two providers (without and with idempotency keys), at most one crash, and a simulated provider and database. Scenario B's provider keeps every key for the whole run and replays the first result for a repeated key; real providers expire keys after some time and may refuse a request whose key is still in flight.
- **The retry budgets are choices.** The careful versions and Ballarch get three charge requests and three status queries, with no pause between attempts; the naive versions get one request in scenario A and the same three in scenario B. The scenario-B results depend on that number. Under Stress, where a request goes unanswered with probability 5/6 and goes unanswered without taking effect with probability 2/6, a naive version with N same-key requests reports a paid order as failed with probability (5/6)^N − (2/6)^N (0.54 for N = 3, 0.33 for N = 6), and the layered design that ends in `NeedsAttention` hands a paid order to an operator with probability (5/6)^N (0.58 for N = 3, 0.33 for N = 6). An earlier reviewer's probe of that design used six requests 500 ms apart. Ballarch's runtime counts attempts per call and its payment Ball counts calls, so the same budget per order depends on how its adapter reports a refusal (see Scenario B). With a refusal reported as evidence, as the scenario-A adapter does, a refused first attempt starts a new call, and Ballarch can send up to five requests per order, of which at most three can have reached the provider. That variant was measured once with the same seeds and 2,000 runs per cell, outside the published cells: it violated no requirement in any cell, and under Stress without crashes it sent 1.79 charge requests per order against 1.69, handed 0.210 `NeedsAttention` per order to an operator against 0.221, and completed 1.346 orders per run against 1.304 (with one crash: 0.229 and 1.291).
- **The scenario-B adaptations are choices.** Ballarch's adapter times out each attempt after 1 s, which the reference HTTP adapter does not do; the reference-adapter row shows what that changes. The careful versions keep their scenario-A recovery (reconcile by status after a restart); sending again with the key on recovery, as Ballarch's Durable runtime does, would probably remove their Beyond-horizon crash violations and complete more orders after a crash under Mild, and was not measured.
- **The fault distributions are assumptions.** Stress is adversarial by design.
- **The delivery horizon is an assumption that the reconciling designs depend on.** The careful versions and Ballarch treat a "no charge" status read after the declared 1 s horizon as final. Under Stress and Mild the simulator guarantees that horizon; under Beyond horizon all five report charged orders as failed in 3.5–4.2% of runs in scenario A. In scenario B the careful versions depend on it only after a crash (3.3% of runs), Ballarch in none of the sampled runs and at 5 of 28,838 swept crash points, Ballarch with the reference adapter also without a crash (4.2% of crash-free and 1.9% of crash runs), and the layered design that ends in `NeedsAttention` not at all. The late delay (5 s) is the environment's existing delay for late answers, not a tuned value. A request that takes effect before their first status query cannot fool them; in scenario A that query goes out about 2 s after the send (their 1 s timeout plus the 1 s horizon), so a delay shorter than that would cause fewer violations or none. A wrong horizon is a correctness assumption, not a cost.
- **The crash model is a choice.** There is one crash per run, at a time uniform over each run's own busy period. The reconciling designs wait past the horizon and run longer (4,978 ms against 762 ms on average under Stress in scenario A), so their crash times spread over a longer period; crash times are comparable relative to each run, not in absolute time. Scheduler tasks take no virtual time, so a crash at a time comes before every task of that instant and never between two of them. A real process spends time in each step, so a real crash can fall between two steps; the crash cells do not sample those points, and the naive designs differ only there. The exhaustive sweep covers them, but counts them per task. The client re-sends orders that were never accepted.
- **Metrics have known biases.**
  - LCOM4 assumes that classes share fields, so it penalizes deciders that keep their state in parameters: Ballarch's Balls, and the naive MVU's `update`. Few classes are measured: 2–6 per design.
  - Propagation cost and CBO depend on how finely code is split into classes. Ballarch's sealed state hierarchies give it 35 named classes in 16 top-level classes and 5 files; its propagation cost is 13.1%, 23.4% and 48.0% at those granularities.
  - Martin's D depends on which dependencies count; both variants are given.
  - Cyclomatic complexity from bytecode counts null-safety operators, comparisons used as values and the branches of `@InlineOnly` standard-library functions, but not `catch` clauses, so it differs from a count on the source.
  - The failure-handling counts depend on the API each design calls. Ballarch's adapters use the provider's callback API, which reports failures as values, and the other eight the throwing client, so Ballarch needs no exception handler where the others need one. The count of calls whose failure a library returns as a value finds the kit functions by a scan, but takes Ballarch's two entry points from a list written by hand.
  - SLOC and framework-type counts depend on the excluded toolkits.
  - The actors versions keep each checkout's whole command handler in one function, as the naive version did; that makes the careful actors `checkout` the most complex function measured (31). Splitting it per stage, as Akka's finite-state-machine style would, would lower the maximum but not the total.
  - The scenario-B line counts depend on how each adaptation was written. The extra layered design was written as a change of the naive layered version, and both Ballarch rows as changes of scenario-A Ballarch.
- **Not represented:** a durable-execution engine (Temporal, Restate, Azure Durable Functions). Advice to prefer one is not backed by this benchmark.
- **The change requests are few, and their author wrote the designs.** Four change requests on a feature of 96–279 SLOC ([RESULTS.md](results/RESULTS.md) section 8), implemented by the author of every design and of Ballarch after the base results were known; three of the four concern an unreliable external service, which is where Ballarch's runtime is meant to help, and none changes only business rules or data. Each patch is one reading of how an expert in the style would make the change. Code lines and units touched are proxies for the effort of a change; review time and defects introduced were not measured. Two requirements (CR3's MissedFailover and CR4's UnchargedFailure) were corrected after the first runs, when correct designs violated them at crash points between recording a charge and sending it; [`changes/README.md`](changes/README.md) gives both versions.
- **The size comparison depends on what is counted.** The differences between the reconciling designs are a few lines in CR3 and CR4, and the ranking changes with the measure: Ballarch's CR2 change was the smallest of the five by code lines and physical lines, but fourth by tokens and with import lines counted. Ballarch's code has more tokens per line (explicit type arguments, qualified state names) and its patches change more import lines. The first published version counted physical lines under a formatting rule with a wrong stated reason, and one ranking flipped when that rule was corrected; the headline now uses logical lines, which do not depend on wrapping. The patches also leave out the scenario-B variants' call sites (see [Change requests](#change-requests)).
- **Not measured:** developer effort, review speed, throughput under load, and behaviour on a real network or a production durable store. Runtime overhead was measured on one machine only (see [Runtime overhead](#runtime-overhead)).
- **The benchmark was not pre-registered.**

## Reproduce

Requires JDK 21 and Python 3.10 or later (standard library only). From `reference/kotlin`:

```sh
./gradlew :benchmark:runner:run --args="2000 ../../benchmark/results"
python3 ../../benchmark/report.py ../../benchmark/results/results.json ../../benchmark/results
```

The run takes about two minutes. A third argument sets the number of seeds of the crash sweep (by default half the runs per cell).

The change requests and the runtime overhead (from the repository root; `verify.py` takes extra Gradle arguments with `--gradle-arg`):

```sh
python3 benchmark/changes/measure.py           # patch metrics; --check verifies that every patch applies and its numbers are current
python3 benchmark/changes/verify.py            # applies each change request in a temporary copy, builds and runs it (about five minutes on 4 processors)
(cd reference/kotlin && ./gradlew :benchmark:runner:overhead)   # writes benchmark/results/overhead.json
python3 benchmark/report.py benchmark/results/results.json benchmark/results
```

`./gradlew build` also runs [`BenchmarkTest`](runner/src/test/kotlin/bench/runner/BenchmarkTest.kt). It repeats the headline observations on 200–300 runs per cell (scenario A and B) and the crash sweep on 60 seeds, checks that every seeded bug is detected and every recovery bug only with a crash, checks that every crash-cell run crashes and that a crash at a time comes before every task due at that time, checks that in scenario B Ballarch and the careful versions send the same requests and reach the same outcomes without crashes, and checks the complexity and cohesion counts against hand-worked fixtures. It also runs [`ChangeRequestsTest`](changes/runner/src/test/kotlin/bench/changes/ChangeRequestsTest.kt), which checks that every design of this checkout, which has none of the change requests, violates each change request's own requirements.
