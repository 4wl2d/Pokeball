# Architecture benchmark: results

Generated by `benchmark/report.py` from `results.json` (2000 runs per cell). Method, definitions and threats to validity: [README](../README.md). Rates are shares of runs, with Wilson 95% intervals in brackets.

Scenario A: the provider has no idempotency keys. Scenario B: the provider honours idempotency keys, and every design is adapted to send them. In both, Stress and Mild respect the provider's declared 1 s delivery horizon; under Beyond horizon about 2% of requests take effect 5 s after they were sent. In crash cells every run crashes exactly once. The *naive* designs share one provider-failure policy chosen by the author (a timeout or I/O error means the payment failed); the *careful* designs handle uncertainty with their style's own tools.

## 3. Scenario B: a provider that honours idempotency keys

Every charge request carries an idempotency key, and the provider does not charge a key twice. The naive designs send a key derived from the order and repeat a request that got no answer with the same key, up to three requests per incarnation, then treat the payment as failed. *Layered, same-key retries, then NeedsAttention* exists only in this scenario: the naive layered design whose retries end in `NeedsAttention` instead of `Failed`. The careful designs repeat an unanswered or refused request with the same key within the same budget of three requests, then reconcile as before. Ballarch declares the charge port Idempotent and sends the call identity as the key; its adapter ends an attempt after 1 s, and its runtime repeats a failed attempt with the same key, up to three requests within the call's 3 s deadline, then the payment Ball reconciles as before. *Ballarch, reference adapter* exists only in this scenario: the same adaptation with an adapter whose attempt ends at the call's 1 s deadline, as in the reference HTTP adapter, so that the runtime never repeats a request whose answer was lost.

## 5. Exhaustive single-crash sweep

A separate check of every point at which a single crash can hit: for each of the first 1000 crash-cell seeds, one run per scheduler task of its crash-free run, crashing immediately before that task. It includes the points between two tasks of the same instant, which a crash time never selects. The points are each design's own scheduler tasks, so their number, and the share of them that violate, depend on how finely a design splits its work into tasks: the share is not comparable across designs.

## 13. Change impact: four change requests

Four change requests, specified in [`changes/README.md`](../changes/README.md) before they were implemented, were applied to the scenario-A code of every design, each as one patch per design (`benchmark/changes/<change request>/<design>.patch`). CR1 refunds a completed order that the customer cancels within 30 s; CR2 awards loyalty points through a second external service without idempotency keys; CR3 adds a second payment provider and fails over to it when the first provably did not charge (the naive versions: when the first failed); CR4 removes the inventory. The same author wrote every patch, after the base results were known.

Three sizes are given for each patch, all computed per file by `difflib` on the code without `package` and `import` lines; in a replaced block, the first min(old, new) lines count as changed and the rest as added or removed. *Code lines* are logical lines: a statement, a declaration header or a `when` branch, however it is wrapped, compared as a sequence of tokens, so they do not depend on line wrapping. *Physical lines* are lines that hold code, compared without indentation, as in section 9; they depend on how each statement is wrapped (the patches follow one formatting rule, given in changes/README.md). *Tokens* (identifiers, keywords, literals, operators and brackets) added and removed depend on no formatting, but count a long qualified name or an explicit type argument as several tokens. The import lines added or removed are counted separately; *with imports* adds them to the code lines. A unit is a top-level class, interface or object with everything nested in it, or the top-level functions and properties of one file; it is touched when one of its code lines is added, removed or changed. Unit counts depend on how a design splits its declarations: Ballarch's `Api.kt` declares each request type as a top-level class, so a change to its messages touches several small units.

## 14. Runtime overhead (machine-dependent)

Measured by `./gradlew :benchmark:runner:overhead`, which writes `benchmark/results/overhead.json`, on OpenJDK 64-Bit Server VM 21.0.12.1+1-1-24.04.4-Ubuntu (Ubuntu), Linux 6.18.44-fc-v139 amd64, 4 processors (2026-10-21). These numbers depend on the machine and its load, so `overhead.json` is not regenerated by CI and is not part of the byte-for-byte check of `results.json`. Each variant performs the same request, a counter increment, and is timed per request after a warm-up; *bytes* are those allocated on the caller's thread, which for the same-thread variant is all the work of a request. Every variant was measured in 3 rounds in one JVM, each with a fresh runtime and its own warm-up, the rounds taking the variants in turn; each statistic is the median of the rounds, with the lowest and highest round in parentheses.
