## 6. Алгебра протокола

<a id="61-surfaces"></a>

### 6.1. Поверхности

Каждый `Ball` разделяет как минимум три поверхности протокола.

| Поверхность | Назначение | Основные типы |
|---|---|---|
| External Interaction | Пользователь, HTTP, CLI, ОС, UI | `Intent`, `Query`, `ReadResult`, `BoundaryResponse`, `Projection`, `Reply` |
| Private Resource | Собственные адаптеры и исполнители | `Effect`, `Fact` |
| Integration | Другие Ball и Flow | принадлежащие получателю `ModuleCommand`/`ModuleResult`, `ModuleCommandPulse`, `ModuleResultPulse`, `ModuleResultOutput`, `Signal`, публичные контракты чтения |

Поверхности — логические границы владения, а не обязательно непустые API. Ball объявляет только используемые замкнутые варианты; пустая поверхность Resource или Integration не требует типов, файлов, нулевых пределов или раздела манифеста.

Транспортный конверт, сериализация, токен аутентификации и метаданные брокера не становятся частью смысловой полезной нагрузки автоматически.

### 6.2. Intent

<!-- pkb-translation:term:start name="Intent" -->
**Intent** — проверенный запрос начать изменение состояния или операцию.
<!-- pkb-translation:term:end -->

```text
SearchRequested(query, pageSize)
CheckoutStarted(cartId, paymentMethodRef)
DocumentCloseRequested(documentId)
```

`Intent` не содержит необработанного HTTP-запроса, дерева JSON, изменяемого DTO, ссылки на репозиторий или сервис либо произвольной карты.

### 6.3. Query

<!-- pkb-translation:term:start name="Query" -->
**Query** — запрос чтения без изменения зафиксированного состояния или владельца чтения; для конкретной версии протокола он однозначно сопоставляется с одной принадлежащей получателю полезной нагрузкой результата, полной для каждого достижимого смыслового исхода после допуска.
<!-- pkb-translation:term:end -->

```text
GetCatalogView
GetCheckoutStatus(operationId)
```

<!-- pkb-translation:term:start name="ConsistencyStamp" -->
**ConsistencyStamp** — точная доступная идентичность зафиксированного снимка, использованного успешным чтением, когда действует условие чтения с отметкой: ревизия и только активные идентичности экземпляра/схемы; сама по себе не обещает ни последующей свежести, ни атомарности нескольких источников.
<!-- pkb-translation:term:end -->

Записи ниже — структурные проекции помеченных определений.

<!-- pkb-translation:term:start name="ReadContext" -->
**ReadContext** — доверенный контекст локального чтения с минимальным набором полей; его зависящая от актора форма проверена, ограничена и создана доверенной границей привязки по смысловой схеме, принадлежащей Ball/Nucleus. Контекст актора появляется, только когда меняет авторизацию/выбор результата чтения; фиксированный издатель/область в том же стеке может доказываться статически, независимое от актора чтение не создаёт артефактов актора, а селекторы принадлежат типизированному `Query`.
<!-- pkb-translation:term:end -->

Записи ниже — структурные проекции помеченных определений.

<!-- pkb-translation:term:start name="CommittedStateSnapshot" -->
**CommittedStateSnapshot** — неизменяемый вход чтения с отметкой, объединяющий Sovereign State с его `CommitRevision`; `BallInstanceId` и `stateSchemaVersion` появляются, только когда наблюдается идентичность экземпляра или сохранённой схемы.
<!-- pkb-translation:term:end -->

Записи ниже — структурные проекции помеченных определений.

Материализованный `read` с отметкой, используемый при условии §8.10/`PBA-30`:

```text
CommittedStateSnapshot<State> {
    commitRevision
    ballInstanceId?        # instance identity crosses scope
    stateSchemaVersion?    # persisted/migrated schema identity is observed
    state: State
}

ReadContext {
    protocolVersion?       # independently versioned boundary
    actorContext?          # read authorization/result selection depends on actor context
}

ConsistencyStamp {
    commitRevision
    ballInstanceId?
    stateSchemaVersion?
}

ReadResult<ResultPayload> {
    payload: ResultPayload
    consistencyStamp: ConsistencyStamp
}

read(
    snapshot: CommittedStateSnapshot<State>,
    query: Query,
    context: ReadContext
) -> ReadResult<ResultPayload>
```

Для каждого `Query` в одной действующей идентичности протокола авторитетные типизированные исходники или манифест ДОЛЖНЫ однозначно сопоставлять ровно один статически известный `ResultPayload`. Материализованные записи выше имеют минимальный набор полей: `commitRevision` определяет снимок с отметкой; идентичность экземпляра появляется, только если экземпляров больше одного или есть путь идентичности через область; идентичность схемы — только когда наблюдается идентичность сохранённого/мигрированного состояния; `protocolVersion` — только на независимо версионируемой границе; контекст актора — только когда от него зависит авторизация чтения. Точная охватывающая область типа/сборки может доказать необязательную идентичность без поля runtime. Дополнительные селекторы — поля самого `Query`, а не неявные наблюдения. `ConsistencyStamp` определяет зафиксированный снимок, из которого построена полезная нагрузка, но не обещает ни свежести после возврата, ни атомарности нескольких источников.

Если зафиксированный State, доверенный `ReadContext` или политика чтения могут менять разрешение или выбор результата, единственный принадлежащий получателю `ResultPayload` ДОЛЖЕН быть замкнутым объединением, полным для каждого достижимого смыслового исхода Query после допуска. Он содержит ровно применимые разрешённые, запрещённые, частично скрытые и намеренно не раскрывающие сведения варианты; путь, который не может достичь категории, не объявляет заглушку. Чистый Policy Gate Nucleus/чтения выбирает вариант после допуска. Успешное вычисление чтения означает завершение этого смыслового выбора получателя; оно не означает разрешённого доступа или раскрытия исходной записи.

Получатель может намеренно сделать отказ политики неотличимым по наблюдению от отсутствия только через объявление одного точного варианта результата без раскрытия сведений и его сопоставления в протоколе получателя. Граница, вызывающая сторона, Assembly, runtime и сгенерированная привязка не могут придумать или подставить `NotFound`, сокрытие полей, отказ, исключение, `BusinessRejection` или другой носитель. Неверные происхождение, получатель, версия, полномочия, сопоставление или отметка остаются сбоем границы и никогда не становятся смысловым результатом без раскрытия сведений.

Когда контекст актора может менять авторизацию чтения или выбирать возвращаемый смысловой результат, доверенная граница привязки строит `ReadContext` из проверенных ограниченных наблюдений с минимальным набором полей по `PBA-44`; Ball/Nucleus владеет схемой контекста и чистым толкованием. Фиксированный доверенный издатель/область в том же стеке может доказываться статически без материализованных полей издателя, аутентификации или доказательств актора. Независимый от актора Query использует `Unit` или `ReadContext` без актора и не создаёт артефакта актора.

Локальный getter в том же стеке без кеша, сравнения во времени, доказательства отсутствия статуса, агрегации или заявления о свежести/согласованности может стереть представление обёрток:

```text
read(state: State, query: Query, context: Unit | ReadContext)
    -> ResultPayload
```

Неизменяемое состояние в области вызова и замкнутый тип результата доказывают те же инварианты отсутствия изменений и сопоставления результата; объекты `BallInstanceId`, ревизии, версии схемы или отметки не выдумываются.

Материализованный `ReadResult` — только успешно вычисленный незафиксированный ответ: его полезная нагрузка сама может быть объявленным получателем смысловым исходом отказа, сокрытия полей или нераскрытия сведений. Это не `SemanticOutput`, у него нет `SemanticHandle`, `sourceOrdinal` или новой ревизии, и на него не действует фиксация до отправки. Неуспешный путь границы, валидации или допуска возвращает существующий `BoundaryResponse`, а не придуманный вариант результата чтения. Любая форма локального чтения не меняет состояние, не создаёт `Effect` и не скрывает внешнее I/O. Если чувствительное чтение требует атомарной записи аудита, моделируйте его как явную аудируемую операцию или отдельный профиль аудируемого чтения, а не скрытый побочный эффект внутри чистого `read`.

### 6.4. Effect

<!-- pkb-translation:term:start name="Effect" -->
**Effect** — частная декларативная внешняя операция Ball-владельца.
<!-- pkb-translation:term:end -->

```text
FindProducts(query, pageSize)
PersistSession(snapshot)
ReadCurrentTime
CaptureProviderPayment(...)
```

`Effect` описывает разрешённое действие, а не объект сервиса или вызов функции.

### 6.5. Fact

<!-- pkb-translation:term:start name="Fact" -->
**Fact** — проверенный, привязанный к происхождению исход ранее принятого `EffectRequest`; немедленное завершение может использовать корреляцию области вызова, а отделённое/допускающее смену порядка завершение и наблюдения подписок несут стабильную материализованную причинную идентичность.
<!-- pkb-translation:term:end -->

```text
ProductsFound(handle, products)
ProductSearchFailed(handle, reason)
CurrentTimeObserved(handle, timestamp)
```

Fact содержит причинную ссылку, сопоставляющую его с принятым `EffectRequest`. Немедленное синхронное завершение может использовать принятую позицию области вызова; завершение, которое может отделяться, менять порядок, повторяться, пересекать границу, восстанавливаться или входить в статус, несёт полную стабильную идентичность дескриптора/источника по §9.1. Push-наблюдение или наблюдение подписки — это `Fact`, только если сама подписка ранее принята и наблюдение возвращает её стабильный `SemanticHandle`. Незапрошенное наблюдение ресурса не должно выдаваться за `Fact`.

### 6.6. Projection

<!-- pkb-translation:term:start name="Projection" -->
**Projection** — неизменяемое смысловое состояние представления для потребителя/отрисовщика.
<!-- pkb-translation:term:end -->

```text
CatalogSearchStatus(operationId, lifecycle, cancellation)
CheckoutReady(summary)
```

Projection — не сущность базы данных, не изменяемая общая модель представления и не транспортный DTO.

<a id="67-boundaryresponse-and-reply"></a>

### 6.7. BoundaryResponse и Reply

<!-- pkb-translation:term:start name="BoundaryResponse" -->
**BoundaryResponse** — ответ границы/runtime, зависящий от стадии, для запроса без принятого Decision: `ValidationFailure`, `AdmissionFailure` или `DecisionRejected`; это не `SemanticOutput`, он не проходит фиксацию до отправки. На маршруте команды проверенный ответ может возвращаться только внутри `CommandRejectedBeforeAcceptance`; он не может представлять принятый результат получателя, исход Resource после принятия или остановку доставки.
<!-- pkb-translation:term:end -->

```text
BoundaryResponse =
    ValidationFailure
  | AdmissionFailure
  | DecisionRejected(BusinessRejection)
```

`BoundaryResponse` — не `SemanticOutput`, у него нет `SemanticHandle`, `sourceOrdinal` или `CommitRevision`, и он не подчиняется фиксации до отправки. Некорректный вход и сбои аутентификации или валидации отклоняются до создания `Intent`; Interaction кодирует фактический `Rejected(BusinessRejection)` Nucleus как `DecisionRejected`, не превращая его в зафиксированный `Reply`.

Несовпадение идемпотентности входа обнаруживает объявленный владелец Interaction/идемпотентности до построения `Intent`. В пределах покрываемого горизонта записи одинаковые `IdempotencyScope + IdempotencyKey` с другим `IntentFingerprint` возвращают ровно `BoundaryResponse(ValidationFailure(IdempotencyConflict))`. Это никогда не `DecisionRejected`: отказа Nucleus не было. Это не создаёт сопоставление кандидата или принятой операции, Decision, ревизию, дескриптор, Reply, выход или источник статуса и не меняет ранее принятую операцию. Напротив, повтор уже принятого корня с тем же отпечатком — не `BoundaryResponse`; §9.6 повторно доставляет доказательство исходного принятого фрейма `ReplyOutput`.

<!-- pkb-translation:term:start name="Reply" -->
**Reply** — адресный смысловой ответ, привязанный к запросу/операции и существующий только как полезная нагрузка принятого `ReplyOutput`; сбой границы или отказ до принятия — не Reply.
<!-- pkb-translation:term:end -->

```text
RequestAccepted(operationId)
CheckoutCompleted(orderId)
```

`Reply` отличается от `Projection`: ответ имеет семантику запрашивающей стороны и корреляции, а проекция описывает наблюдаемое представление состояния. `Reply` существует только как полезная нагрузка принятого `ReplyOutput`.

### 6.8. ModuleCommand

<!-- pkb-translation:term:start name="ModuleCommand" -->
**ModuleCommand** — принадлежащая получателю адресная полезная нагрузка публичной команды для другого Ball-владельца полномочий.
<!-- pkb-translation:term:end -->

```text
Inventory.ReserveItems(...)
Payment.Capture(...)
Notification.SendReceipt(...)
```

Command — не частный `Effect`. Для каждой командной операции получатель владеет ровно одним замкнутым версионированным сопоставлением `ModuleCommand -> ModuleResult`. Вызывающая сторона импортирует сопоставление через `dependencies.commands`; она не делает команду псевдонимом внешнего `Intent` и не объявляет повторно любую полезную нагрузку как собственную.

<!-- pkb-translation:term:start name="ModuleCommandPulse" -->
**ModuleCommandPulse** — канонический проверенный вход получателя, несущий `commandSource` принятого источника, действующую идентичность протокола, принадлежащий получателю `ModuleCommand` и происхождение издателя; `decide` получателя — единственная точка его принятия.
<!-- pkb-translation:term:end -->

Доверенная граница получателя строит канонический вход команды только из проверенного принятого фрейма источника:

```text
ModuleCommandPulse {
    commandSource: CausalToken
    effectiveProtocolIdentity
    command: ModuleCommand
    issuerProvenance
}
```

`commandSource` выводится из принятого фрейма `ModuleCommandRequest` источника, включая полный смысловой дескриптор и порядковый номер источника. `effectiveProtocolIdentity` разрешает принадлежащее получателю сопоставление команды/результата. Граница получателя проверяет принятие источника, идентичность протокола, владение полезной нагрузкой, размер, происхождение и каждое активное правило подлинности до построения Pulse. Канонический `decide` получателя — единственная точка принятия; получение транспортом, вызов адаптера, строка inbox, ACK или вызов маршрута не являются принятием получателя.

Assembly выбирает маршрут, действующую пару протокола/версий и привязку и передаёт проверенное значение. Она не создаёт и не меняет `commandSource`, полезную нагрузку команды, происхождение издателя или другой бизнес-смысл. Привязка в том же стеке может стереть материализованный адаптер или конверт, только когда точный принятый кортеж источника и вход получателя доказуемо остаются идентичными.

### 6.9. ModuleResult

<!-- pkb-translation:term:start name="ModuleResult" -->
**ModuleResult** — принадлежащая получателю полезная нагрузка бизнес-исхода для одного сопоставления команды получателя; выпускается только через `ModuleResultOutput` и принимается как полезная нагрузка `ModuleResultPulse`.
<!-- pkb-translation:term:end -->

```text
InventoryReserved(reservationId)
InventoryReservationRejected(reason)
PaymentCaptureOutcomeUnknown(reference)
```

<!-- pkb-translation:term:start name="ModuleResultOutput" -->
**ModuleResultOutput** — канонический `SemanticOutput` получателя, создаваемый только внутри принятого Decision получателя; несёт `sourceOrdinal` фрейма получателя, `commandSource` принятого источника, принадлежащий получателю `ModuleResult` и `semanticHandle = commandSource.semanticHandle` для корреляции без передачи владения.
<!-- pkb-translation:term:end -->

Nucleus получателя создаёт результат только внутри принятого Decision получателя:

```text
ModuleResultOutput {
    semanticHandle = commandSource.semanticHandle
    sourceOrdinal
    commandSource: CausalToken
    payload: ModuleResult
}
```

`sourceOrdinal` — позиция выхода результата в принятом фрейме получателя. Равенство `semanticHandle` и `commandSource.semanticHandle` обеспечивает только корреляцию; оно не передаёт владение получателя и не реэкспортирует его полезную нагрузку. Выход всегда учитывается в контрактах `maxOutputsPerDecision` и `maxOutputBytesPerDecision` получателя. Если его маршрут сохраняется, повторяется или независимо наблюдаем, он также занимает один слот доставки/статуса получателя, для которого возможна остановка, и учитывается в соответствующих конечных пределах получателя.

<!-- pkb-translation:term:start name="ModuleResultPulse" -->
**ModuleResultPulse** — канонический проверенный вход источника, несущий `commandSource` принятого источника, `resultSource` принятого получателя, действующую идентичность протокола, принадлежащий получателю `ModuleResult` и происхождение издателя.
<!-- pkb-translation:term:end -->

Проверенный маршрут результата строит вход источника только из этого принятого фрейма получателя:

```text
ModuleResultPulse {
    commandSource: CausalToken
    resultSource: CausalToken
    effectiveProtocolIdentity
    result: ModuleResult
    issuerProvenance
}
```

`commandSource` остаётся токеном принятой команды источника. `resultSource` выводится из принятого фрейма получателя и определяет выход результата получателя в его `sourceOrdinal`. Маршрут проверяет оба принятых кортежа, принадлежащую получателю полезную нагрузку, действующую идентичность протокола и происхождение издателя. Assembly передаёт проверенные значения, но не создаёт и не меняет ни токен, ни полезную нагрузку результата. Стирание представления в том же стеке должно доказать те же кортежи источника и получателя.

Ключ доставки результата — ровно кортеж `(effectiveProtocolIdentity, commandSource, resultSource)`; Core не вводит отдельно названного типа идентичности. `DispatchStopped` на стороне получателя для этого выхода использует полный кортеж. Это факт доставки результата получателя; сам по себе он не задаёт аспект принятия источника, бизнес-исхода, отмены или статуса процесса.

Транспортный ACK и `ModuleResultPulse` — разные наблюдения. ACK может доказать принятие получателя, но не бизнес-успех. Pulse результата доказывает принятие получателя только через проверенное происхождение от принятого получателя.

При повторной доставке команды получателя с той же идентичностью/отпечатком после принятия фрейма команды, но до появления фрейма результата, получатель возвращает только проверенное ACK-доказательство исходного принятого фрейма и состояние ожидания результата. Он не строит предварительный `ModuleResult`, не ждёт завершения и не повторяет смысловую работу/работу Resource получателя. После принятия результата повторная доставка использует точное доказательство существующего фрейма результата и сохраняет `commandSource`, `resultSource`, действующую идентичность протокола, ревизию получателя, дескриптор/порядковый номер и полезную нагрузку; меняется только механический `AttemptId`. Противоречащий отпечаток или доказательство фрейма приводят к закрытому отказу.

Каждый версионированный контракт получателя статически классифицирует каждый достижимый отказ либо как ответ границы до принятия по §6.13, либо как принятый `ModuleResultOutput`. Привязка, профиль, повтор или условие runtime не могут выбирать форму динамически. Принятый результат обязателен, если отказ создаёт любое состояние получателя или запись операции, исход идемпотентного воспроизведения, выход, действие Resource, видимость статуса/сверки, заявление о долговечности или иное доказательство принятой операции. `DecisionRejected(BusinessRejection)` до принятия допустим, только если ни один из этих фактов получателя не был принят. Поэтому сбой Execution Gate или Resource после принятия получателем остаётся путём принятого результата получателя; сбой отправки никогда не понижает принятый результат до ответа до принятия. Доказательство носителя и доказательство принятого результата для одной действующей идентичности протокола и `commandSource` конфликтуют и приводят к закрытому отказу.

> Команда, похожая на чтение, допустима и осознанно несёт цену принятия получателем, если вызывающей стороне нужны привязанный к происхождению принятый результат, стабильная идентичность команды/шага, идемпотентное воспроизведение, статус или семантика сверки. Когда принятая запись получателя не нужна, верная конструкция — `ReadDependency`/`Query`, не создающая Decision, ревизии или смыслового выхода получателя.

### 6.10. Signal

<!-- pkb-translation:term:start name="Signal" -->
**Signal** — смысловая публикация без одной обязательной запрашивающей стороны; не универсальный `DataChanged`.
<!-- pkb-translation:term:end -->

```text
SessionRevoked
OrderConfirmed
CatalogIndexUpdated
```

Signal — не команда. Получатель не должен толковать публикацию как полномочие совершить привилегированное действие без отдельного разрешения или контракта команды.

<!-- pkb-translation:term:start name="ObservedSignal" -->
**ObservedSignal** — конверт причинного входа с проверенным происхождением, созданный из ранее принятого `SignalPublication` по объявленному маршруту сигнала.
<!-- pkb-translation:term:end -->

Получатель преобразует ранее принятый `SignalPublication` в конверт причинного входа:

```text
ObservedSignal {
    sourceBallInstanceId
    sourceCommitRevision
    semanticHandle
    sourceOrdinal
    signal: Signal
    issuerProvenance
}
```

`ObservedSignal` принимается только после проверки происхождения и соответствия зафиксированному `SignalPublication`. Наблюдения подписок Resource используют причинно связанный `Fact`, а не `ObservedSignal`.

### 6.11. Pulse

<!-- pkb-translation:term:start name="Pulse" -->
**Pulse** — упорядоченное замкнутое семейство `Intent | Fact | ModuleCommandPulse | ModuleResultPulse | ObservedSignal | ControlPulse`; необработанное внешнее изменение/отмена входит только как `Intent` после валидации Interaction и не является полем `DecisionContext`.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="ControlPulse" -->
**ControlPulse** — объявленное доверенное наблюдение жизненного цикла/таймера/отмены/доставки от границы runtime/ресурса/маршрута; это не необработанный внешний вход изменения. Если механическое наблюдение отправки/ACK после фиксации или носителя команды до принятия меняет Sovereign State, оно проходит как этот типизированный вход через `decide` единственного писателя, а не записывается runtime напрямую; бизнес-`Fact` или `ModuleResultPulse` не переклассифицируется. Decision обработки носителя в том же стеке потребляет переданный слот альтернативного завершения и не создаёт нового причинного корня.
<!-- pkb-translation:term:end -->


```text
Pulse =
    Intent
  | Fact
  | ModuleCommandPulse
  | ModuleResultPulse
  | ObservedSignal
  | ControlPulse
```

`ControlPulse` включает только объявленные наблюдения жизненного цикла, таймера, отмены или доставки. Произвольные системные события на строках не используются.

`ControlPulse` создаётся только доверенной границей runtime, ресурса или маршрута после проверки объявленного источника и происхождения. Необработанный запрос клиента, API или UI не может стать `ControlPulse`: после Double Quarantine внешний запрос начать или отменить смысловую операцию — это `Intent`. Результат отмены получателя или ресурса остаётся причинно связанным `Fact` или `ModuleResultPulse`; наблюдение отмены runtime может быть `ControlPulse`, только если эта собственная категория явно объявлена.

Если механическое наблюдение runtime или маршрута после фиксации об отправке или ACK меняет Sovereign State — например, переводит сохранённый шаг команды в `Dispatched`, записывает принятие или неоднозначность либо конечную остановку доставки, — runtime НЕ ДОЛЖЕН писать состояние напрямую. Он создаёт объявленный типизированный `ControlPulse`, после чего обычный `decide` единственного писателя применяет наблюдение. Уже типизированный бизнес-`Fact` или `ModuleResultPulse` сохраняет собственную причинную категорию и не оборачивается в `ControlPulse`. Проверенный `CommandRejectedBeforeAcceptance` из §6.13 переносится таким объявленным механическим наблюдением маршрута, а не Pulse результата. Механический Pulse доставки не может существовать до принятия источником; сама фиксация источника не доказывает отправку.

На ветви команды до принятия в том же стеке `decide(ControlPulse)` источника, применяющий носитель, потребляет переданное резервирование альтернативного завершения уровня 1, определённое в §8.4. Граница не создаёт ни нового причинного корня, ни незарезервированного слота завершения.

### 6.12. SemanticOutput

<!-- pkb-translation:term:start name="SemanticOutput" -->
**SemanticOutput** — упорядоченное замкнутое семейство `ProjectionOutput | ReplyOutput | EffectRequest | ModuleCommandRequest | ModuleResultOutput | SignalPublication | TimerRequest`; каждый присутствующий вариант имеет типизированную полезную нагрузку и принятую позицию последовательности с нуля, а стабильный `SemanticHandle` добавляется только для отделённой/адресуемой работы.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="ProjectionOutput" -->
**ProjectionOutput** — канонический конверт `SemanticOutput` с полезной нагрузкой `Projection` и принятой позицией последовательности; стабильный дескриптор присутствует, только когда проекция отделена/адресуема.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="ReplyOutput" -->
**ReplyOutput** — канонический конверт `SemanticOutput` с полезной нагрузкой `Reply` и принятой позицией последовательности; стабильный дескриптор присутствует, только когда доставка/статус ответа отделены или независимо адресуемы.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="EffectRequest" -->
**EffectRequest** — канонический конверт `SemanticOutput` с полезной нагрузкой `Effect` и принятой позицией последовательности; отделённое/адресуемое исполнение также несёт полный `SemanticHandle` и материализованный `sourceOrdinal`.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="ModuleCommandRequest" -->
**ModuleCommandRequest** — канонический конверт `SemanticOutput` с полезной нагрузкой `ModuleCommand` и принятой позицией последовательности; его путь между Ball активирует полный `SemanticHandle` и материализованный `sourceOrdinal`.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="SignalPublication" -->
**SignalPublication** — канонический маршрутизируемый конверт `SemanticOutput` с полезной нагрузкой `Signal`, полным `SemanticHandle` и материализованным `sourceOrdinal`.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="TimerRequest" -->
**TimerRequest** — канонический отделённый конверт `SemanticOutput` с полным `SemanticHandle`, материализованным `sourceOrdinal` и полезной нагрузкой `TimerIntent` для Ball с объявленными таймерами.
<!-- pkb-translation:term:end -->


```text
SemanticOutput =
    ProjectionOutput
  | ReplyOutput
  | EffectRequest
  | ModuleCommandRequest
  | ModuleResultOutput
  | SignalPublication
  | TimerRequest           # only if the Ball uses timers
```

Все варианты имеют типизированную полезную нагрузку и порядковый номер в принятой последовательности выходов. Стабильный дескриптор присутствует только при условии отделённой работы из §3.5; §20.1 — маршрут навигации к нему:

```text
SemanticOutputEnvelope<Payload> {
    semanticHandle: SemanticHandle?   # required for detached/addressable work
    sourceOrdinal: UInt32             # semantic position; may be representation-erased in call scope
    payload: Payload
}

ProjectionOutput     = SemanticOutputEnvelope<Projection>
ReplyOutput          = SemanticOutputEnvelope<Reply>
EffectRequest        = SemanticOutputEnvelope<Effect>
ModuleCommandRequest = SemanticOutputEnvelope<ModuleCommand>
ModuleResultOutput   = accepted target-result envelope defined in §6.9
SignalPublication    = SemanticOutputEnvelope<Signal>
TimerRequest         = SemanticOutputEnvelope<TimerIntent>
```

Для `ModuleResultOutput` путь результата между Ball всегда активирует полный материализованный дескриптор, и §6.9 фиксирует его как `commandSource.semanticHandle`; дополнительное поле `commandSource` не входит в общий конверт. `sourceOrdinal` — уникальная позиция с нуля внутри упорядоченного `Decision.outputs`: значения идут от `0..outputs.size-1`. Она материализуется и сохраняется, когда выход пересекает область принятого вызова, сохраняется, маршрутизируется, доставляется повторно или наблюдается независимо. Для одного немедленного локального выхода позиция списка доказывает тот же факт без хранимого поля. Если `semanticHandle` требуется, он полон и стабилен; отсутствие на активном пути недопустимо. Эти имена и значения конвертов каноничны; стирание представления не создаёт протокол-псевдоним.

### 6.13. Классы ошибок

Ошибки разделяются на:

```text
BusinessRejection       # intent is valid but prohibited by state/policy
ValidationFailure       # Interaction does not create an Intent
AdmissionFailure        # runtime capacity unavailable; Decision not accepted
ResourceFailure         # external operation failed with known outcome
Cancelled               # cancellation outcome is known
TimedOut                 # local wait/deadline elapsed; action outcome may differ
OutcomeUnknown          # action may have happened; reconciliation required
ProgrammingFault        # bug, invariant violation, trap, nontermination
```

Это каталог ошибок Core, а не обязательное объединение для каждого Ball. Конкретная граница открывает только достижимые варианты: например, `OutcomeUnknown` появляется только при неоднозначном исполнении, а `QueueFull`/варианты допуска — только при соответствующем пути вместимости. Опущенные недостижимые варианты не требуют заглушек.

PBA-04 классифицирует предикат по объявленному владельцу и входам, а не по тому, похож ли он случайно на проверку диапазона, размера или формы:

| Контракт предиката | Владелец и стадия вычисления | Допустимый смысловой результат |
|---|---|---|
| действительность представления или замкнутый инвариант протокола/типа, чья истинность независима от зафиксированного State, смыслового Context и бизнес-политики | Interaction до построения смыслового входа | `BoundaryResponse(ValidationFailure)`; `Intent`/`Query` не достигает Nucleus |
| бизнес-выбор или любое правило, чей результат зависит от зафиксированного State или смыслового Context, включая смысловой предел §13.1 | Nucleus после допустимого смыслового входа | изменение: `Rejected(BusinessRejection)` до принятия; допущенное чтение: один вариант принадлежащего получателю `ResultPayload` |
| фиксированное ограничение, намеренно переведённое из бизнес-политики в замкнутый инвариант протокола/типа | владелец протокола, затем Interaction для новой действующей идентичности протокола | `ValidationFailure`; перенос ограничения без требуемого изменения совместимости семантики протокола недопустим |

Например, нарушение объявленного предела типа коллекции — валидация. Прохождение типа, но превышение `maxItemsPerOrder` State/Context — бизнес-отказ Nucleus. Объявление `maxItemsPerOrder` фиксированным инвариантом протокола вместо этого — выбор версионированного контракта, а не второе толкование того же действующего протокола на другой стадии.

Смысл ошибки определяется стадией, на которой есть доказательства:

| Стадия | Допустимый носитель или результат | Влияние на статус/аспект | Запрещённая подмена |
|---|---|---|---|
| валидация до смыслового входа | `BoundaryResponse(ValidationFailure)`, включая `IdempotencyConflict` до Intent; на маршруте команды — только проверенный носитель до принятия | нет принятого Decision, ревизии, операции, выхода или бизнес-исхода; конфликт не меняет прежнюю принятую операцию | валидация — не `BusinessRejection`, Reply, принятый результат или `NotFound` |
| допуск до принятия | `BoundaryResponse(AdmissionFailure(reason))`; на маршруте команды — только проверенный носитель до принятия | нет принятого Decision/ревизии/выхода; аспект команды источника может стать `RejectedBeforeAcceptance + NotExpected` после получения проверенного носителя | сбой вместимости — не бизнес-отказ, принятие получателя или остановка доставки |
| `decide` получателя отказывает до принятия | `BoundaryResponse(DecisionRejected(BusinessRejection))`; на маршруте команды — только проверенный носитель до принятия | нет принятой ревизии/операции/выхода получателя; проекция носителя источника остаётся `RejectedBeforeAcceptance + NotExpected` | информационная причина не становится принятым `outcome = Rejected` |
| Decision получателя принимает бизнес-исход | принятый `ModuleResultOutput`, затем проверенный `ModuleResultPulse` | статус принятия/результата получателя сохраняется; источник может проецировать `Accepted` вместе с принадлежащим получателю исходом только после проверенного доказательства результата | отправка или более поздний сбой никогда не понижают результат до носителя или `BoundaryResponse` |
| Resource/Execution Gate действует после принятой работы | привязанный к происхождению `Fact` и, для командного получателя, более поздний принятый `ModuleResultOutput`; достижимые варианты результата/статуса включают `ResourceFailure`, `TimedOut` или `OutcomeUnknown` | прежнее принятие источника/получателя сохраняется; исход/статус уточняется только по объявленным доказательствам | без отката, носителя до принятия или выдуманного бизнес-отказа |
| политика доставки исчерпывается после принятого выхода | доверенное наблюдение `DispatchStopped` | только аспект доставки/статуса с ключом принятого выхода/маршрута результата | не бизнес-сбой, отмена, неисполнение получателем или стирание принятого результата |
| программная ошибка | политика fault runtime; до принятия ничего не публикует, после принятия сохраняет уже принятые факты по выбранному профилю | эксплуатационный сбой/карантин и только уже объявленные доказательства статуса | никогда не выдумывается как валидация, допуск, бизнес-результат, Reply или успех доставки |

Сбой более поздней стадии никогда не переписывает более раннее принятие или принятый результат. Каждая строка использует только замкнутые варианты, достижимые для конкретного протокола/профиля.

`ValidationFailure`, `AdmissionFailure` и `BusinessRejection` могут кодироваться в `BoundaryResponse`, но не становятся `SemanticOutput` и не получают идентичности фиксации.

Для корневого запроса любой смысловой ID, уже зарезервированный при отказе на одной из стадий до принятия, остаётся только кандидатом. Граница возвращает применимый `BoundaryResponse`, не открывает кандидата как авторитетный `OperationId` или ключ поиска статуса и не создаёт корневой источник операции/статуса, строку известного статуса, маркер хранения, авторитетный `SemanticHandle` или выход. Проверенный `CommandRejectedBeforeAcceptance` отличается лишь у уже принятого источника: он может уточнить соответствующий Step участника операции источника через объявленный `ControlPulse`, по-прежнему не создавая принятой операции получателя.

<!-- pkb-translation:term:start name="CommandRejectedBeforeAcceptance" -->
**CommandRejectedBeforeAcceptance** — проверенный механический носитель маршрута команды с `commandSource`, действующей идентичностью протокола, ровно одним `BoundaryResponse` до принятия и происхождением границы получателя. Это ни Reply, ни результат получателя; у источника он проецирует `RejectedBeforeAcceptance + NotExpected` и при неверном происхождении не создаёт доверенного Pulse. На ветви непринятого получателя в том же стеке нет принятого уровня получателя, а Decision источника, применяющий носитель, атомарно потребляет переданный слот альтернативного завершения уровня 1 в исходной причинной области.
<!-- pkb-translation:term:end -->

Для маршрута команды канонический механический носитель до принятия:

```text
CommandRejectedBeforeAcceptance {
    commandSource
    effectiveProtocolIdentity
    boundaryResponse:
        ValidationFailure
      | AdmissionFailure
      | DecisionRejected(BusinessRejection)
    targetBoundaryProvenance
}
```

- Носитель строится только после проверки `commandSource`, действующей идентичности протокола, замкнутого ответа и происхождения границы получателя.
- Это ни `ReplyOutput`, ни `ModuleResult`.
- Он не создаёт принятого Decision/ревизии/выхода получателя.
- Попытка получателя в том же стеке, создающая его, не потребляет принятого уровня получателя; §8.4 атомарно передаёт уже зарезервированный слот альтернативного завершения уровня 1 Decision носителя у источника.
- Он достигает состояния источника только через объявленную типизированную механическую проекцию `ControlPulse`.
- Источник не получает вложенный `BoundaryResponse` как самостоятельный результат.
- Поддельное, изменённое, отсутствующее, устаревшее или относящееся не к тому получателю происхождение не создаёт доверенного Pulse источника, аспекта отказа или компенсации.
- Классификация отказов контракта получателя — часть его действующей идентичности протокола.

Для `AdmissionFailure`:

- `AdmissionFailure` имеет конечное замкнутое объединение `reason` для конкретного профиля/привязки.
- Примеры Core — каталог применимости, а не разрешение открытой строки.
- Неизвестный дискриминатор или произвольная причина отклоняется до построения доверенного `AdmissionFailure` и не может быть приведена к другой стадии.
- Причина Core `CausalBudgetExceeded(scope, limit)` означает, что Decision не принят, потому что полный причинный бюджет не удалось зарезервировать.
- Это не бизнес-отказ, и она не разрешает сброс бюджета при повторе или возобновлении.

Для классификации тайм-аута:

- `TimedOut` не должен автоматически становиться `ResourceFailure`.
- После отправки тайм-аут часто означает `OutcomeUnknown`.

<a id="614-protocol-closure"></a>

### 6.14. Замкнутость протокола

<!-- pkb-translation:pba-source:start id="PBA-04" title="Closed Protocol" -->
**Исходное положение PBA-04 — Замкнутый протокол.**

- **Правило:**
  - Для заданной версии протокола набор вариантов должен быть статически известен и обработан полностью.
  - Каждый конкретный профиль/привязка также открывает одно конечное замкнутое объединение `AdmissionFailure.reason`.
  - Каждый конкретный профиль/привязка отклоняет неизвестные причины или причины в виде открытой строки.
  - Общие `Message`, `Any`, `Map<String, Any>` и поиск обработчиков по строкам не являются каноническим протоколом.
  - `ValidationFailure` до смысловой стадии покрывает только представление или объявленный инвариант замкнутого протокола/типа, чья истинность не зависит от зафиксированного State, смыслового Context и бизнес-политики.
  - Правило, принадлежащее владельцу как бизнес-выбор, или правило, чей результат зависит от зафиксированного State либо смыслового Context, вычисляется Nucleus: изменение возвращает `Rejected(BusinessRejection)` до принятия, а допущенное чтение выбирает один вариант принадлежащего получателю `ResultPayload`.
  - Фиксированное ограничение диапазона, размера или формы может обеспечивать Interaction, только когда владелец протокола намеренно объявляет его версионированным инвариантом замкнутого типа. Перенос ограничения между этим инвариантом и политикой Nucleus меняет семантику протокола и следует правилам совместимости §10.11.
- **Применимость:** `A`: каждая используемая категория протокола; `P`: допуск может отказать.
- **Владелец объявления:** владелец протокола/профиля/привязки владеет замкнутыми вариантами/причинами.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** полнота типа/схемы, совместимость и отклонение неизвестных/открытых причин.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** точная ссылка на протокол может заменить копию списка; отсутствующая категория/путь допуска пусты и не имеют объединения причин.
- **Основной путь проверки:** `§17.1`

<a id="definition-source-records-for-6"></a>

### Исходные записи определений для §6

Эти помеченные определения — единственные исходные данные глоссария для терминов, которыми владеет этот раздел.

<!-- pkb-translation:term:start name="AdmissionFailure" -->
**AdmissionFailure** — `BoundaryResponse` до принятия, чья причина принадлежит конечному замкнутому объединению конкретного профиля/привязки. Он не создаёт принятого состояния, ревизии, операции, дескриптора или выхода; неизвестный дискриминатор/открытая строка отклоняется до доверенного конструирования и не может стать бизнес-отказом или статусом более поздней стадии.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="BusinessRejection" -->
**BusinessRejection** — ожидаемый доменный результат `Rejected(...)` изменяющего решения Nucleus до принятия, без изменения состояния или fault runtime. Допущенное чистое чтение вместо этого возвращает принадлежащий получателю смысловой исход внутри `ResultPayload` и не использует этот носитель.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="Decision" -->
**Decision** — ограниченный результат изменения Nucleus, зависящий от режима и выбранный профилем состояния: `SnapshotDecision` со следующим State или `EventDecision` с событиями/NoDomainChange; каждый несёт полный упорядоченный пакет `SemanticOutput` и принимается атомарно через свой точный фрейм.
<!-- pkb-translation:term:end -->














<!-- pkb-translation:term:start name="ReadResult" -->
**ReadResult** — успешно вычисленная незафиксированная обёртка Query, используемая при условии чтения с отметкой; содержит полезную нагрузку получателя и `ConsistencyStamp` с минимальным набором полей. Полезная нагрузка полна для каждого достижимого смыслового исхода после допуска, включая объявленный отказ/сокрытие полей/нераскрытие сведений, если они есть; getter в том же стеке может вернуть её прямо, и ни одна форма не получает идентичности фиксации/смысловой идентичности.
<!-- pkb-translation:term:end -->
