## 12. Профили исполнения

Профили — независимые измерения. Одна перегруженная метка вроде `DurableSecureFast` не используется.

```text
execution:   Inline | BoundedConcurrent
state:       Transient | SnapshotOutbox | EventJournal
isolation:   InProcess | Isolated
security:    Standard | Hardened
composition: Static
```

`Secure` как сильное заявление о защите от противника зарезервировано для отдельной спецификации изоляции и безопасности.

Проект или привязка к среде исполнения может один раз выбрать точный профиль по умолчанию. Ball, который его использует, не дублирует строку профиля, а записывает только явное разрешённое переопределение. Действующий профиль — статически разрешённый выбор проекта плюс это отличие. Выбор более сильного профиля активирует его механизмы и тесты; простое перечисление всех профилей этого не делает.

<a id="121-semantics-common-to-all-profiles"></a>

### 12.1. Семантика, общая для всех профилей

Каждый профиль сохраняет безусловно применимую семантику:

- три логические зоны;
- явное владение;
- чистое ограниченное решение;
- отсутствие повторного входа в переход;
- атомарное принятие Decision;
- отсутствие неявных полномочий;
- конечные пределы каждого присутствующего переменного измерения.

Если есть условие применения выхода, отделённой работы, дубликатов, повторов, отмены, неоднозначности, конкурентности, долговечности, изоляции или безопасности, выбранный профиль также сохраняет соответствующий контракт §8–§11. Имя профиля не требует механизмов для отсутствующего пути и не может отменить механизмы для присутствующего.

### 12.2. Inline

```text
Interaction -> decide -> atomically publish AcceptedSnapshotDecisionFrame | AcceptedEventCommit -> dispatch retained outputs
```

Свойства:

- в каждый момент выполняется один изменяющий переход;
- обязательного почтового ящика нет;
- обязательных параллельных эффектов нет;
- синхронизация, очередь, корутина, сериализация или переключение потока не навязываются;
- синхронное завершение обрабатывается на следующей итерации после принятия;
- допустим фиксированный буфер выходов или буфер, принадлежащий вызывающей стороне.

Подходит для мобильных, настольных и встраиваемых приложений, локального серверного сценария и привязки для модульных тестов.

### 12.3. BoundedConcurrent

```text
bounded mailbox
  -> single-writer decision loop
  -> bounded effect/command workers
```

Требуется:

- конечная вместимость почтового ящика;
- типизированный `BoundaryResponse(AdmissionFailure(reason))` для обратного давления/допуска до принятия;
- конечное число обработчиков, если они есть;
- политика справедливого обслуживания, если управляющие входы в отдельных очередях могут голодать;
- обработка Fact/Result вне порядка, если завершения могут менять порядок;
- тесты гонок отмены/крайнего срока, если эти пути есть;
- отсутствие конкурентного изменения одного экземпляра состояния.

<a id="124-transient-state"></a>

### 12.4. Состояние Transient

- состояние живёт только в памяти процесса;
- при сбое можно потерять состояние, ответы активным вызовам и незавершённые операции;
- источник не заявляет долговечную доставку;
- после сбоя исход внешнего побочного эффекта может быть неизвестен;
- восстановление использует повторную инициализацию или синхронизацию по контракту приложения.

### 12.5. SnapshotOutbox

Безусловно присутствующий контракт долговечного состояния записывает снимок состояния и ревизию фиксации в одной авторитетной транзакции и восстанавливается из зафиксированного снимка. При отсутствии выходов часть outbox пуста и может отсутствовать в представлении.

Дополнительные положения возникают независимо, по своим условиям применения:

- если Decision имеет долговечные выходы источника, та же транзакция записывает полный пакет выходов, а отправка начинается только после фиксации;
- присутствующая долговечная запись источника остаётся `Pending`, только пока объявленная политика доставки разрешает работу, и хранится до конечного горизонта этой политики;
- если есть повторы, число попыток конечно в рамках действующего бюджета времени/попыток, и они сохраняют тот же `OutputId`;
- дедупликация у получателя или исполнителя обязательна только для необратимого исполнения, допускающего дубликаты;
- если политика повторной/сохраняемой доставки может исчерпаться, источник атомарно записывает `DispatchStopped` с доступной причиной/свидетельствами и не отбрасывает принятый выход молча;
- записи входа/inbox или идемпотентности и горизонт их хранения существуют только при возможности повторного принятия/доставки;
- ожидаемая ревизия или обеспеченная хранилищем эпоха владения проверяется только при конкурентности или переносимом владении;
- неоднозначная фиксация необратимого входа в хранилище не разрешает слепое повторное вычисление;
- статус операции существует только при условии §9.11 и содержит только достижимые для неё аспекты.

Безусловная гарантия Core заканчивается долговечным принятием состояния. Для присутствующих выходов источника или статуса она дополнительно включает лишь семантику хранения и завершения, разрешённую для этих путей. Она не обещает получение адресатом, принятие адресатом или внешнее исполнение при любой последовательности сбоев.

Конкретная привязка может заявлять `at-least-once` только для присутствующего пути выхода, относительно явно названной точки доставки и с записанными допущениями о прогрессе/сбоях, горизонтом повторов и хранения и политикой завершения. Без такого контракта присутствующий outbox даёт только объявленную ограниченную семантику отправки с возможными дубликатами, а не безусловную доставку в будущем или ровно однократное внешнее исполнение.

### 12.6. EventJournal

- авторитетное изменение состоит из упорядоченных доменных событий;
- каждый результат Accepted записывает `AcceptedEventCommit`, включая `NoDomainChange` с пустым пакетом событий;
- конверт фиксации, пакет событий и маркер принятого входа принимаются атомарно; метаданные идемпотентности, изменения статуса и записи выходов источника входят в транзакцию только при наличии собственных независимых условий применения;
- состояние восстанавливается через `evolve`;
- присутствующие долговечные выходы не создаются заново запуском текущего кода перехода;
- точное воспроизведение требует закреплённых артефактов и контекста и относится к отдельной спецификации расширения.

### 12.7. InProcess

- границы логические и обеспечиваются дисциплиной времени компиляции или исполнения;
- допустимы прямые вызовы и общий распределитель памяти, но каждый синхронный вызов между Ball до передачи управления/уступки исполнения — это `Direct Control Dependency`, и граф прямого управления остаётся ацикличным;
- локализация сбоев и изоляция учётных данных от враждебного кода не заявляются;
- минимум привилегий требует внешних учётных данных и адаптеров с ограниченной областью действия, а не только модификаторов видимости.

### 12.8. Isolated

- граница процесса/песочницы;
- IPC не становится асинхронным автоматически: синхронный IPC-вызов между Ball до передачи управления/уступки исполнения остаётся `Direct Control Dependency` и подчиняется требованию ацикличного графа;
- версионированный аутентифицированный IPC; аутентификация другой стороны не заменяет проверку издателя авторизации, если есть пути акторов/разрешений;
- заданные профилем подлинность и целостность присутствующего контекста актора и разрешений по §11.3;
- ограниченные размер/глубина фрейма;
- отсутствие общей изменяемой бизнес-памяти;
- отдельные/ограниченные учётные данные для присутствующих путей внешних ресурсов;
- пределы CPU/памяти/реального времени для изолированного исполнения; доступ к сети/файлам запрещён конструкцией или получает собственные конечные пределы, только если предоставлен;
- политика сбоя/перезапуска/карантина;
- защита от воспроизведения/идемпотентность, если класс операции допускает дубликаты или повторы.

### 12.9. Hardened

`Hardened` усиливает каждый присутствующий путь безопасности в выбранном профиле исполнения/изоляции; он не создаёт неиспользуемые пути акторов, ресурсов, интерпретаторов, секретов или разрешений. Применяйте только пункты, чьи условия выполнены:

- контекст актора от одобренного издателя или фиксированное доверенное доказательство издателя/области в том же стеке, если личность актора влияет на Decision либо авторизацию/выбор результата Query или чтения статуса;
- возможности с минимумом привилегий для присутствующих внешних ресурсов;
- безопасные приёмники на присутствующих границах интерпретаторов;
- обращение с секретами для присутствующих потоков секретов;
- явные разрешения для привилегированного доказательства, пересекающего границу полномочий;
- ограниченные меры против злоупотребления ресурсами;
- тесты безопасности для активных путей и доказательства заявленных допущений об угрозах.

Это не означает абсолютную безопасность.

<a id="1210-profile-selection"></a>

### 12.10. Выбор профиля

| Сценарий | Рекомендуемый начальный профиль |
|---|---|
| Локальный автомат состояния UI | `Inline + Transient + InProcess + Standard` |
| Асинхронная функция мобильного приложения | `BoundedConcurrent + Transient/SnapshotOutbox + InProcess` |
| Долговечный серверный агрегат | `BoundedConcurrent + SnapshotOutbox + InProcess + Hardened` |
| Враждебный плагин/парсер | `BoundedConcurrent + Transient/SnapshotOutbox + Isolated + Hardened` |
| Распределённый необратимый эффект | Долговечный источник + отдельный контракт исполнителя/провайдера; одного профиля Core недостаточно |

<a id="definition-source-records-for-12"></a>

### Исходные записи определений для §12

Эти помеченные определения — единственные исходные данные глоссария для терминов, которыми владеет этот раздел.


<!-- pkb-translation:term:start name="EventJournal" -->
**EventJournal** — профиль долговечности, в котором авторитетное состояние восстанавливается из зафиксированных доменных событий, а каждый принятый вход, включая `NoDomainChange`, получает долговечный `AcceptedEventCommit`; записи идемпотентности, статуса и выходов источника входят в эту транзакцию только при наличии соответствующих путей.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="SnapshotOutbox" -->
**SnapshotOutbox** — профиль долговечности, в котором снимок состояния принимается долговечно, а все присутствующие долговечные выходы источника входят в ту же атомарную транзакцию; повторы, обработка дубликатов, конечный `DispatchStopped` и аспекты статуса/хранения появляются только при наличии их путей доставки; доставка в будущем не гарантируется.

<a id="13-limits-budgets-and-performance"></a>

## 13. Пределы, бюджеты и производительность

<a id="131-three-classes-of-limits"></a>

### 13.1. Три класса пределов

<a id="semantic-limits"></a>

#### Смысловые пределы

Влияют на бизнес-решение или решение оркестрации:

```text
maxItemsPerOrder
maxWorkflowSteps
maxCommands
maxRetriesByPolicy
businessDeadline
```

Они принадлежат состоянию или контексту и видны `Nucleus`.

<a id="runtime-caps"></a>

#### Ограничения runtime

Ограничивают ресурсы реализации на путях, где эти ресурсы есть:

```text
CPU
wall time
memory
mailbox
IPC bytes
storage bytes
parallel workers
delivery attempts per output
outbox and operation-status retention
```

Их обеспечивает runtime; они могут вызвать отказ допуска или fault, но не переписывают бизнес-решение. Проект/привязка может один раз объявить и проверить ограничение; Ball повторяет его, только если переопределяет общее значение или нуждается в другой смысловой реакции на сбой.

`maxCumulativeFanout` — ограничение причинной композиции, а не бизнес-выбор: §10.9 может доказать его статически по замкнутому графу выходов/маршрутов, либо привязка обеспечивает то же число ветвей через существующее причинное резервирование до принятия. Во втором случае это состояние допуска runtime: оно не может входить в `DecisionContext` или сбрасываться асинхронным обработчиком/передачей управления.

`maxInputBytes`, `maxStateBytes` и `maxOutputBytesPerDecision` — ограничения ресурсов до принятия, а не бизнес-выбор. Раздел 8.3 фиксирует каждое активное числовое измерение через неизменяемый `BoundedByteMeasure`, принадлежащий привязке: точную стадию границы и включённые метаданные входа/Context, полное представление кандидата следующего State или полное представление упорядоченной последовательности выходов. Статически ограниченные тип и представление не требуют счётчика байтов во время исполнения; иначе граница или принимающий компонент применяет выбранную меру на точной стадии и не может подменить её несопоставимым сетевым представлением, представлением в куче/хранилище, перенести значение в `DecisionContext` или обрезать значение.

<a id="economicshared-quotas"></a>

#### Экономические/общие квоты

Деньги, вызовы провайдера, кредиты API и общий баланс арендатора требуют авторитетного реестра или резервирования. Core требует только явного контракта и запрещает копировать весь родительский баланс в параллельные ветви. Полный протокол распределённого бюджета — расширение.

<a id="132-backpressure"></a>

### 13.2. Обратное давление

Если допуск может быть отклонён из-за насыщения ограниченного ресурса runtime или общего ресурса, перегрузка возвращается как типизированный исход. Ниже — пример каталога применимости Core, а не открытое или обязательное конкретное объединение:

```text
TemporarilyUnavailable(retryAfter?)
CapacityExceeded(scope)
QueueFull
StoragePressure
```

Каждый конкретный профиль/привязка с возможным отказом допуска объявляет одно конечное замкнутое объединение `AdmissionFailure.reason`, содержащее только достижимые случаи. Декодирование, конструирование и проверки полноты отклоняют неизвестный дискриминатор или произвольную/открытую строку; они не превращают её в `TemporarilyUnavailable`, `BusinessRejection` или другую стадию. Прямой путь Inline без возможного отказа допуска не объявляет пустое объединение причин.

До принятия Decision такая перегрузка возвращается как `BoundaryResponse(AdmissionFailure(<typed overload outcome>))`. Она не создаёт принятого состояния, `CommitRevision`, `SemanticHandle` или `SemanticOutput`. Наблюдение доставки после принятия не превращается задним числом в отказ допуска.

Отказ допуска не выдаётся за постоянный бизнес-отказ. Неограниченная очередь запрещена. Прямой путь Inline без очереди или возможного отказа допуска не нуждается в типе обратного давления или пустой политике.

`DispatchStopped` после уже принятого долговечного выхода — не отказ допуска и не бизнес-отказ. Это конечное наблюдение доставки: источник хранит выход и статус по объявленной политике хранения и передаёт следующее решение политике сверки или ручной обработки.

### 13.3. Zero Mandatory Runtime Tax

<!-- pkb-translation:pba-source:start id="PBA-40" title="Zero Mandatory Runtime Tax" -->
**Исходное положение PBA-40 — Отсутствие обязательных накладных расходов runtime.**

- **Правило:**
  Семантика Core не требует:

  ```text
  runtime handler lookup
  reflection discovery
  in-process serialization
  mandatory queue
  mandatory thread hop
  object message hierarchy
  service locator
  ```

  Только конкретная привязка Inline с замером на точной цепочке инструментов может заявлять `maxStructuralAllocationsPerDecision = 0`.

  Различайте:

  - **структурное выделение памяти** — вызвано только архитектурным механизмом runtime;
  - **выделение памяти под полезные данные** — для нужных доменных данных или результата;
  - **копирование полезных данных** — перенос полезной нагрузки через границу.
- **Применимость:** `A`: проектирование Core; проверка реализации при выборе Inline.
- **Владелец объявления:** Core/профиль и владелец привязки Inline.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** проверка сборки; замер нужен только для заявления.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** одна привязка обслуживает много Ball; отдельная обёртка для каждого Ball не нужна.
- **Основной путь проверки:** `§17.5`

<a id="134-claim-contract"></a>

### 13.4. Контракт заявления

<!-- pkb-translation:pba-source:start id="PBA-41" title="Measured Claim" -->
**Исходное положение PBA-41 — Подтверждённое измерением заявление.**

- **Правило:** заявление о производительности, долговечности, доставке, восстановлении, получении, принятии, однократности, RPO, RTO, изоляции, безопасности или соответствии называет точную границу гарантии, привязку и область, механизм, допущения, хранение, доказательства и то, что не гарантируется; без полных доказательств в этой области заявление не делается. Заявление, сравнивающее значения `maxTransitionSteps` между привязками, дополнительно доказывает равенство идентификатора/версии Decision Work Meter, версии артефакта перехода и определения единицы; иначе эти значения намеренно считаются несопоставимыми.
- **Применимость:** `C`: делается любое именованное заявление о производительности, долговечности, доставке, восстановлении, получении, принятии, однократности, RPO, RTO, изоляции, безопасности или соответствии; сравнение шагов перехода между привязками дополнительно требует одинаковой идентичности счётчика/артефакта/единицы.
- **Владелец объявления:** заявитель называет границу гарантии, точную привязку/область, механизм, допущения, хранение, доказательства/отсутствующие гарантии и идентичность сравниваемых счётчиков/артефактов/единиц.
- **Область действия:** точно названные граница, привязка, среда, нагрузка, горизонт хранения и аудитория заявления.
- **Владелец контроля / доказательств:** заявитель и владелец доказательств замеров/безопасности/сбоев/восстановления/доставки/соответствия; при сравнении значений — владелец проверки равенства идентичности счётчиков.
- **Разрешение, сбой и соответствие:** отсутствие полей/доказательств заявления или выход за их область отменяет заявление, а не создаёт подразумеваемую гарантию; неподтверждённое усиление означает несоответствие.
- **Повторное использование и поведение без условия применения:** повторное использование допустимо только при одинаковом дайджесте/области; разные счётчики остаются несопоставимыми; без доказательств заявление опускается.
- **Основной путь проверки:** `§17.9`

<!-- pkb-translation:term:start name="Claim Record" -->
**Claim Record** — заявление о гарантии производительности, долговечности, доставки, восстановления, получения, принятия, однократности, RPO, RTO, изоляции, безопасности или соответствия для конкретной привязки вместе с точно названными границей, областью, механизмом, допущениями, хранением, доказательствами и явно отсутствующими гарантиями. Сами по себе долговечность источника или сохранённая незавершённая работа не доказывают более сильный последующий исход. Если заявление не делается, пакет доказательств не требуется.
<!-- pkb-translation:term:end -->

Ball, проект или привязка создаёт Claim Record только для заявления, которое действительно делает:

```text
ClaimRecord {
    exactNamedBoundary
    exactBindingAndScope
    mechanism
    assumptions
    retention
    evidence
    explicitNonGuarantees
}
```

Его метрики и доказательства могут включать:

```text
transition p50/p95/p99
structural allocations
payload copies
state bytes
mailbox occupancy
outbox age
max effects/commands
external response bytes
CPU/wall limits
binary contribution
```

Абсолютное число без нагрузки, оборудования, компилятора и runtime, распределения полезных данных и метода измерения не является обоснованным заявлением. Без доказательств заявление запрещено; обычная работа над реализацией не требует пустого пакета доказательств.

<a id="135-design-time-tax"></a>

### 13.5. Издержки проектирования

Архитектурные издержки не ограничены runtime:

```text
manifest size
number of artifacts
routes per operation
manual review hours
waiver count
schema/evidence maintenance
flow-to-feature ratio
```

Простой Ball не должен платить формальностями за неиспользуемые распределённые гарантии.

Издержки первого использования человеком — часть этой цены: время до первого верного изменения, обращения к справочникам, помощь экспертов, правки не того владельца и переделки. Сравнивайте одинаковое поведение и нужные гарантии с уже применяемым в проекте компетентным подходом. Считайте настройку общей привязки и поддержку доказательств отдельно от работы над каждой функцией, затем учитывайте обе части при решении о внедрении; перенос затрат в общий компонент или сгенерированный файл их не убирает. Само по себе меньшее число файлов не доказывает ни простоту поддержки, ни корректность.

Для пробного внедрения проект выбирает нужную метрику, нагрузку, метод измерения, базовую линию и порог решения «продолжить/перестроить/остановить». Возможные метрики: размер состояния, пиковое число операций на ключ, стоимость перехода, конкуренция за ресурсы, область влияния изменения, стоимость восстановления и перечисленные выше издержки проектирования. Core не задаёт универсального числа. Измерение в пилоте становится заявлением о производительности, только если проект делает это заявление по §13.4.

Общие механизмы, политики и доказательства проверяются один раз в их точной области; каждый покрываемый Ball ссылается на них. Локальное изменение записывает только новое условие защитного ограничения, смысловое отличие, переопределение или доказательство, утратившее силу. Копирование неизменной политики проекта или повторение `N/A` для отсутствующих путей само по себе создаёт лишние издержки проектирования.
