## 3. Каноническая модель

<a id="31-ball-type-and-instance"></a>

### 3.1. Тип и экземпляр Ball

`BallType` определяет протокол и семантику решений. `BallInstance` — конкретная область состояния и полномочий единственного писателя.

```text
BallInstanceId {
    namespace
    ballType
    stateKey
}
```

- `namespace` предотвращает коллизии между развёртываниями, арендаторами или областями;
- `ballType` определяет семейство протокола;
- `stateKey` задаёт локальную границу согласованности и раздела.

Смысловая область существует всегда. Запись `BallInstanceId` материализуется, только когда экземпляров несколько или идентичность пересекает границу хранения, маршрута, отделённой доставки, статуса, передачи владения или наблюдаемости. Для локального singleton Ball идентичность может доказывать охватывающая типизированная область; сериализованный объект `namespace`, `ballType` или `stateKey: singleton` не требуется.

<a id="32-state-revision"></a>

### 3.2. Ревизия состояния

Принятые изменения полностью упорядочены внутри одного экземпляра. Материализованный монотонный `CommitRevision` требуется, когда этот порядок используется для оптимистической конкурентности, асинхронного упорядочивания, долговечного принятия, чтения/статуса с отметкой, переносимого владения, воспроизведения или внешне наблюдаемой идентичности снимка. Последовательная локальная привязка без этих путей может доказать порядок областью вызовов единственного писателя и не добавлять видимое домену поле ревизии.

```text
CommitRevision: UInt64 или более широкое монотонное значение
```

Если ревизия есть, она растёт даже тогда, когда байты смыслового состояния не меняются, но вход принят, состояние операции обновлено или результат доставки либо отмены записан. Ревизия не является отметкой реального времени.

<a id="33-canonical-mutation-and-read-forms"></a>

### 3.3. Канонические формы изменения и чтения

Выбранный профиль состояния фиксирует ровно одну из следующих функций изменения и типов результата. Они не образуют объединение runtime, и привязка не обязана реализовывать обе принятые ветви.

Форма снимка, выбранная `Transient` или `SnapshotOutbox`:

```text
decide(
    state: State,
    pulse: Pulse,
    context: DecisionContext
) -> SnapshotDecisionResult<State>

SnapshotDecisionResult<State> =
    Accepted(SnapshotDecision<State>)
  | Rejected(BusinessRejection)

SnapshotDecision<State> {
    nextState
    outputs: BoundedSequence<SemanticOutput>
}
```

Форма событий, выбранная `EventJournal`:

```text
decide(
    state: State,
    pulse: Pulse,
    context: DecisionContext
) -> EventDecisionResult

EventDecisionResult =
    Accepted(EventDecision)
  | Rejected(BusinessRejection)

EventDecision =
    EventMutation {
        events: NonEmptySequence<DomainEvent>
        outputs: BoundedSequence<SemanticOutput>
    }
  | NoDomainChange {
        outputs: BoundedSequence<SemanticOutput>
    }
```

Когда замкнутый набор выходов пуст, `outputs` — статически пустая последовательность, представление которой можно стереть. Привязка снимка может реализовать принятое значение как `SnapshotDecision(nextState)` без выделения коллекции или конверта. EventJournal никогда не возвращает независимый `nextState`; §8.9 определяет его точную принятую фиксацию и контракт `evolve`.

Это краткое каноническое сравнение. Подробные разделы добавляют только поля и поведение, активируемые названным условием; они не заменяют строку другой алгеброй операций.

| Форма операции | Смысловой владелец и явный вход | Возвращаемое смысловое значение | Принятие и ревизия | Допустимая стадия отказа или сбоя |
|---|---|---|---|---|
| Изменение снимка | Nucleus; `State + Pulse + DecisionContext` | `Accepted(SnapshotDecision { nextState, outputs }) \| Rejected(BusinessRejection)` | Runtime/принимающий компонент атомарно публикует принятый фрейм снимка; `CommitRevision` следует §3.2 | валидация представления/типа или допуск до `decide`; бизнес-отказ в `decide`; объявленные пути fault после принятия |
| Изменение EventJournal | Nucleus; `State + Pulse + DecisionContext` | `Accepted(EventMutation { events, outputs } \| NoDomainChange { outputs }) \| Rejected(BusinessRejection)` | Runtime/принимающий компонент атомарно записывает `AcceptedEventCommit`; каждый принятый результат продвигает `CommitRevision`; State восстанавливается через `evolve` | те же классы стадий, что у изменения снимка; без искусственного `nextState` или события при отказе |
| Query/чтение | Policy Gate Nucleus/чтения; зафиксированный снимок + `Query + ReadContext` | успешное вычисление возвращает единственный принадлежащий получателю `ResultPayload`, обёрнутый в `ReadResult`, когда действует условие чтения с отметкой; эта полезная нагрузка замыкает каждый достижимый разрешённый, запрещённый, частично скрытый или намеренно не раскрывающий сведения смысловой исход | нет принятия Decision, маркера принятия, новой ревизии, дескриптора или смыслового выхода; отметка сообщает существующую ревизию снимка | валидация/допуск могут отказать до `read`; после допуска принадлежащая получателю полезная нагрузка несёт смысловой результат, никогда не `BusinessRejection`, исключение или придуманный `BoundaryResponse` |

Программная ошибка, сбой процесса, незавершение или нарушенный внутренний инвариант — не `BusinessRejection`. Это обрабатывается политикой fault runtime и не создаёт частичного `Decision`.

<a id="34-cause-decision-and-consequence"></a>

### 3.4. Причина, решение и последствие

```text
Cause:
    Intent | Fact | ModuleCommandPulse | ModuleResultPulse
  | ObservedSignal | ControlPulse

Decision:
    SnapshotDecision(nextState + семантические выходы)
  | EventMutation(непустые события + семантические выходы)
  | NoDomainChange(семантические выходы)

Consequence:
    ProjectionOutput | ReplyOutput | EffectRequest
  | ModuleCommandRequest | ModuleResultOutput
  | SignalPublication | TimerRequest
```

`Projection`, `Reply`, `Effect`, `ModuleCommand`, `ModuleResult`, `Signal` и `TimerIntent` — типы смысловых полезных нагрузок. `ModuleCommand` и `ModuleResult` принадлежат контракту получателя. `Nucleus` возвращает полезные нагрузки только как смысловое семейство выходов из §6.12; немедленным типизированным вызовам не нужен материализованный конверт. Механические записи доставки, транспортные попытки, строки хранилища и метаданные трассировки не являются бизнес-выходами `Nucleus`.

<a id="35-semantic-and-mechanical-identity"></a>

### 3.5. Смысловая и механическая идентичность

Идентификаторы делятся на два класса.

**Смысловые ID** принадлежат домену и могут храниться в состоянии:

<!-- pkb-translation:pba-source:start id="PBA-16" title="Trusted Identifier Allocation" -->
**Исходное положение PBA-16 — Доверенное выделение идентификаторов.**

- **Правило:**
  - Смысловые ID должны быть известны до `decide`.
  - `Nucleus` НЕ ДОЛЖЕН читать неявный генератор случайных значений.
  - Смысловые ID приходят как:
    - проверенный ID клиента, если контракт его разрешает;
    - детерминированное значение, выведенное из существующих смысловых данных;
    - доверенный зарезервированный ID из `DecisionContext`;
    - ID, зарезервированный входной границей или runtime до вычисления.
  - Зарезервированный `OperationId` — лишь кандидат смыслового значения, пока корневая операция не принята.
  - Если корневая валидация, допуск или `decide` отказывают до принятия, этот кандидат не создаёт запись принятой операции, авторитетный `SemanticHandle`, выход, источник статуса или маркер хранения.
  - Корневой `BoundaryResponse` не представляет кандидата как авторитетный `OperationId` или ключ поиска статуса.
  - Механические ID принадлежат runtime.
  - Механические ID могут появляться только после принятия или фиксации и не должны требоваться для доменного решения.

  **Примеры и механика:**

  Примеры смысловых ID:

  ```text
  OperationId
  OrderId
  PaymentId
  SearchSessionId
  ```

  Примеры механических ID:

  ```text
  CommitId
  OutputId
  AttemptId
  StorageTransactionId
  ```
- **Применимость:** `P`: Decision нужен вновь выделенный или проверенный на доверие смысловой ID.
- **Владелец объявления:** Ball и издатель входа/контекста.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** распределитель/валидатор, тесты чистоты/коллизий и идентичности при корневом резервировании/отказе/принятии.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** можно сослаться на политику издателя; без нового ID резервирование опускается.
- **Основной путь проверки:** `§17.4`
<!-- pkb-translation:pba-source:end -->
<!-- pkb-translation:term:start name="SemanticHandle" -->
**SemanticHandle** — стабильная видимая домену идентичность запланированной работы, которая может пережить вызов, повториться, сменить порядок, быть независимо отменена, сверена, восстановлена или наблюдаема. Временное хранение в текущем вызове и само пересечение границы Ball не требуют дескриптора; немедленный выход использует принятую позицию последовательности и область типизированного вызова.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:pba-source:start id="PBA-15" title="Semantic Handle" -->
**Исходное положение PBA-15 — Смысловой дескриптор.**

- **Правило:**
  Смысловое состояние ссылается на запланированную работу через стабильный `SemanticHandle`, когда работа хранится за пределами текущего вызова, может завершиться позднее, повториться или сменить порядок, быть независимо отменена или сверена, пережить восстановление либо наблюдаться независимо, в том числе через статус операции:

  ```text
  SemanticHandle {
      operationId
      outputKind
      localOrdinalOrName
  }
  ```

  Runtime может хранить сопоставление для такой отделённой работы:

  ```text
  SemanticHandle -> OutputId
  ```

  но он не переписывает бизнес-состояние лишь для материализации транспортного ID. Немедленный вызов в одной сборке может использовать типизированного получателя и область вызова как идентичность и происхождение команды. Само пересечение границы Ball не требует материализованного дескриптора, токена источника, токена результата или идентификатора протокола. Хранение промежуточного значения только в текущем вызове не активирует стабильную идентичность. Позиция принятого выхода и связь вызова с возвратом определяют эту работу без `OperationId`, `SemanticHandle` или объекта-обёртки.

  Правило стабильной смысловой идентичности отделённой или адресуемой запланированной работы — контракт `SemanticHandle` в предыдущем абзаце; немедленная работа в области принятого вызова по-прежнему определяется позицией в принятом фрейме.
- **Применимость:** `P`: работа переживает текущий вызов, может завершиться позднее, повториться или сменить порядок, быть независимо отменена, сверена, восстановлена или наблюдаема.
- **Владелец объявления:** владелец состояния/протокола Ball.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** тесты сопоставления идентичности Nucleus/runtime.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** выделение может быть общим; для немедленной работы в области вызова артефакты операции/дескриптора опускаются.
- **Основной путь проверки:** `§17.1`

<a id="36-identity-hierarchy"></a>

### 3.6. Иерархия идентичности

Следующие идентификаторы не взаимозаменяемы:

| Идентичность | Что определяет | Когда появляется | Повторное использование |
|---|---|---|---|
| `RequestId` | Одну независимо коррелируемую транспортную попытку или попытку запроса | Когда попытка пересекает или переживает область вызова | Новый для каждой новой попытки |
| `IdempotencyKey` | Повторное принятие одного логического изменения | До принятия на входе | Сохраняется при повторах клиента |
| `OperationId` | Принятую бизнес-операцию с независимо наблюдаемым жизненным циклом | Резервируется до `decide`, получает полномочия после принятия | Стабилен в течение этого цикла |
| `SemanticHandle` | Отделённую адресуемую запланированную работу или шаг операции | В решении Nucleus, когда действует условие отделённой работы | Стабилен при повторах доставки |
| `CommitId` | Принятую запись фиксации runtime | При принятии или фиксации | Стабилен для этой записи фиксации |
| `OutputId` | Зафиксированную запись выхода runtime | При принятии или фиксации | Стабилен при повторной доставке |
| `AttemptId` | Одну попытку отправки или исполнения | Перед конкретной попыткой | Новый для каждой попытки |
| `StorageTransactionId` | Зафиксированную транзакцию хранилища, обеспечившую принятие | После успешной фиксации хранилища | Уникален для этой транзакции |

Резервирование кандидата `OperationId` даёт детерминированную идентичность возможному Decision; оно не создаёт операцию. Если корневая валидация, допуск или `decide` отказывают до принятия, кандидат никогда не становится авторитетным и не создаёт `SemanticHandle`, строку известного статуса операции, маркер хранения, выход или цепочку происхождения принятой операции. Граница возвращает только типизированный ответ по §6.13.

Типичная цепочка происхождения для отделённой операции с повторами:

```text
RequestId attempt-1 ─┐
RequestId attempt-2 ─┼─ same IdempotencyKey
                     └─ OperationId
                          └─ SemanticHandle
                               └─ OutputId
                                    ├─ AttemptId 1
                                    └─ AttemptId 2
```

Новый `RequestId` нельзя использовать для обхода идемпотентности, а новый `OperationId` нельзя создавать лишь из-за повтора транспортной попытки. Путь без повторов, отделённой работы, долговечной записи, статуса или сопоставления за пределами текущего вызова не материализует всю эту цепочку.

### Исходные записи определений для §3

Эти помеченные определения — единственные исходные данные глоссария для терминов, которыми владеет этот раздел.

<!-- pkb-translation:term:start name="AttemptId" -->
**AttemptId** — механическая идентичность одной попытки доставки/исполнения; меняется при повторе и не заменяет `OperationId`, `SemanticHandle` или `OutputId`.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="CommitId" -->
**CommitId** — механическая идентичность принятой записи фиксации runtime; не заменяет `CommitRevision` и не используется как смысловая идентичность до фиксации.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="CommitRevision" -->
**CommitRevision** — материализованный монотонный номер принятого изменяющего входа/Decision внутри BallInstance, когда порядок наблюдается через конкурентность, хранение, асинхронность, чтение/статус, владение, воспроизведение или другую границу; последовательная локальная область вызова может доказать порядок без его хранения.
<!-- pkb-translation:term:end -->




<!-- pkb-translation:term:start name="OperationId" -->
**OperationId** — стабильная идентичность принятой логической операции с отделённым или независимо наблюдаемым жизненным циклом; не равна RequestId или попытке доставки и отсутствует, когда достаточно области вызова. Резервирование до принятия — лишь значение-кандидат; без принятого корневого фрейма оно не создаёт операции или полномочий статуса.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="OutputId" -->
**OutputId** — идентичность зафиксированной записи выхода в runtime/хранилище. Ей не обязательно быть частью доменного состояния.
<!-- pkb-translation:term:end -->



<!-- pkb-translation:term:start name="RequestId" -->
**RequestId** — материализованная идентичность одной независимо коррелируемой транспортной попытки/попытки запроса; прямому входу в области вызова она не нужна; ID не заменяет `IdempotencyKey` или `OperationId`.
<!-- pkb-translation:term:end -->




<!-- pkb-translation:term:start name="StorageTransactionId" -->
**StorageTransactionId** — механическая идентичность успешно зафиксированной транзакции хранилища, обеспечившей принятие; это не видимый домену дескриптор, идентичность операции или независимое доказательство бизнес-исхода.
<!-- pkb-translation:term:end -->

<a id="4-choosing-a-ball-boundary"></a>

## 4. Выбор границы Ball

`Ball` не становится автоматически экраном, конечной точкой, таблицей, репозиторием, сервисом, агрегатом или bounded context. Его границу выбирают по полномочиям и области инвариантов.

<a id="41-parts-should-be-combined-into-one-ball-when-they-have"></a>

### 4.1. Части следует объединять в один Ball, когда у них есть

- инварианты, которые должны приниматься одним решением;
- один ключ состояния и одна локальная граница согласованности;
- общий жизненный цикл и единица восстановления;
- один смысловой владелец;
- близко совпадающая граница доверия;
- совместимые профили масштаба и конкуренции за ресурсы;
- размер состояния и сложность перехода, подходящие для одного экземпляра.

<a id="42-parts-should-be-separated-when-they-have"></a>

### 4.2. Части следует разделять, когда у них есть

- независимые конечные исходы;
- разные требования к согласованности или долговечности;
- разные границы привилегий или доверия;
- разные ключи разделов или существенно разные профили нагрузки;
- независимые жизненные циклы;
- потребность в отдельной локализации сбоев;
- разные смысловые владельцы и темп изменений.

<a id="43-practical-rule"></a>

### 4.3. Практическое правило

> **Ball — наименьшая практически осуществимая область, в которой нужное решение может принять один владелец полномочий без доступа к изменяемому состоянию другого Ball.**

Слишком малая граница создаёт болтливый протокол и искусственные процессы. Слишком большая — God Nucleus, горячий ключ и огромную область влияния изменений.

Core ограничивает допустимые графы полномочий и зависимостей; он не обещает единственного графа разбиения системы. Два разбиения могут соответствовать, если каждое независимо доказывает те же правила владения, инвариантов, жизненного цикла, доверия, ограниченности и зависимостей. Одно лишь имя или структура пакетов не выбирает каноническое разбиение.

<a id="44-decision-tree-and-falsifiers"></a>

### 4.4. Дерево решений и опровергающие проверки

Задавайте вопросы по порядку:

1. Владеет ли кандидат изменяемым смысловым фактом, бизнес-Decision, полномочиями протокола/жизненного цикла или частным последствием ресурса? Если ничем из этого — оставьте его обычной утилитой или адаптером, а не Ball.
2. Должны ли две части принимать один строгий инвариант с одним ключом состояния, писателем, жизненным циклом и единицей восстановления? Если да — объедините их, если это не нарушает более сильную границу доверия, владения, раздела, долговечности или локализации сбоев.
3. Есть ли у частей независимые владельцы, ключи состояния, жизненные циклы, конечные исходы, границы доверия/долговечности или существенные потребности нагрузки/локализации сбоев? Если да — разделите их и используйте объявленную зависимость вместо общего изменяемого состояния.
4. Владеет ли кандидат состоянием и решениями локальной возможности? Если да — это кандидат Feature Ball.
5. Владеет ли он существенной координацией между владельцами полномочий: жизненным циклом, порядком/ветвлением/соединением, компенсацией/восстановлением/отменой, сверкой или независимым конечным исходом? Если да — это кандидат Flow Ball; одного числа вызовов или перехода команды недостаточно.
6. Владеет ли он только производным состоянием запросов, позициями источников, свежестью и политикой перестроения, не имея командных полномочий над фактами источников? Если да — это кандидат Read Model Ball.
7. Значение — лишь фокус, прокрутка, анимация, парсер, сокет или равносильная механика, не влияющая на решения? Оставьте его `EphemeralState`. Если оно может изменить бизнес-Decision, моделируйте его как зафиксированный State или явный доверенный текущий вход `Pulse`/`DecisionContext`.

Конкретные опровергающие проверки делают метки проверяемыми:

| Выбор | Подтверждающие доказательства | Опровержение |
|---|---|---|
| объединить | один инвариант, ключ состояния, писатель, жизненный цикл, восстановление и смысловой владелец | любая часть требует независимого принятия, владения, доверия/долговечности, раздела, конечного исхода или локализации сбоев |
| разделить | каждая сторона имеет своего владельца полномочий и может взаимодействовать через замкнутый контракт | сохранение нужного инварианта потребовало бы прямого доступа к чужому изменяемому состоянию или неатомарного разделённого решения |
| утилита | чистая механика без состояния, принадлежащая одной роли Ball, либо общий механический Foundation по PBA-43, без собственных полномочий протокола, жизненного цикла, состояния или ресурса | владеет изменяемыми смысловыми фактами, бизнес-решениями, жизненным циклом, полномочиями внешних последствий или общей доменной/бизнес-политикой без одного владельца Ball/Flow |
| Feature Ball | владеет каноническим состоянием/решениями одной локальной возможности | лишь координирует других владельцев полномочий и не владеет фактом локальной возможности |
| Flow Ball | владеет хотя бы одним свойством существенной координации и политикой его завершения | это лишь один переход/последовательность вызовов без независимого жизненного цикла, порядка, восстановления/отмены/сверки или полномочий исхода |
| Read Model Ball | владеет производным состоянием запросов, позициями, свежестью и перестроением | принимает команды для фактов источников, становится их вторым писателем или не имеет полномочий над материализованным чтением |

<a id="46-what-is-not-a-ball"></a>

### 4.6. Что не является Ball

Чистый помощник без состояния, комбинатор парсеров, числовая библиотека, форматтер или пакет объектов-значений без собственных полномочий состояния, жизненного цикла, протокола и ресурса обычно является утилитой, а не `Ball`. Локальная утилита Ball — артефакт реализации ровно одного Ball и одной логической роли; другой владелец полномочий не импортирует её как общую доменную политику. Общая для Ball утилита разрешена, только если это механический Foundation по PBA-43. Общая доменная или бизнес-семантика вместо этого остаётся явными локальными реализациями либо получает одного владельца Ball/Flow и объявленный Application Surface/протокол.

### Исходные записи определений для §4

<!-- pkb-translation:term:start name="Feature Ball" -->
**Feature Ball** — Ball, владеющий локальной бизнес-возможностью/полномочиями состояния.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="Flow Ball" -->
**Flow Ball** — Ball, владеющий существенной координацией конкретного процесса: любым независимым жизненным циклом, порядком/ветвлением/соединением, компенсацией/восстановлением/отменой, сверкой или конечным исходом между владельцами полномочий. Одного числа вызовов или перехода недостаточно.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="Material Coordination" -->
**Material Coordination** — владение жизненным циклом процесса, смысловым порядком/ветвлением/соединением, компенсацией/восстановлением/отменой, сверкой или независимым конечным исходом между владельцами полномочий. Одно реальное свойство может требовать Flow; повторные вызовы без такого владения не требуют.

<a id="5-three-logical-zones"></a>

## 5. Три логические зоны

Зоны — архитектурные роли. Они не требуют трёх процессов, трёх классов или трёх объектов в куче.

<!-- pkb-translation:pba-source:start id="PBA-01" title="Three-Zone Boundary" -->
**Исходное положение PBA-01 — Граница трёх зон.**

- **Правило:** каждый `Ball` приложения имеет логически разделённые роли Interaction, Nucleus и Resource/маршрута, определённые в §§5.1–5.3. Разделение сохраняет их разные полномочия и разрешённые вызовы, даже если один файл, стек вызовов или сгенерированная привязка использует **стирание представления** — опускает материализованную обёртку или адаптер, доказывая те же смысловые факты и рёбра ролей (§22); одно лишь физическое соседство не доказывает разделения.
  Карту логических ролей и рёбер проверки/конструирования могут прямо нести авторитетные исходники и охватывающая привязка: типизированные точки входа, ограничения видимости/импортов, фактические места вызовов, проверенные места конструирования и места принятой записи. Если факты там однозначны и доступны проверке, отдельный документ карты, таблица или манифест не нужны. Добавляйте аннотации или точные ссылки на исходники лишь для ещё неочевидных фактов; аннотация не обеспечивает соблюдение. Каждый присутствующий путь всё равно имеет определимую роль, полномочия, проверенное происхождение, где нужно, и разрешённое направление вызова; пустые роли Resource не требуют артефакта реализации.
- **Применимость:** `A`: каждый Ball, включая структуру в одном файле/стеке или сгенерированную структуру.
- **Владелец объявления:** владелец Ball определяет карту логических ролей и разные полномочия.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** исходники/граф типов привязки, карта ролей и рёбер Trusted Boundary, граф вызовов, доказательства происхождения и принятой записи.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** можно сослаться на общую структуру/линтер; физические адаптеры и пакеты пустых зон необязательны, разделение ролей обязательно.
- **Основной путь проверки:** `§17.5`
<!-- pkb-translation:pba-source:end -->

### 5.1. Interaction Hemisphere

Interaction адаптирует внешний мир к смысловому протоколу и обратно.

Interaction — логическая роль адаптера. Trusted Boundary — уполномоченная граница проверки и конструирования, а не ещё одна логическая зона и не синоним Interaction. Конкретная привязка часто реализует эту границу на входе Interaction или маршрута; совместное размещение или стирание представления допустимы, только пока доказательства проверки/происхождения границы и обязанности адаптации Interaction можно проверить отдельно. Ни одна сторона не получает от другой полномочий бизнес-политики или State.

Для каждого присутствующего пути границы он ДОЛЖЕН выполнять применимые шаги:

- разбирать сетевой/платформенный вход, когда границу пересекает необработанное представление;
- отклонять некорректный вход;
- нормализовать только по объявленным правилам полей;
- аутентифицировать через доверенную границу, когда используются полномочия актора/арендатора;
- проверять представление и каждый объявленный инвариант замкнутого протокола/типа, включая принадлежащие ему диапазоны, размеры и смысловую форму;
- строить проверенный, ограниченный `DecisionContext` или зависящий от актора `ReadContext` с **минимальным набором полей** из доверенных наблюдений, когда контекст нужен, — только с полями, активированными реальными смысловыми условиями и условиями границ (§22);
- создавать типизированный внешний `Intent` или `Query`, строить проверенный `ModuleCommandPulse` из принятого фрейма источника на объявленном маршруте команды либо возвращать незафиксированный `BoundaryResponse`;
- преобразовывать каждый присутствующий вид ответа/выхода в безопасный для контекста выход;
- применять кодирование и экранирование при пересечении данными границы интерпретатора/канала.

Классификация следует PBA-04 и §6.13, а не внешнему виду предиката. Interaction возвращает `ValidationFailure` только для представления или объявленного инварианта протокола/типа, чья истинность не зависит от зафиксированного State, смыслового Context и бизнес-политики. Правило, зависящее от State/Context, или правило, намеренно отданное владельцу как бизнес-выбор, достигает Nucleus. Фиксированное ограничение переходит в Interaction, только когда владелец протокола делает его версионированным инвариантом замкнутого типа; смена такого владения меняет семантику протокола, а не молча переносит то же правило между стадиями.

Уже доверенный, ограниченный, типизированный вход в том же стеке может нуждаться лишь в смысловой валидации и адаптации; ему не нужны парсер, объект аутентификации или сериализованный DTO лишь ради соблюдения логической зоны.

Доверенная граница привязки владеет проверкой исходного происхождения, подлинности, целостности, версии, действительности и конечного размера до построения любого контекста. Ball/Nucleus владеет замкнутой смысловой схемой контекста и толкует проверенные поля. Фиксированный доверенный издатель/область в том же стеке может доказываться охватывающей привязкой вместо копирования в значение контекста; это стирание представления не переносит смысловое толкование или бизнес-разрешение в границу.

Для маршрута команды доверенная граница Interaction/маршрута получателя владеет шагом проверки и конструирования §6.8. Она сохраняет принятый `commandSource` источника, действующую идентичность протокола, полезную нагрузку команды получателя и происхождение издателя; она не превращает команду во внешний `Intent` и не считает транспортное получение принятием получателя. Соответствующая проверенная граница результата строит `ModuleResultPulse` только из принятого фрейма `ModuleResultOutput` получателя.

Он НЕ ДОЛЖЕН:

- менять Sovereign State;
- совершать бизнес-переход;
- принимать решение о бизнес-разрешении или выборе результата чтения;
- создавать `Effect` или `ModuleCommand`;
- напрямую вызывать адаптер Resource для операции приложения;
- считать поле запроса доказательством аутентификации;
- передавать необработанный объект фреймворка в `Nucleus`.

Interaction может хранить эфемерное состояние UI или транспорта: фокус, прокрутку, анимацию, буферы сокета и состояние парсера запроса. Если значение UI или транспорта может менять бизнес-Decision, это не `EphemeralState`: сохраняйте его как зафиксированный State, если оно должно пережить текущую причину, либо передавайте как явный доверенный текущий вход `Pulse`/`DecisionContext` по §8.1. Скрытое значение виджета/контроллера/кеша никогда не получает полномочий решения лишь потому, что доступно локально.

### 5.2. Protocol Nucleus

`Nucleus` — единственное место локального бизнес-решения.

<!-- pkb-translation:term:start name="Nucleus" -->
**Nucleus** — чистый ограниченный смысловой владелец полномочий Ball, которому принадлежат State, схемы протокола/контекста и их толкование, а также единственное локальное бизнес-решение/Policy Gate. Он не выполняет I/O или проверку исходного происхождения и импортирует только собственные артефакты, включая локальные утилиты Ball, принадлежащие роли Nucleus, механический foundation и точные объявленные Application Surface получателя/производителя, нужные замкнутым контрактам Query/Pulse/Decision, без передачи владения.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:pba-source:start id="PBA-03" title="Pure Bounded Nucleus" -->
**Исходное положение PBA-03 — Чистый ограниченный Nucleus.**

- **Правило:** для каждого пути Decision Nucleus владеет смысловой схемой и толкованием явных входов и контекста, единолично владеет локальным бизнес-решением и бизнес-разрешением, не выполняет I/O или проверку исходного происхождения и завершается в действующих пределах, разрешённых §8.3. Когда этот предел задаёт числовое объявление `maxTransitionSteps`, а не только статическое доказательство, принадлежащий привязке Decision Work Meter из §8.3 измеряет его без изменения бизнес-смысла.
- **Применимость:** `A`: каждый путь Decision; числовое объявление `maxTransitionSteps` активирует точный контракт счётчика.
- **Владелец объявления:** Ball/Nucleus владеет чистой сигнатурой, смысловым толкованием контекста, политикой и пределами; привязка владеет механикой счётчика.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** тесты чистоты Nucleus/привязки, единственного места политики, границы происхождения, завершения, статического предела или разрешения/детерминизма счётчика.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** можно ссылаться на точную механику счётчика; смысловое владение остаётся локальным, а одного статического доказательства достаточно без артефакта счётчика.
- **Основной путь проверки:** `§17.1`
<!-- pkb-translation:pba-source:end -->

Он:

- владеет экземпляром Sovereign State;
- владеет замкнутыми смысловыми схемами и толкованием `DecisionContext` и любого зависящего от актора `ReadContext`, используемого его поверхностью чистого чтения;
- импортирует только собственные State, протоколы и локальные утилиты Nucleus в Ball, механический foundation и точные объявленные типы `Application Surface`, принадлежащие получателю или производителю и нужные его замкнутым контрактам `Query`, `Pulse` и `Decision`;
- принимает замкнутый `Pulse` и явный `DecisionContext`;
- возвращает ограниченный `Decision`;
- не выполняет I/O;
- не читает неявные часы, случайность, окружение, локаль, флаги функций или локатор сервисов;
- не импортирует SDK платформы или драйверы HTTP, SQL либо файловой системы;
- не меняет реестры runtime напрямую;
- не вызывает Nucleus другого Ball;
- не импортирует чужой изменяемый State, внутренности Nucleus, частные адаптеры Resource, зеркала вызывающей стороны или повторно объявленные типы получателя, либо реэкспортированные чужие контракты.

Только Policy Gate `Nucleus` решает вопрос бизнес-разрешения по зафиксированному State, текущей причине или Query и проверенному смысловому контексту. Он может сформировать ограничения разрешения в области действия, но не проверяет исходные учётные данные/материал происхождения через I/O и не передаёт бизнес-выбор привязке или Resource. Финальное техническое обеспечение у получателя или ресурса остаётся отдельным Execution Gate по §11.3.

<!-- pkb-translation:pba-source:start id="PBA-06" title="Controlled Causality" -->
**Исходное положение PBA-06 — Управляемая причинность.**

- **Правило:** если существует смысловой выход внешнего действия, его смысловое намерение создаёт только Nucleus внутри Decision. Это включает построение принадлежащего получателю `ModuleCommand` через его точный объявленный импортированный Application Surface; Interaction и Assembly проверяют, связывают и передают, но не создают и не синтезируют смысловое намерение.
- **Применимость:** `P`: существует смысловой выход внешнего действия.
- **Владелец объявления:** Nucleus/протокол выходов Ball.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** правило зависимостей и тесты выходов.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** механика конвертов может быть общей; при пустом наборе выходов правило опускается.
- **Основной путь проверки:** `§17.1`
<!-- pkb-translation:pba-source:end -->

### 5.3. Resource Hemisphere

Resource исполняет частный `Effect` своего `Ball` или даёт адаптер к объявленному внешнему ресурсу.

Эти обязательства активируются присутствующим путём операции Resource. Ball, работающий только с состоянием, имеет пустую логическую зону Resource и не нуждается в адаптере, обёртке capability или тестовых примерах ресурса.

Для каждой присутствующей операции Resource ДОЛЖЕН:

- иметь минимальную capability;
- соблюдать конечные действующие пределы запроса и ответа операции;
- не принимать нового бизнес-решения.

Непосредственно перед исполнением с полномочиями Execution Gate Resource/получателя проверяет применимые доказательства, возможности, ограничения, версии, свежесть/отзыв, конечную точку, квоту и привязки безопасных приёмников из §11.3. Он обеспечивает уже принятое действие и возвращает объявленный типизированный технический исход; он не переосмысляет бизнес-разрешение и не создаёт второго бизнес-решения.

Дополнительные обязательства возникают только со своим условием:

- граница интерпретатора использует безопасный приёмник;
- путь крайнего срока соблюдает контракт тайм-аута;
- путь отмены соблюдает контракт отмены;
- путь, создающий результат, проверяет внешний ответ и отображает исключения и статусы в замкнутый `Fact`;
- результат, пересекающий область вызова, возвращает корреляцию и проверенное происхождение, нужные этому маршруту.

Resource НЕ ДОЛЖЕН:

- менять Sovereign State;
- вызывать Interaction для принятия решения;
- заменять доменную политику повторов или запасного пути скрытым неограниченным циклом;
- возвращать сущность базы данных, HTTP-ответ или объект SDK в `Nucleus`;
- использовать неограниченные общие учётные данные, когда заявлен минимум привилегий.

<a id="54-polar-isolation"></a>

### 5.4. Полярная изоляция

<!-- pkb-translation:pba-source:start id="PBA-02" title="Polar Isolation" -->
**Исходное положение PBA-02 — Полярная изоляция.**

- **Правило:** роли Interaction и Resource/маршрута не образуют прямого пути приложения или бизнеса. Общая или сгенерированная механика может обслуживать обе стороны, только если не несёт изменяемого бизнес-смысла и не создаёт скрытого пути обмена.
- **Применимость:** `A`: каждый Ball.
- **Владелец объявления:** владелец Ball определяет разрешённые рёбра ролей.
- **Область действия:** точная область, заданная полями «Правило» и «Применимость».
- **Владелец контроля / доказательств:** проверки компилятора/зависимостей/графа вызовов и тесты скрытого обмена.
- **Разрешение, сбой и соответствие:** разрешается по §0.2; нарушение означает несоответствие в указанной области, если Правило не задаёт более строгий локальный сбой.
- **Повторное использование и поведение без условия применения:** общее правило графа можно использовать повторно; общая механика доказывает отсутствие изменяемого бизнес-пути, а не добавляет булево поле каждому Ball.
- **Основной путь проверки:** `§17.5`
<!-- pkb-translation:pba-source:end -->

```text
Interaction --X--> Resources
Resources   --X--> Interaction
```

Разрешённый смысловой путь проходит через `Nucleus`. Механическая инфраструктура — логгер, распределитель памяти, примитив трассировки или ограниченная коллекция — может использоваться обеими сторонами только по исходному положению выше.

<a id="55-permitted-dependency-graph"></a>

### 5.5. Разрешённый граф зависимостей

```text
interaction -> собственный внешний протокол
resources -> собственный протокол ресурсов
nucleus -> собственный State + собственные протоколы + локальные утилиты Nucleus этого Ball + точные объявленные Application Surface цели/производителя, необходимые закрытым контрактам Query/Pulse/Decision + механический foundation
assembly -> публичные протоколы + маршруты
runtime -> точки интеграции Ball, без внутренних бизнес-механизмов
```

Таблица задаёт и зависимости ролей внутри Ball, включая локальные утилиты Ball, принадлежащие одной роли, и единственный разрешённый смысловой импорт между Ball. Импорт локальной утилиты остаётся в графе времени компиляции, но не создаёт маршрута между владельцами полномочий или строки зависимости. Импорт Application Surface не передаёт владение. Nucleus НЕ ДОЛЖЕН импортировать чужой изменяемый State, внутренности, частные адаптеры Resource, реализации платформы/I/O, общие доменные утилиты без владельца или зеркала вызывающей стороны; он НЕ ДОЛЖЕН повторно объявлять или реэкспортировать импортированный протокол. Interaction и Assembly НЕ ДОЛЖНЫ создавать импортированную полезную нагрузку, сопоставление, отказ или другой бизнес-смысл.

Запрещено:

```text
interaction -> конкретный адаптер ресурса
адаптер ресурса -> UI/контроллер
nucleus -> SDK платформы
Ball A -> внутренности/состояние Ball B
бизнес-код -> глобальный локатор сервисов
```

### Исходные записи определений для §5

Эти помеченные определения — единственные исходные данные глоссария для терминов, которыми владеет этот раздел.


<!-- pkb-translation:term:start name="Interaction Hemisphere" -->
**Interaction Hemisphere** — роль адаптера внешнего/маршрутного входа-выхода: разбор, нормализация, валидация, пределы, кодирование, проверка принятого фрейма и построение доверенного `DecisionContext`/зависящего от актора `ReadContext` при выполнении условий; она не толкует бизнес-разрешение и не выбирает видимый бизнесу результат чтения. Присутствующий путь может содержать границу Trusted Boundary или примыкать к ней, но роль адаптера и уполномоченная граница проверки/конструирования не синонимы.
<!-- pkb-translation:term:end -->


<!-- pkb-translation:term:start name="Representation Erasure" -->
**Representation Erasure** — отсутствие материализованного адаптера, конверта, обёртки или поля, когда точные доказательства охватывающего типа/потока управления сохраняют то же смысловое значение, принятый кортеж, владение, полномочия, пределы и проверку. Меняется только представление; оно не может создать протокол-псевдоним, убрать активное защитное правило или передать смысл.
<!-- pkb-translation:term:end -->

<!-- pkb-translation:term:start name="Resource Hemisphere" -->
**Resource Hemisphere** — роль адаптера/исполнителя, которая реализует принятый Effect через минимальную capability и применяет непосредственный Execution Gate; она проверяет применимые доказательства/возможности/ограничения/версии/свежесть/отзыв/конечную точку/квоты/привязки приёмников и отображает типизированные исходы в `Fact`, привязанный к происхождению, не принимая нового бизнес-решения.
<!-- pkb-translation:term:end -->
