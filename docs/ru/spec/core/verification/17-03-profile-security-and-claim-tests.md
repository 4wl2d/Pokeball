### 17.6. Тесты конкурентного профиля

Для `BoundedConcurrent` добавьте случаи, чьи подпути существуют:

- входы `Fact` и `ModuleResultPulse` не по порядку, когда завершения могут менять порядок;
- заполненная почта или обратное давление возвращают закрытый `BoundaryResponse(AdmissionFailure(reason))` до принятия;
- конкурентные дубликаты входящих запросов, когда дублирование возможно;
- конкурентный дубликат цели с той же идентичностью и в состоянии принятой команды с ожидающим результатом, и в состоянии принятого результата: один принятый кадр или результат цели и только ACK либо воспроизведение точного кадра;
- отмена против завершения, когда существует отмена;
- тайм-аут против позднего результата, когда существуют сроки или неоднозначность;
- авария рабочего процесса, когда существуют рабочие процессы;
- ограниченная причинная цепочка, когда завершение может повторно войти в Decision;
- голодание и поведение приоритетов, если о них заявлено.

Для `Transient` с путём, содержащим выходы, внедрение сбоев проверяет обе стороны единственной точки публикации:

- сбой при резервировании или материализации до публикации не делает видимыми ни состояние, ни какой-либо выход;
- сбой сразу после атомарной публикации, но до первой отправки оставляет видимым полный сохранённый `AcceptedSnapshotDecisionFrame` или `AcceptedEventCommit`, из которого весь недоставленный пакет может продолжить путь по политике профиля;
- сбой между отправкой двух выходов не откатывает состояние или первый выход и не теряет сохранённую запись второго;
- отдельного окна с возможностью сбоя между публикацией состояния и постановкой в очередь не существует.

<a id="177-durable-state-profile-tests"></a>

### 17.7. Тесты профилей долговечного состояния

Для `SnapshotOutbox` и `EventJournal` выберите точки аварии из существующих путей:

```text
before transaction
inside transaction
commit acknowledged but response lost
root accepted ReplyOutput committed but response lost     # exact root replay path
before dispatch                                      # output path
request sent but ACK lost                            # ACK path
after target acceptance before source update         # detached result path
after target acceptance before target result exists  # pending-result duplicate ACK path
after accepted ModuleResultOutput before result dispatch # target result path
target result delivery exhausted                     # target stop tuple path
post-commit observation before/after ControlPulse    # delivery-observation path
before/after result commit                           # result path
recovery with pending outbox                         # output path
recovery after accepted NoDomainChange               # EventJournal path
delivery exhaustion persisted as DispatchStopped     # terminal delivery/status path
initial ReplyOutput exhaustion in status authority   # detached reply/status path
```

При наличии долговечного материализатора статуса операции тесты сбоев и гонок также покрывают наблюдение до его причинного источника, аварию с ограниченным ожиданием до и после применения источника, повторные и противоречащие свидетельства с тем же ключом, независимые порядки аспектов жизненного цикла, отмены, результата и остановки, резервирование `N/N+1` до принятия источника, давление после принятия без вытеснения или обрезания, попытку записать маркер при отстающей позиции источника или непустом ожидании, зафиксированный маркер до исчезновения записи, покрытый поздний дубликат, истечение срока маркера и отсутствие воскрешения. Зарезервированный ID кандидата, чей корневой запрос отклонён при валидации, допуске или Decision, не имеет принятого источника статуса для восстановления и не может быть синтезирован в известную запись или маркер хранения. Авария после принятого `ModuleResultOutput` цели, но до отправки результата сохраняет источник принятого результата цели; исчерпание маршрута цели добавляет `DispatchStopped` цели, а источник остаётся Pending/Unknown до проверенного результата или сверки.

Каждый тестовый пример заявления о доставке, долговечности, восстановлении, получении, принятии, однократности, RPO или RTO называет точные границу и область, механизм, предпосылки, хранение, свидетельства и отсутствующие гарантии. Парные отрицательные примеры доказывают, что одна лишь долговечность источника и одна лишь сохранённая ожидающая работа не устанавливают ни получение или принятие целью, ни более сильный исход ниже по цепочке.

Канонический пример Checkout дополнительно проверяет:

```text
Checkout recovery after accepted CheckoutStarted/CartLocked before InventoryReserved
Checkout recovery after accepted CheckoutStarted preserves exact equality of retained ingress fingerprint and atomic idempotency record
Checkout recovery after accepted InventoryReserved before PaymentCaptured
Checkout recovery after direct or reconciled PaymentCaptured before Order result
Checkout recovery after Order rejection before/between Refund, Release and Unlock
Checkout recovery after accepted StillUnknown preserves the terminal NeedsManualReconciliation frame and creates no new status generation
```

Канонический пример Catalog v2 дополнительно проверяет развёртывание сохранённого состояния:

```text
each v1 Idle/Searching/Ready/Failed/Cancelled variant -> exact authoritative v2 upcast
v1 CancellationRejected + authoritative bounded reason evidence -> v2 CancellationRejected(reason)
v1 CancellationRejected without that evidence -> quarantine/manual remediation
pending v1 output or Fact retains its v1 protocol/artifact meaning and is not decoded as v2
no schema-v1 record enters normal v2 decide and no missing field receives a null/default substitute
```

Минимальные свойства также зависят от условий применения. Пункты о Checkout ниже — свидетельства для §16, а не шаблон для другого долговечного Ball:

- нет отправки до фиксации источника, когда существуют выходы;
- нет состояния без соответствующей долговечной записи выходов, когда существуют выходы;
- нет повторного создания исходящей очереди через повторный запуск перехода, когда очередь существует;
- принятый `NoDomainChange` восстанавливает те же ревизию, маркер принятия и пакет выходов, когда выбран EventJournal;
- правила аварии до отправки и наблюдения доставки применяются, когда существуют соответствующие пути выходов, ACK или неоднозначности;
- авария после принятого `ModuleResultOutput` цели сохраняет этот кадр цели согласно выбранному профилю; повторная отправка использует тот же кортеж доставки результата и никогда не восстанавливает бизнес-смысл в Assembly;
- авария после принятия кадра команды цели, но до создания результата сохраняет одну ожидающую операцию цели; дубликат с той же идентичностью возвращает только проверенное ACK-доказательство и никогда не запускает Decision или Effect цели повторно, а позднейший принятый результат воспроизводится из своего точного кадра;
- исчерпание маршрута результата цели записывает `DispatchStopped` с `(effectiveProtocolIdentity, commandSource, resultSource)` и оставляет Checkout Pending/Unknown до проверенного результата или сверки; поздний результат может уточнить Checkout, не стирая остановку цели;
- допуск `N/N+1` по байтам и числу выходов цели и условным слотам остановки тестируется независимо от десяти слотов остановки выходов источника Checkout;
- остановка начального ответа и остановки командных шагов материализуются над одним ограниченным множеством `SemanticHandle`; наблюдение ответа не выдаёт себя за Pulse команды и не меняет `CheckoutState`;
- материализация статуса не теряет остановку, пришедшую до её причинной записи рабочего процесса, и не заменяет маркер хранения поздним дубликатом после покрытой позиции источника;
- SnapshotOutbox/EventJournal восстанавливают точные сохранённые значения M/S/I/P и происхождение без повторного запуска `decide` или чтения истории среды исполнения либо участника; Transient явно не обещает этого после потери процесса;
- после аварии `InventoryReserved(I)` создаёт точный Capture из сохранённых M + S и текущего действительного разрешения действия, прямой или полученный при сверке `PaymentCaptured(P)` создаёт точный Confirm из сохранённых S/I + P, а отказ заказа создаёт Refund/Release/Unlock только для сохранённых P/I/корзины;
- то же авторитетное действие с противоречащими значением, версией или доказательством, преждевременная очистка и компенсация неверной цели приводят к отказу по умолчанию; очистка после последнего конечного потребителя выдерживает повторное восстановление;
- полный сохранённый кадр C/RS/RI/RP удовлетворяет точному `maxStateBytes = N` при одном кортеже меры измерения State; семантически равное альтернативное сохраняемое представление отображается в ту же измеряемую последовательность, а `N+1` отклоняет весь Decision до принятия State, ревизии и выходов без обрезания;
- активное состояние Checkout v1 без авторитетных свидетельств миграции M/S/I/P не получает синтезированные значения по умолчанию и не входит в обычный `decide` v2; привязка к среде исполнения доказывает миграцию либо направление в карантин или на ручной путь;
- запись Checkout схемы v2 от прежнего артефакта переходов не входит в обычное восстановление лишь на основании совпадающей формы: сохранённый отпечаток входящего запроса проверяется по авторитетной принятой записи или объявленной миграции, иначе операция помещается в карантин; обычный Nucleus не читает реестр;
- дубликат корневого входящего запроса после потери принятого ответа повторно доставляет точный исходный принятый кадр `ReplyOutput` с новым `AttemptId`; запись идемпотентности и кадр имеют общий объявленный срок повторов, а конфликт отпечатка остаётся сбоем валидации до Intent без семантической записи;
- восстановление принятого Checkout `StillUnknown` возвращает тот же конечный `NeedsManualReconciliation`, исходные свидетельства проведения платежа и статуса и пустую последовательность выходов; повторная доставка не создаёт второй Decision или дескриптор, а обычная v1 не может автоматически возобновить процесс;
- устаревший владелец не может выполнить фиксацию, когда владение перемещаемо;
- неоднозначный внешний исход остаётся неизвестным до сверки, когда такой риск существует.

<a id="178-security-tests"></a>

### 17.8. Тесты безопасности

Для каждого присутствующего условия, связанного с субъектом, привилегиями, возможностями, интерпретатором, секретами или злоупотреблением, выберите только применимые тесты ниже. Записи Capture/Cancel/Refund/Release/Unlock — свидетельства только для примера Checkout:

- контекст субъекта от действительного утверждённого издателя с проверенными подлинностью и целостностью становится доверенным входом Decision, но сам по себе не даёт полномочий;
- действительный зависимый от субъекта контекст Query или статуса от утверждённого издателя выбирает только пространство имён и результат, разрешённые чистым семантическим чтением Ball; типизированная форма между Ball и статически доказанная форма в том же стеке эквивалентны;
- защищённый пример Query допускает один и тот же действительный контекст субъекта утверждённого издателя в каждый достижимый случай `ResultPayload`, принадлежащий цели: разрешённые данные, явный отказ, скрытие закрытых данных и намеренно объявленный нераскрывающий вариант; чистый Policy Gate выбирает случай, и каждое допущенное исполнение возвращает `ReadResult` без Decision, ревизии, выхода, исключения, `BusinessRejection` или `BoundaryResponse` после допуска;
- защищённый Query с неверным происхождением или издателем, неверной формой либо недопустимый Query отклоняется на объявленной границе до чтения и никогда не превращается в семантический `NotFound`; отказ при действительном контексте может не раскрывать наличие данных, только если объявлен этот точный принадлежащий цели вариант содержимого, и ни граница, ни вызывающая сторона, ни Assembly не могут его выдумывать;
- удаление любого достижимого варианта содержимого с разрешением, отказом, скрытием закрытых данных или нераскрытием нарушает исчерпываемость закрытого протокола, а не зависящий от субъекта или безусловно разрешённый Query не содержит недостижимой заглушки отказа;
- поддельные или изменённые свидетельства субъекта, неверный или неутверждённый издатель или realm и отсутствующие, устаревшие или непроверяемые обязательные свидетельства приводят к отказу по умолчанию до любого зависимого от субъекта Decision или результата Query или статуса, включая типизированную непривилегированную команду или чтение между Ball;
- в остальном эквивалентное, но не зависящее от субъекта решение или чтение не создаёт контекст субъекта, строку издателя, артефакт аутентификации или специальный тестовый пример для субъекта;
- поддельный контекст или доказательство, неверные цель, действие, объект, операция, ограниченное поле или версия и отсутствующая возможность отклоняются на владеющей доверенной границе или Execution Gate без неявных учётных данных или нового бизнес-решения;
- отказ бизнес-политики Nucleus Payment — принятый результат цели, а отказ Execution Gate после принятия — привязанный технический Fact и принятый результат; ни один не является носителем отказа до принятия;
- устранение представлений в том же стеке или сгенерированном коде сохраняет точные проверенный контекст, происхождение принятой причины и результата, порядок шлюзов и граф вызовов ролей;
- скрытые локаторы сервисов, изменяемое глобальное бизнес-состояние, выбор политики или маршрута в foundation и коммуникации ролей через foundation не проходят проверки архитектуры и безопасности;
- отсутствующее, просроченное или адресованное неверной аудитории разрешение;
- поддельное или изменённое разрешение и недоверенный или неверный издатель;
- подмена суммы, валюты, объекта, операции или другого ограниченного поля команды после авторизации;
- ограниченное привилегированное действие, допускающее дубликаты, привязывает каждое ограниченное поле контракта действия и применимую идентичность идемпотентности на Execution Gate; несовпадение или противоречащее содержимое с той же идентичностью приводит к отказу по умолчанию;
- привилегированный Grant между владельцами полномочий, чей контракт действия не определяет ограниченных полей цели или содержимого и чьё исполнение не может повторяться, всё равно проверяет утверждённого издателя, подлинность и целостность, контекст субъекта, аудиторию, действие, объект, операцию и действительность, но опускает `constraints` и любой дополнительный артефакт воспроизведения или идемпотентности; привязка неизменного содержимого принятого выхода остаётся отдельной проверкой по §11.3, когда это условие присутствует;
- неверные сохранённая привязка субъекта, способ оплаты, дескриптор действия, версия контекста, версия котировки или действительность разрешения при асинхронной задержке или восстановлении;
- изменённая или просроченная ссылка на контекст субъекта требует текущего `subjectBindingProof` для того же стабильного субъекта, издателя и realm; владение дайджестом или ID без доказательства не разрешает действие;
- Capture/Cancel/Refund/Release/Unlock получают отдельные текущие разрешения действий; разрешение на проведение платежа не используется повторно, а отсутствие резервной авторизации ведёт к типизированному остаточному или ручному исходу без привилегированного выхода;
- сырое разрешение, сессия или principal отсутствуют в текущем состоянии рабочего процесса, статусе, Projection и обычной телеметрии; точное зафиксированное разрешение остаётся только в защищённой записи выхода с закрытыми данными, скрытыми при выводе, до объявленного срока отправки и аудита;
- недостаточный уровень подтверждения субъекта;
- отозванная возможность;
- изменившаяся версия целевого объекта;
- слишком широкая область конечной точки или учётных данных;
- ограниченная граница возможностей успешно выполняет объявленный ограниченный класс операций; учётные данные администратора с локальной обёрткой или проверкой не проходят тест;
- разрешение файлового пути от корня возможности успешно, а прямой обход пути — нет; другие применимые параметризованные, структурированные и кодируемые по контексту точки исполнения имеют парные отрицательные тесты инъекций;
- доверенная привязка `InProcess + Hardened` с обычными внешними учётными данными ограниченной области и без требований сдерживания враждебных компонентов или отдельного субъекта остаётся InProcess; учётные данные, которые нужно изолировать от менее доверенного кода в той же среде, или высокопривилегированные данные, требующие собственного субъекта безопасности, выбирают `Isolated`;
- попытки SSRF, обхода пути, команд оболочки или прямого SQL;
- полная политика потока секретов покрывает каждый достижимый путь State, любого выхода, хранения, сериализации, журнала и телеметрии в его точной области; политика только для журналов не проходит проверку, когда достижим любой путь вне журналов;
- истощение ресурсов аутентифицированным субъектом.

<a id="179-claim-records-and-benchmarks"></a>

### 17.9. Записи заявлений о гарантиях и замеры производительности

Этот подраздел применяется при заявлении о гарантии. Каждый соответствующий тестовый пример сначала материализует полный `ClaimRecord`: точные названные границу, привязку и область, механизм, предпосылки, хранение, свидетельства и явные отсутствующие гарантии. Отрицательные примеры с удалёнными полями, неверной границей или областью, устаревшими свидетельствами, одной лишь долговечностью источника или одной лишь сохранённой ожидающей работой запрещают заявление, а не выводят более сильную гарантию.

При заявлении о производительности отчёт дополнительно записывает:

```text
hardware and OS
language/runtime/compiler version
optimization flags
allocator/GC mode
payload sizes and distribution
warmup and sample method
instrumentation overhead
profile combination
latency distribution
allocation/copy counts
```

Как проекция свидетельств заявления из отмеченного исходного положения `PBA-41`, такой замер сравнивает следующие базовые варианты там, где они применимы:

```text
direct hand-written call
Pokeball Inline binding
concurrent binding where applicable
existing framework baseline
```

Если заявление сравнивает числовые счётчики `maxTransitionSteps` между привязками к среде исполнения, отчёт записывает `meterIdentity`, `meterVersion`, `transitionArtifactVersion` и `unitDefinition` для каждого сравниваемого счётчика и доказывает равенство всех четырёх значений до числового сравнения. Иначе счётчики остаются явно несравнимыми и могут приводиться только как отдельные наблюдения, локальные для каждой привязки.

Не заявляйте «нулевые накладные расходы» по одному микробенчмарку без реалистичного содержимого и настроек сборки.

<a id="1710-observability"></a>

### 17.10. Наблюдаемость

Рекомендуемые причинные поля для путей, которые их материализуют:

```text
ballType
ballInstanceId
commitRevision
pulseType
semanticHandle
operationId
outputId when available
stateRevisionBefore/After
attemptId
outcome
latency
traceId
```

Эксплуатационная трасса, аудит безопасности и данные точного воспроизведения — разные артефакты. Трасса с удалёнными закрытыми данными не гарантирует воспроизведение.
