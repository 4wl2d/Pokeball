# Композиция в Pokeball

Обращайтесь к этому руководству, когда действительно нужен другой владелец состояния. Локальная композиция может использовать обычные типы, вызовы и один общий механизм принятия. Вспомогательная функция, папка или один обмен командой и результатом сами по себе не создают Flow.

<a id="a-counter-with-two-capabilities"></a>

## Counter с двумя интерфейсами возможностей

Counter владеет одним целым числом и разрешает увеличение до 3. Он предоставляет два принадлежащих цели интерфейса; Assembly передаёт каждому потребителю подходящий:

```text
CounterRead.value(): Int
CounterCommands.increment(): IncrementResult
IncrementResult = Changed(value: Int) | NotAccepted(reason: LimitReached)

pure counterDecide(value, Increment):
    if value >= 3: return NotAccepted(LimitReached)
    return Accepted(state = value + 1, result = Changed(value + 1))
```

`NotAccepted` означает, что Counter не принял ни изменения, ни выхода. `Changed` возвращается только после принятия изменения Counter. Прямой вызов цели и его возврат устанавливают корреляцию и происхождение в пределах этого доверенного вызова одной сборки. Само пересечение Ball не требует токенов команды/результата, enum издателей, поля идентификатора протокола или материализованного конверта. Для недоверенного или независимо доставляемого сообщения проверяйте настоящий источник и передавайте причинные сведения, необходимые для его доставки.

Counter описывает операции, а не имена потребителей. Чтение и увеличение остаются возможностями одного владельца. Добавление разрешённого потребителя — ещё одна привязка к `CounterCommands`; оно не меняет тип результата или бизнес-логику Counter. Если разрешение зависит от вызывающего, Counter по-прежнему принимает это бизнес-решение из доверенных входа и контекста. Узкие интерфейсы выражают доступный API; обычная видимость в языке не обеспечивает изоляции враждебного кода.

<a id="share-the-acceptance-mechanism"></a>

## Переиспользуйте механизм принятия

Следующий псевдокод использует один `SerialOwner` для Counter и источника. Проверку потока-владельца и механизм принятия обеспечивает реализация:

```text
handle(input):
    requireOwningThreadAndNoActiveDecision()
    candidate = runPureDecisionWithoutReentry(committed.state, input)
    if candidate is NotAccepted: return candidate
    requireExecutorForPresentOutputs(candidate)
    committed = candidate                 // State and all outputs together.
    try:
        for output in candidate.outputs:  // Retained by this immediate call.
            execute(output)               // After acceptance, outside decide.
    catch UnhandledExecutorFault:
        retainFrameAndStopNewMutations(candidate)
        throw
    return candidate.result
```

State и выходы здесь неизменяемы. При входе проверяется поток-владелец; решение не может повторно войти в своего владельца. Принятый вызов удерживает полный frame во время отправки. Необработанная ошибка исполнителя сохраняет этот frame и останавливает новые изменения; надзор и восстановление находятся за пределами примера. Counter возвращает результат сразу, поэтому принятому результату не нужна очередь. В этих закрытых путях нет растущего пакета, отделённой работы или повторов. Маленький механизм иллюстрирует привязку `Inline + Transient + InProcess + Standard`; это не универсальная среда исполнения и не обязательная библиотека.

Источник владеет текущим отображением. Его решение выдаёт один запрос увеличения, а исполнитель передаёт возвращённое значение новым входом источника:

```text
pure sourceDecide(state, Click):
    return Accepted(state = Waiting(state.displayed), outputs = [Increment])
pure sourceDecide(state, Returned(Changed(value))):
    return Accepted(state = Showing(value))
pure sourceDecide(state, Returned(NotAccepted(reason))):
    return Accepted(state = Refused(state.displayed, reason))
pure sourceDecide(state, ExecutionFailed):
    return Accepted(state = ExecutorFailed(state.displayed))

execute(Increment):
    try:
        result = counterCommands.increment()
    catch DeclaredExecutorFailure:
        source.handle(ExecutionFailed)
        return
    source.handle(Returned(result))

counter = SerialOwner(0, counterDecide)
reader = CounterRead(counter.read)
commands = CounterCommands(() => counter.handle(Increment))
source = makeSource(commands)
additionalConsumer = makeSource(commands)  // Assembly-only addition.
```

Исполнитель запускается только для принятого выхода источника. Counter принимает собственное изменение, затем источник принимает обновление отображения через тот же сериализованный механизм. Текущий вызов связывает непосредственный возврат с запросом; для доказательства этого порядка не нужно восстанавливать отсутствующие поля tuple. Отображаемое число источника — захваченное значение, а не второй записываемый источник полномочий Counter.

В реализации своего проекта проверьте три пути:

| Путь | Counter | Источник |
|---|---|---|
| Увеличение ниже лимита | Принимает увеличенное значение; возвращает `Changed(value)` | Принимает возвращённое значение для отображения |
| Увеличение на границе лимита | Возвращает `NotAccepted(LimitReached)` без принятия | Принимает отображение отказа; сохраняет прежнее значение |
| Исполнитель ошибается после принятия Counter | Принятое увеличение сохраняется | Принимает `ExecutionFailed`; никогда не записывает `NotAccepted` |

Для последнего пути внедрите ошибку при возврате уже принятого результата и проверьте, что принятое изменение Counter сохраняется. Это проверяет разделение стадий отказа в локальном примере. Внешнее действие, которое могло произойти, остаётся неизвестным, пока у контракта нет доказательства; ни timeout, ни ошибка исполнителя не означают непринятия. Такой контракт добавляет необходимые ему закрытые исходы, не заимствуя единую обязательную форму carrier.

<a id="check-the-work-that-can-grow"></a>

## Проверяйте работу, которая может расти

Этот источник выдаёт команду один раз; Counter возвращает один результат; обработчик результата ничего не выдаёт. Такая полная структура ограничивает один вызов. Ей не нужны числовые квоты зависимостей/участников/маршрутов, поле причинной глубины, резервирование level-1/level-2 или отдельный геометрический расчёт fan-out. Одного DAG импортов недостаточно: новая команда увеличения из каждого обработчика результата могла бы создать бесконечную цепочку с теми же импортами.

Очередям, внешним запросам, сохраняемым выходам, повторам и динамическому fan-out по-прежнему нужны реальные ограничения. Отклоняйте работу до принятия, если переполнение может затем привести к её потере. Когда действует накопительный причинный бюджет, сохраняйте его при передаче и повторе. Проект может выбрать числовые ограничения статической композиции ради конкретной цели, но добавление статически связанного потребителя само по себе не требует новой глобальной квоты.

<a id="try-three-small-changes"></a>

## Выполните три небольших изменения

Для этих упражнений используйте binding и средства тестирования своего проекта. Проверьте увеличение до 3 включительно, отказ при попытке превысить 3, принятие источником до вызова цели, сериализованную обработку завершения источником и описанный выше путь ошибки после принятия. При изменении реализации сохраняйте те же проверки поведения.

Ожидаемый объём каждого изменения:

| Изменение | Доменный код | Код композиции | Повторённая механика binding | Вручную синхронизируемые производные описания |
|---|---|---|---|---|
| Добавить небольшой Ball индикатора | Одно решение переключения | Одно создание `SerialOwner` | Нет; используется существующий класс | Нет |
| Добавить разрешённого потребителя Counter | Нет | Одно соединение `makeSource(commands)` | Нет | Нет |
| Переименовать переменную и извлечь проверку лимита | Одно решение с переименованием и одна чистая функция | Нет | Нет | Нет |

В таблице считаются ожидаемые изменения функций и соединений, а не измеренная производительность или удобство. Проверьте, что в вашей реализации проверки границы, отказа, порядка принятия и возврата сохраняются при рефакторинге. Типы и wiring примера дают доступный для проверки исходный контракт без второго manifest или таблицы маршрутов; инструмент может получить такие представления при необходимости. Эти упражнения из документации не доказывают удобства для всех систем или начинающих людей. [Оценка для проекта](EVALUATION.md) описывает более широкое измеряемое сравнение.

<a id="how-an-application-is-composed"></a>

## Как устроена композиция приложения

Pokeball различает четыре роли компонентов приложения:

| Роль | Чем владеет | Чем не владеет |
|---|---|---|
| `Feature Ball` | Локальной бизнес-возможностью и полномочиями над её состоянием | Внутренними деталями или изменяемым состоянием другой функции |
| `Flow Ball` | Жизненным циклом конкретной координации нескольких участников и её конечным исходом | Доменными фактами участников или общим движком рабочих процессов |
| `Read Model Ball` | Производным состоянием для запросов, позициями источников, свежестью и правилом перестроения | Полномочиями команд над исходными фактами |
| Пакет утилит | Чистой технической логикой без состояния | Полномочиями над состоянием, протоколом, жизненным циклом или ресурсами |

Реальные зависимости остаются видимыми через принадлежащие цели интерфейсы и wiring. Физические импорты вспомогательного кода остаются в ациклическом графе времени компиляции; они не образуют ещё один вид семантической зависимости. Непосредственный доверенный вызов может использовать типизированную цель как действующую идентичность операции. Явные версии нужны, когда стороны версионируются или развёртываются независимо. Assembly выбирает маршруты, версии и привязки; бизнес-решения и смысл результатов остаются у владельцев.

**Существенная координация** есть, когда один владелец полномочий должен владеть любым независимым жизненным циклом процесса, семантическим порядком или ветвлением/объединением, компенсацией или восстановлением, отменой, сверкой либо конечным исходом между владельцами полномочий участников. Одного такого свойства достаточно, если оно нарушает условия простого взаимодействия в один переход. Число вызовов, последовательная запись кода или один обмен командой и результатом сами по себе не означают существенную координацию и не требуют `Flow Ball`.

<a id="reads-draining-and-status-authority"></a>

### Чтения, Draining и полномочия над статусом

Межвладельческий `ReadDependency` однозначно определяет одного целевого владельца полномочий, принадлежащее цели отображение `Query -> ResultPayload` и действующую идентичность протокола, целевого владельца чтения/статуса, требование вызывающей стороны к свежести/согласованности, а также маршрут и привязку Assembly. Вызывающая сторона и Assembly не переопределяют результат цели, метку, факт статуса или смысл чтения. Несколько чтений остаются независимыми и не обещают единого атомарного снимка нескольких источников без отдельного объявленного механизма.

`Draining` отклоняет новые логические изменения, но обслуживает каждый доступный объявленный `Query` и запрос статуса из своего зафиксированного источника полномочий. Если источник чтения недоступен, доверенная граница может вернуть существующий ответ проверки или допуска до `read`; после допуска `read(...) -> ReadResult` остаётся успешным и не создаёт Decision.

У каждого пространства имён статуса ровно один зафиксированный источник запросов с ревизиями и одним писателем; он не получает полномочий команд над исходными бизнес-фактами. `OperationId` обозначает принятую корневую операцию: резервирование кандидата до `decide` либо отклонение корневой проверки, допуска или Decision до принятия не создаёт операции, дескриптора, выхода, известной строки статуса или маркера хранения. Зафиксированный снимок, покрывающий нужную область, может вернуть `NotFound`; непринятие нижестоящей целью остаётся аспектом Step уже принятой исходной операции. Совместное размещение может уменьшить отставание и число транзакционных границ; отдельный владелец статуса/Read Model может изолировать нагрузку запросов и объединять объявленные источники, но платит отставанием материализации и подтверждениями позиций источников. Ни один вариант не допускает двух независимо записываемых ответов статуса.

<a id="security-context-and-foundation"></a>

### Безопасность, контекст и Foundation

Когда актор, арендатор, издатель, область доверия, уровень подтверждения или делегирование могут менять `Decision` либо разрешение или выбор результата `Query`/чтения статуса, доверенная граница привязки к среде исполнения строит проверенный, ограниченный контекст с минимальным набором полей. Основа — одобренный издатель либо равноценное фиксированное доверенное доказательство в том же стеке. Поддельное, изменённое, выпущенное не тем издателем или в другой области, отсутствующее, устаревшее либо иначе непроверяемое обязательное доказательство ведёт к закрытому отказу. Решения и чтения, не зависящие от актора, не создают артефактов контекста актора, издателя, аутентификации или доказательств актора.

Только Nucleus Policy Gate принимает бизнес-решение о разрешении на основе зафиксированного State, текущей причины или Query и доверенного контекста. Непосредственно перед исполнением с полномочиями Resource/target Execution Gate проверяет все применимые доказательства, capabilities, ограничения, версии, свежесть/отзыв, конечную точку, квоту и привязку безопасного приёмника, не принимая нового бизнес-решения. Сбой проверки после принятия остаётся объявленным путём Resources, результата или статуса; он не может откатить или понизить статус принятой работы либо стать носителем ответа до принятия.

Общий код Foundation содержит только технические примитивы. Он не владеет изменяемым бизнес-смыслом, решениями бизнес-правил, доменными полномочиями или статусом, выбором маршрутов, локатором сервисов или скрытым состоянием связи. Общая доменная/бизнес-утилита без владельца запрещена: оставьте семантику внутри Ball, в том числе с намеренным небольшим дублированием, либо назначьте одного владельца Ball/Flow и откройте его объявленный Application Surface/протокол.
