# Сопоставление примера Checkout

> **Статус:** производный неканонический пакет. Он не определяет и не расширяет Pokeball Core. Проверьте [BASELINE.md](BASELINE.md); приоритет имеет Core.

Откройте это продолжение только для активированного свойства, аналогичного каноническому сценарию Checkout Flow. Оно не задаёт значения проекта по умолчанию.

У Checkout четыре участника с полномочиями — Cart, Inventory, Payment и Order — и девять принадлежащих целям отображений команд и маршрутов полного цикла. Четыре отношения `FlowParticipation` описывают координацию. Эти числа — видимые сведения примера, а не обязательные пределы Core. Auth предоставляет доверенный контекст, Checkout владеет Flow; ни один не является участником. Типы и wiring могут порождать manifest и представление маршрутов.

Каноническая трасса сохраняемых значений:

```text
CheckoutStarted + DecisionContext(actorContext=A, artifactVersion=IV)
  retains M + ingress fingerprint + IV + actor binding
CartLocked retains S
InventoryReserved retains I -> Capture(S, M, current grant)
PaymentCaptured retains P -> Confirm(S, I, P)
Order rejection -> Refund(P) + Release(I) + Unlock(original cart/lock)
```

Начальная доверенная привязка проверяет и ограничивает `IV` как точную версию артефакта отпечатка Interaction, выбранную для этого входа. Checkout сохраняет `interactionArtifactVersion = IV`; она отличается от `transitionArtifactVersion` Nucleus и никогда не берётся из отсутствующего общего поля Context или неявного состояния сборки. Отсутствующая, устаревшая, несовпадающая или недоверенная `IV` отклоняется до принятия. В пределах объявленного допустимого горизонта повтора охватываемый повтор с тем же ключом/отпечатком повторно доставляет доказательство исходного принятого кадра `ReplyOutput(RequestAccepted(operationId))` с неизменными `BallInstanceId`, `CommitRevision`, материализованным `OutputId`, `semanticHandle`, `sourceOrdinal`, полезной нагрузкой, `OperationId` и сохранённой `IV`; меняется только `AttemptId`, второго Decision Checkout, принятого кадра, выхода, команды или источника статуса нет. Пока охватывающая запись идемпотентности хранится, тот же ключ с другим отпечатком возвращает до Intent `BoundaryResponse(ValidationFailure(IdempotencyConflict))`, но никогда `DecisionRejected`, и не создаёт сопоставление операции Checkout, Decision, ревизию, дескриптор, Reply, выход или источник статуса. Принятый кадр и запись хранятся не меньше горизонта повтора; после исчезновения записи ни воспроизведение, ни конфликт не подразумеваются. Восстановление, миграция и карантин используют исходно сохранённое происхождение.

Каждое сохраняемое значение несёт корреляцию владельца/наблюдения, версии, происхождение и хранение до последнего потребителя, требуемые долговечным путём. Прямое доказательство и доказательство сверки одного P подтверждают друг друга; противоречивое доказательство приводит к отказу по умолчанию. Восстановление использует зафиксированные значения, а не реестр участника/среды исполнения или повторный запуск текущего кода перехода.

Каждая команда Checkout проходит один и тот же мост принятой цели:

```text
accepted Checkout ModuleCommandRequest
-> verified target ModuleCommandPulse(commandSource, effectiveProtocolIdentity,
                                       command: ModuleCommand, issuerProvenance)
-> target decide
-> accepted target ModuleResultOutput(sourceOrdinal, commandSource,
                                      payload: ModuleResult)
-> verified Checkout ModuleResultPulse(commandSource, resultSource,
                                       effectiveProtocolIdentity,
                                       result: ModuleResult, issuerProvenance)
```

Assembly привязывает и обслуживает маршрут; она не может создавать ни один причинный токен, полезную нагрузку или смысл отказа. Устранение представления в том же стеке доказывает те же кортежи. Ключ доставки результата — безымянный кортеж `(effectiveProtocolIdentity, commandSource, resultSource)`.

Обычные бизнес-исходы всех девяти маршрутов Checkout используют принятые результаты целей:

| Команда | Путь принятого результата |
|---|---|
| `Cart.LockForCheckout` | успех или доменный отказ/конфликт блокировки |
| `Cart.Unlock` | успех/отклонение/сбой/неизвестность |
| `Inventory.Reserve` | `InventoryReserved` или `InventoryReservationRejected` |
| `Inventory.Release` | успех/отклонение/сбой/неизвестность |
| `Payment.Capture` | средства списаны/отклонено/сбой/исход неизвестен |
| `Payment.CancelCapture` | принята до старта/в процессе, слишком поздно, отклонена или неизвестно |
| `Payment.Refund` | успех/отклонение/сбой/неизвестность |
| `Payment.GetOperationStatus` | `Captured`, `DefinitelyNotCaptured` или `StillUnknown` |
| `Order.Confirm` | подтверждён либо окончательно отклонён/сбой/неизвестность |

`InventoryReservationRejected` никогда не является носителем до принятия. `DefinitelyNotCaptured(RejectedBeforeAcceptance, ...)` описывает отказ исходного `Payment.Capture`, а не `Payment.GetOperationStatus`. Окончательный отказ `Order.Confirm` после capture — принятый результат. Checkout может принять собственный `RejectedBeforeExternalCommitment`, но этот исход Flow не копирует причину носителя.

Каноническая проекция носителя точна: охватывающий `source` Checkout проецирует `commandSource`; разрешённая зависимость — `effectiveProtocolIdentity`; `reason` — один замкнутый `boundaryResponse`; `acceptanceEvidence` — `targetBoundaryProvenance`. Проверенный носитель даёт `acceptance = RejectedBeforeAcceptance` и `outcome = NotExpected`; переданный `BusinessRejection` лишь информирует. Проверенный принятый `ModuleResultOutput(Rejected(...))` даёт `acceptance = Accepted` и `outcome = Rejected`. Конфликт носителя и результата приводит к отказу по умолчанию.

Вызов участника, отправленный из принятого выхода Checkout, сохраняет владение цели, стадию отказа и сериализованное завершение Flow. Полное конечное локальное исполнение не требует уровней резервирования. Независимо доставляемые, сохраняемые, повторяемые и внешние пути Checkout по-прежнему требуют переносимых причинных свидетельств, конечной ёмкости и отсутствия потери принятого; смена транспорта не сбрасывает применимое ограничение этой работы.

Payment показывает Dual Gate и границу команды/чтения. Доверенная граница цели проверяет принятый источник команды, действующую идентичность протокола, контекст актора/Grant в области действия, пределы и происхождение до создания `ModuleCommandPulse`. Nucleus Payment владеет бизнес-схемой и Policy Gate и единолично принимает бизнес-Decision/результат. Непосредственно перед исполнением провайдера Execution Gate проверяет текущее доказательство, минимальные технические полномочия ограниченного класса операций провайдера на реальной границе capability, ограничения, версию, свежесть/отзыв, endpoint, квоту и применимый безопасный приёмник, не создавая бизнес-решение. Отказ проверки/допуска/происхождения до `decide` использует носитель; принятый отказ Nucleus — принятый `ModuleResultOutput(Rejected(...))`; сбой провайдера/Execution Gate после принятия остаётся доказательством Resource/результата/статуса и не может стать носителем.

При повторной доставке команды Payment в пределах горизонта идемпотентности наблюдение зависит от того, существует ли уже кадр результата цели. До принятия результата — например, после принятия `EffectRequest` провайдера командой `Payment.Capture`, но до её порождающего результат `Fact` — Payment возвращает только проверенное доказательство ACK исходного принятого кадра цели и состояния ожидания результата; он не ждёт, не запускает новый Decision, не меняет ревизию состояния, не выдумывает ожидающий результат и не исполняет провайдера снова. После принятия результата он повторно доставляет точный принятый кадр результата с неизменными действующей идентичностью, `commandSource`, `resultSource`, ревизией цели, `semanticHandle`, `sourceOrdinal` и полезной нагрузкой; меняется только `AttemptId`. Другой отпечаток команды или противоречивые доказательства приводят к отказу по умолчанию.

`Payment.GetOperationStatus` остаётся командой, потому что Checkout нужны принятое происхождение, стабильная идентичность шага, идемпотентное воспроизведение, статус и сверка. Её принятие снимка с тем же состоянием повышает ревизию Payment и выдаёт принятый результат через плоский `AcceptedSnapshotDecisionFrame<State> { commitRevision?, nextState, outputs }`; EventJournal записывает `AcceptedEventCommit` с `decision = NoDomainChange { outputs = [...] }` без независимого `nextState`. Повторная доставка в пределах горизонта возвращает прежний результат и доказательство цели без нового Decision/ревизии. Обычный поиск без записи использует вместо этого `ReadDependency`/`Query`.

`Captured` и `DefinitelyNotCaptured` следуют объявленным автоматическим переходам. Принятый `StillUnknown` исчерпывает единственный обычный слот сверки `payment-status` Checkout v1: Checkout сохраняет исходные аспекты принятия/исхода capture и точное доказательство статуса, проводит слот через `Accepted + Succeeded`, принимает один Decision источника с `outputs = []` и задаёт `terminalOutcome = NeedsManualReconciliation`. Он не создаёт второе поколение статуса, таймер, команду, Effect, компенсацию или путь повторного открытия. Дубликат/повторная доставка не создаёт второй Decision, ревизию, дескриптор или выход. Обычный v1 не переписывает конечный кадр молча; более позднее доказательство требует отдельно объявленного артефакта ручной работы/восстановления.

Checkout объявляет `maxRetainedDispatchStops: 10` и имеет ровно десять канонических слотов остановки доставки источника:

```text
0 Cart.LockForCheckout
1 initial RequestAccepted ReplyOutput
2 Inventory.Reserve
3 Payment.Capture
4 Payment.CancelCapture
5 Payment.GetOperationStatus
6 Order.Confirm
7 Inventory.Release
8 Payment.Refund
9 Cart.Unlock
```

`initialAcceptanceReply` — точный дескриптор `SemanticHandle(operationId, Checkout.RequestAccepted, "initial-acceptance")`. Его доверенный `ControlPulse` доставки только для статуса привязан к принятому кортежу источника Reply; это не командный Pulse или бизнес-результат, и он не пишет напрямую в `CheckoutState`. Начальный Decision резервирует слоты `cartLock` и `initialAcceptanceReply` до принятия.

Checkout создаёт `CheckoutKnownStatus` только из записи принятой операции Checkout. Зарезервированный кандидат корня с последующим отказом проверки, допуска или `decide` Checkout даёт только типизированный корневой `BoundaryResponse`: авторитетного `OperationId`, дескриптора, выхода, строки статуса или маркера хранения нет. Поэтому зафиксированный снимок статуса, охватывающий пространство имён, может вернуть `CheckoutNotFound` для этого кандидата при обычном барьере отсутствия материализатора. Напротив, непринятие команды участника остаётся соответствующим аспектом `Step.acceptance = RejectedBeforeAcceptance` уже принятой операции Checkout; это не жизненный цикл корня.

Материализатор статуса резервирует всю достижимую ёмкость операции/ожидания/аспектов/маркера/остановок до принятия источника, никогда не вытесняет принятые факты, применяет причинные источники либо ограниченное ожидание, идемпотентно объединяет тождественные дубликаты, отказывает по умолчанию при противоречивых доказательствах одного ключа и создаёт маркер хранения только после охватываемых позиций источника и пустого ожидания. Тесты проверяют отказ зарезервированному ID корня и его принятие, изоляцию носителя участника, только reply, reply плюс все девять команд, оба порядка двух остановок, дубликат/конфликт, сохранение жизненного цикла/отмены, гонки маркера/ожидания, отсутствие воскрешения и ёмкость `10/11`.

Принятый `ModuleResultOutput` участника использует отдельный принадлежащий участнику слот остановки цели с ключом кортежа доставки результата. Сбой до отправки результата не стирает этот принятый результат в выбранном профиле цели. Исчерпание маршрута цели записывает `DispatchStopped` цели, но не добавляет одиннадцатый слот источника Checkout и не устанавливает аспект Checkout; Checkout остаётся в `Pending`/неизвестности до проверенного результата или сверки, а поздний результат может уточнить его, не стирая факт остановки цели.

Это достижимые пути Checkout, а не универсальные требования к Ball.
