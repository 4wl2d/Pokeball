Resources каталога получает только ограниченную capability `Catalog.Search` через реальную границу клиента/учётных данных с ограниченными правами и не имеет административного клиента. Его SQL-пример показывает привязку параметров и явное экранирование для диалекта; при наличии пути к интерпретатору файловой системы он не заменяет отдельные положительные проверки файлового доступа от корня capability и отрицательные проверки необработанного обхода пути.

Каноническая причинная трасса:

```text
SearchRequested поколения N
-> принятое состояние + дескриптор N отделённого FindProducts
-> результат с привязкой к происхождению
-> применить текущий / проигнорировать устаревший / сохранить типизированный сбой или OutcomeUnknown
-> отобразить зафиксированное состояние одной тотальной функцией CatalogView
-> опубликовать выход только после принятия
```

Когда поколение `N+1` начинается до результата `N`, §15.7 Core намеренно опускает промежуточный блок повторного запуска, но предполагает, что его отдельный Decision принят и установил новое поколение и дескриптор до сопоставления устаревшего результата.

Catalog v2 фиксирует `protocolVersion = 2.0.0`, `stateSchemaVersion = 2` и `transitionArtifactVersion = 2.0.1`. Поле состояния `revision` — доменная ревизия, которой владеет Catalog, а не `CommitRevision`, которым владеет принимающая сторона. Конкретная привязка к среде исполнения приравнивает или выводит их друг из друга только через явный контракт, доказывающий точное равенство и сохраняющий оба смысла владения. Его запрос — точно `GetCatalogView -> CatalogView`. Зафиксированный `CatalogState` отображается через шесть явных непересекающихся случаев без запасной ветви:

```text
Idle           -> CatalogIdle
Searching      -> CatalogSearchStatus(operationId, Searching(...), cancellation)
Ready          -> CatalogSearchStatus(operationId, Ready(...), cancellation)
Failed         -> CatalogSearchStatus(operationId, Failed(...), cancellation)
OutcomeUnknown -> CatalogSearchStatus(operationId, OutcomeUnknown(...), cancellation)
Cancelled      -> CatalogSearchStatus(operationId, Cancelled(...), cancellation)
```

Составной статус сохраняет жизненный цикл/результат вместе с независимым аспектом отмены, включая `CancellationRejected(reason)`. `ProjectionOutput` состояния поиска использует то же отображение. Более слабое наблюдение неизвестного исхода не может ухудшить доказанный результат `Ready`/`Failed`; более поздний соответствующий доказанный результат может уточнить `OutcomeUnknown`.

Для отмены в `Searching` или `OutcomeUnknown` при имеющемся `pendingSearch` команда `SearchCancelled(intentOperationId)` сначала требует `intentOperationId = state.operationId = pendingSearch.operationId`. Несовпадение возвращает точно `Rejected(BusinessRejection.StaleSearchOperation(expectedOperationId = state.operationId, receivedOperationId = intentOperationId))`, которое Interaction кодирует как `BoundaryResponse(DecisionRejected(...))`. Ни Decision, ни State, ни ревизия, ни дескриптор, ни `ProjectionOutput`, ни `EffectRequest` отмены, ни выход не принимаются; отмена не может нацелиться на другой текущий поиск. Иное исходное состояние следует собственному закрытому контракту отклонения и не может позаимствовать дескриптор. При точном совпадении совместимые порядки принятой незавершённой работы и результата сходятся без потери жизненного цикла, отмены или причины отказа; конечная отмена сама доказывает принятие, а последующее более слабое наблюдение ничего не меняет. Взаимоисключающие доказательства конечного результата и отмены сохраняют первый принятый конечный кадр и отклоняют противоречащее второе доказательство до принятия — симметрично в обоих порядках.

У `ProductSelected(productId)` шесть явных переходов, точно соответствующих `Idle`, `Searching`, `Ready`, `Failed`, `OutcomeUnknown` и `Cancelled`. Каждый сохраняет все поля и аспекты своего состояния, кроме принятого увеличения ревизии, и выпускает ровно один выход:

```text
SignalPublication(
    payload = ProductSelectionConfirmed(productId),
    sourceOrdinal = 0
)
```

Catalog владеет `CatalogSignal.ProductSelectionConfirmed`; Assembly лишь связывает маршрут производителя/потребителя `2.0.0/2.0.0` и не может определять или создавать данные. Показанный в Core путь выбора не зависит от актора и несёт только свой зарезервированный ID выбора; поля актора, конфигурации и времени отсутствуют, пока не появятся независимые условия для них.

Сохранённое состояние схемы v1 попадает в `decide` v2 только после преобразования уполномоченным владельцем. Запись отказа в отмене v1 преобразуется, только если ограниченные принятые свидетельства дают точную новую обязательную причину; иначе она изолируется или передаётся на объявленное ручное исправление. Не принимаются причины null, пустые, общие, выведенные из логов или предположенные; сохранённые выходы v1 сохраняют смысл v1.

Регрессионный набор Catalog сохраняет различие доменной ревизии и `CommitRevision`, все шесть отображений состояния в представление и шесть переходов `ProductSelected`, точное совпадение и устаревшие Intents отмены A после B без Effect для неверного поиска, каждую совместимую комбинацию жизненного цикла × отмены × причины отказа, оба порядка конечного конфликта, уточнение поздним результатом/неизвестным исходом и отсутствие лишних полей при независимости от актора. Имеющееся требование статуса нельзя выполнить, опустив его Query или один достижимый аспект.

Ball без внешней операции, отделённого результата или пути отмены не наследует эти механизмы.

## Использование при ревью

1. Найдите один аналогичный путь или риск, а не похожее имя домена.
2. Сошлитесь на Core и соответствующее правило `PKB-AR-*`, а не только на пример.
3. Сравните нормативный исходный код проекта и действующее правило с инвариантом.
4. Используйте только тесты, которые включает этот путь.
5. Вернитесь к Core, если пример не покрывает свойство.
