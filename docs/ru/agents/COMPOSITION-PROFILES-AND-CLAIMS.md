## 5. Действующий профиль

Разрешайте четыре измерения независимо, даже когда одна именованная политика задаёт их вместе:

| Измерение | Варианты | Механизм по триггеру |
|---|---|---|
| Исполнение | `Inline` / `BoundedConcurrent` | mailbox/воркеры/обратное давление — только при выборе конкурентного исполнения |
| Состояние | `Transient` / `SnapshotOutbox` / `EventJournal` | долговечные записи/восстановление/статус — только при выборе долговечности |
| Изоляция | `InProcess` / `Isolated` | IPC/principal/локализация ресурсов — только при выборе изоляции |
| Безопасность | `Standard` / `Hardened` | усиленные меры для актора/Grant/аудита/злоупотреблений — только при выборе усиления |

Разрешение профиля состояния также выбирает ровно одну форму изменения и принятия. `Transient` и `SnapshotOutbox` используют каноническую сигнатуру `decide(...) -> SnapshotDecisionResult<State>` и публикуют плоский `AcceptedSnapshotDecisionFrame<State> { commitRevision?, nextState, outputs }`. `EventJournal` использует каноническую сигнатуру `decide(...) -> EventDecisionResult` и записывает `AcceptedEventCommit` с `decision: EventDecision`; он восстанавливает State через `evolve` и никогда не добавляет независимый Event `nextState`. Это взаимоисключающие выбранные контракты, а не объединение времени исполнения. Они описывают наблюдаемое принятие, а не обязательные физические объекты или копии. Локальная привязка может использовать обычные State и возвращаемые значения, сохраняя полное принятие до отправки. Неизменяемые подструктуры могут разделяться; изменяемые builder, принадлежащие только кандидату, никогда не меняют ранее опубликованное значение и не выходят к читателям. Повторно используйте один сериализованный механизм принятия/обработки выходов для разных владельцев вместо копирования на каждый Ball.

Проект/привязка к среде исполнения может один раз выбрать точную политику по умолчанию. Ball не нужна повторная строка политики, когда выбор привязки его охватывает; он записывает только явный локальный выбор или разрешённое отличие. Разрешение должно дать один действующий профиль; изменяемый псевдоним «latest» или реестр времени исполнения недопустим.

Область полномочий учётных данных и защита самих учётных данных — разные триггеры. Обычные внешние учётные данные с ограниченными полномочиями могут оставаться в доверенной привязке `InProcess + Hardened`, если модель угроз не заявляет сдерживание враждебных компонентов и не требует отдельного security principal для этих данных. Выберите `Isolated`, когда учётные данные должны быть недоступны менее доверенному коду в том же процессе либо высокопривилегированные данные требуют защиты собственным principal; минимальные привилегии и все активированные правила Policy/Execution Gate действуют в обоих профилях.

## 6. Заявления о гарантиях

Выбор профиля — не заявление о гарантиях. Когда проект говорит `durable`, `at-least-once`, `isolated`, `secure`, `atomic`, `zero overhead` или подобное, создайте запись о заявлении:

```text
claim and exact boundary
exact scope
effective profile/policy digest
mechanism and failure assumptions
ordering/delivery point and retention horizon
evidence artifact and observed result
explicit non-guarantees
owner/review date
```

Запись никогда не выводит получение/принятие целью, безопасность исполнителя, долговечный ответ, доставку в конечном итоге, однократное исполнение или восстановление за своей названной границей из одной лишь долговечности источника или сохранённой ожидающей работы. Без записи удалите заявление, а не добавляйте предполагаемые механизмы.

## 7. Foundation

Когда помощник предлагается более чем для одного Ball, один авторитетный источник и проверка в области проекта классифицируют его как стабильную механическую Foundation либо отвергают как доменную/бизнес-семантику без владельца. Один раз запишите проверку экспортов/зависимостей/графа вызовов, результат проверки изменяемого состояния/протокола/полномочий на ресурсы/выбора маршрута/скрытого взаимодействия, принятые исключения, владельца и точный дайджест источника или политики.

Общая Foundation не содержит изменяемого бизнес-смысла, решений бизнес-политики, доменных полномочий, выбора маршрута, service locator, реестра времени исполнения или скрытого состояния взаимодействия. Доменная/бизнес-семантика помощников остаётся локальной в Ball, включая намеренное небольшое дублирование, либо получает одного владельца Ball/Flow и объявленную Application Surface/протокол; переименовать её в Foundation нельзя. Область проекта/привязки к среде исполнения охватывает свои Ball без повторения проверки в каждом; Ball записывает только локальное исключение или отличие. Если общей механической Foundation нет, артефакт Foundation не создают.

<a id="8-change-output"></a>

## 8. Результат изменения

Обычная работа с композицией сообщает только изменённые рёбра, действующее объявление или политику/отличие, новые активированные риски и тесты. Обновляйте Assembly, контракты целей, состояние Flow или общую политику только там, где они авторитетны. Полное досье графа/заявления создают только для заявления о соответствии или выпуске по [TEST-AND-REVIEW-GATES.md](TEST-AND-REVIEW-GATES.md).
