# Первая функция приложения на Pokeball

> [!NOTE]
> Это учебное руководство, а не нормативный документ. Pokeball определяет упорядоченный [набор документов Core](spec/pokeball-architecture-core.md). Примеры объясняют отдельные пути; они не служат реализацией среды исполнения или заключением о соответствии.

[Обзор](README.md) · **Быстрый старт** · [Внедрение](ADOPTION.md) · [Оценка для проекта](EVALUATION.md)

Начните с одного факта, у которого есть владелец, и одного правила. Ball может занимать один файл. Смысл разделения — различать адаптацию входа, решение об изменении, принятие этого изменения и выполнение действий, которые из него следуют.

<a id="a-complete-local-example"></a>

## Полный локальный пример

Черновик заказа владеет количеством товара, которое покупатель собирается купить. Бизнес-правило допускает количество от 1 до 20. Черновик не владеет остатками, не принимает заказ, не резервирует товар, не считает платёж и не выполняет I/O.

Хост выделяет черновику одну закрытую область последовательных вызовов в одном потоке-владельце. Вызовы не уступают выполнение и не вызывают обратные вызовы; другой поток не может получить доступ к состоянию. Выбранные язык и хост должны реально обеспечивать это ограничение: комментария недостаточно. Неизменяемое состояние фиксированного размера публикуется одним присваиванием. При потере процесса черновик теряется.

Эти условия задают `Inline + Transient + InProcess + Standard` со статической композицией. Независимый от языка псевдокод ниже показывает всю функцию приложения в одном файле:

```text
record State { quantity: UInt8 }
enum Intent { QuantitySelected(value: UInt8) }
enum Query { GetQuantity }
enum BusinessRejection { QuantityOutsideRange }
record QuantityNotAccepted { reason: BusinessRejection }

pure decide(state: State, intent: Intent):
    match intent:
        QuantitySelected(value):
            if value < 1 or value > 20:
                return Rejected(QuantityOutsideRange)
            return Accepted(SnapshotDecision(State(quantity = value)))

pure read(state: State, query: Query):
    match query:
        GetQuantity: return state.quantity

scope OrderDraft on its enforced owning thread:
    private committed = State(quantity = 1)

    selectQuantity(value: UInt8):
        // Interaction: this trusted typed entry point accepts a UInt8.
        candidate = decide(committed, QuantitySelected(value))
        match candidate:
            Rejected(reason):
                return QuantityNotAccepted(reason)
            Accepted(decision):
                // Acceptor: the only state publication, with no suspension.
                committed = decision.nextState
                return normally

    quantity():
        return read(committed, GetQuantity)
```

`UInt8` — целое без знака от 0 до 255. Его представление ограничено; более узкий диапазон 1–20 намеренно задан как бизнес-правило в `decide`. Если адаптер UI или HTTP получает текст, перед вызовом этой точки входа он разбирает его и проверяет представление `UInt8`. Правило 1–20 при этом не переносится в разбор. См. [проверку входа и бизнес-правила](spec/core/03-model-boundaries-zones.md#51-interaction-hemisphere).

`Intent` — единственный вариант `Pulse` этого Ball. Его `DecisionContext` по смыслу равен `Unit`: время, актор, конфигурация или другие поля контекста не меняют решение. Закрытое множество семантических выходов пусто, поэтому `SnapshotDecision(nextState)` не содержит пустую коллекцию выходов. Это допустимые [сокращения представления](spec/core/03-model-boundaries-zones.md#33-canonical-mutation-and-read-forms), а не иная семантика решения.

Результат `Accepted` из `decide` остаётся кандидатом, пока владелец его не опубликует. Отклонённый кандидат не меняет зафиксированное состояние. Нормальный возврат после публикации — обычное завершение локального вызова; адресованного семантического `Reply` здесь нет. Определённый контрактом возврат `QuantityNotAccepted` выражает [отказ до принятия](spec/core/06-protocol-algebra.md#613-error-classes); общая оболочка carrier для этого непосредственного вызова не нужна. Геттер читает только текущее зафиксированное состояние в той же области и напрямую возвращает данные закрытого типа `UInt8`.

Адаптера Resources нет, потому что внешних действий нет. Роль Resources пуста. [Три логические роли](spec/core/03-model-boundaries-zones.md#5-three-logical-zones) не требуют трёх классов или папок.

<a id="check-the-behavior"></a>

## Проверьте поведение

Проверьте эти утверждения средствами тестирования реальной реализации. Для всей последовательности ниже используйте один новый объект-владелец `draft` с начальным количеством 1:

```text
original = State(quantity = 1)
assert decide(original, QuantitySelected(20))
       == Accepted(SnapshotDecision(State(quantity = 20)))
assert original == State(quantity = 1)   // decide did not mutate its input

draft.selectQuantity(20)
assert draft.quantity() == 20

assert draft.selectQuantity(21)
       == QuantityNotAccepted(QuantityOutsideRange)
assert draft.quantity() == 20          // rejection published nothing

assert draft.selectQuantity(0)
       == QuantityNotAccepted(QuantityOutsideRange)
assert draft.quantity() == 20

draft.selectQuantity(3)
assert draft.quantity() == 3
```

Проверьте и саму реализацию: в `committed` пишет только владелец; ссылка на изменяемое состояние не выходит наружу; обе точки входа соблюдают ограничение доступа; каждая ветка завершается без цикла, рекурсии, пакета работ, зависящего от выделения памяти, или I/O. Фиксированный размер входа и состояния вместе с конечным потоком управления даёт этому примеру статическую границу затрат. Малый размер файла сам по себе этих свойств не доказывает. Соответствующие проверки описаны в [тестах переходов и свойств](spec/core/verification/17-01-transition-and-property-tests.md#17-testing-review-and-operational-verification).

<a id="make-an-ordinary-business-change"></a>

## Измените обычное бизнес-правило

Пусть верхний предел количества вырос до 30. Измените верхнюю границу в `decide` и добавьте проверки: 30 принимается, 31 отклоняется и не меняет последнее принятое количество. Уже допустимые черновики остаются допустимыми. Протокол `UInt8` по-прежнему представляет оба значения, а геттер, владелец и адаптация входа сохраняют смысл.

В этом и состоит ожидаемая польза локального рассуждения: правило и объясняющие его тесты находятся рядом. Изменение правила само по себе не требует нового интерфейса, поля манифеста, маршрута, адаптера Resources или Flow.

При обычном изменении проверьте:

- По-прежнему ли только этот Ball владеет изменяемым фактом и записывает его?
- Выражают ли существующие закрытые входы новый запрос?
- Можно ли принять решение на основе State и явного текущего входа/контекста?
- По-прежнему ли принятие атомарно публикует решение целиком?
- Добавило ли изменение внешнее действие, асинхронный срок жизни, другого владельца полномочий, переменную размерность, границу доверия или более сильную гарантию?

Последний вопрос определяет, что читать дальше. Он не требует заполнять все возможные категории.

<a id="what-this-example-deliberately-does-not-materialize"></a>

## Что в этом примере намеренно не создаётся

Эти пропуски следуют из описанного поведения:

| Артефакт | Почему его здесь нет |
|---|---|
| Поля идентификатора экземпляра и ревизии | Одна локальная область доказывает идентичность и порядок; нет хранения между запусками, асинхронного порядка или доступной снаружи идентичности снимка. [§§3.1–3.2](spec/core/03-model-boundaries-zones.md#31-ball-type-and-instance) |
| Кадр выходов, очередь, адаптер Resources | Нет семантических выходов или I/O; принятие одного состояния — одна атомарная публикация. [§8.5](spec/core/08-decision-and-acceptance.md#85-atomic-decision-acceptance) |
| Чтение с меткой согласованности или перечисление стадий жизни | Геттер работает в том же стеке, временем жизни управляет хост; нет кэша, статуса или независимого жизненного цикла. [§§8.10–8.11](spec/core/08-decision-and-acceptance.md#810-local-read) |
| Маршруты Assembly и Flow | Нет другого Ball, к которому нужно обращаться или с которым нужно координировать работу. [§10](spec/core/10-system-composition.md#10-system-composition) |
| Манифест, иерархия интерфейсов, DI-контейнер | Исходный код и хост уже показывают контракт; эти артефакты не добавляют нужной границы. [§14.1](spec/core/14-manifest-and-organization.md#141-role-of-the-manifest), [§14.6](spec/core/14-manifest-and-organization.md#146-interfaces-di-and-code-generation) |

Обычная реализация не требует досье об отсутствии только потому, что категория не используется. Заявление о соответствии или выпуске, которое опирается на отсутствие, включает отдельные [правила применимости и подтверждения](spec/core/00-status-scope-goals.md#02-proportionality-principle).

<a id="share-immutable-parts-of-one-state"></a>

## Разделяйте неизменяемые части одного State

Один Document Ball может владеть неизменяемым `DocumentState(metadata, paragraphs)`. Изменение заголовка создаёт новые metadata и разделяет прежние неизменяемые paragraphs. Для этого не нужны Ball на каждый абзац или физическое глубокое копирование:

```text
next = DocumentState(Metadata(title = newTitle), current.paragraphs)
assert next.paragraphs is current.paragraphs
assert current.metadata.title == previousTitle

builder = mutableList(current.paragraphs)  // Private to this candidate.
builder.append(newText)
if exceedsDocumentLimit(builder): return NotAccepted(DocumentSize)
next = DocumentState(current.metadata, immutableTuple(builder))
```

Читатели получают только неизменяемые значения. Builder не выходит в принятый State; отказ после его изменения сохраняет все опубликованные документы. [Тесты Document](../../tests/test_local_composition.py) проверяют разделение структуры при изменении заголовка, изоляцию кандидата и отказ за разрешённой границей размера документа. Способ хранения и копирования остаётся выбором реализации.

Для следующей **локальной** зависимости перейдите к [композиции Counter](COMPOSITION.md#a-counter-with-two-capabilities). Она переиспользует один сериализованный binding у нескольких владельцев, предоставляет возможности чтения/увеличения и проверяет принятие, отказ и ошибку после принятия обычными вызовами. Добавление потребителя не создаёт токенов команды/результата, enum вызывающих или ещё одного диспетчера.

<a id="next-change-asynchronous-search"></a>

## Следующее изменение: асинхронный поиск

Внешний поиск добавляет реальную проблему: обратные вызовы могут прийти не по порядку. Оставьте одного Ball владельцем текущего поиска и включите идентичность принятого запроса в состояние, на котором строится решение.

1. Примите State поиска A вместе со всем пакетом `EffectRequest(FindProducts(...))`. Отправьте его после принятия.
2. Примите поиск B с новым стабильным дескриптором поиска и поколением, снова вместе с его запросом.
3. Проверьте завершение B по принятому запросу. Соответствующий `Fact` доходит до `decide`, который принимает результаты B.
4. Проверьте опоздавшее завершение A по запросу A. Оно подлинное, но устарело: `decide` сравнивает полный дескриптор и поколение с текущим поиском и сохраняет результаты B.

```text
accepted A → accepted B → result B → result A
current view:                 B          B
```

Теперь хост или привязка к среде исполнения должны обеспечить атомарное принятие состояния и выходов, сохранение выходов для отправки после принятия, последовательную обработку завершений, стабильную идентичность и проверку происхождения, а также конечные пределы запроса, ответа, работы и числа незавершённых операций. Для каждого завершения нужно строить его собственный доверенный Context, а не наследовать Context вызова, который начал работу. Достижимые сбои и неоднозначные исходы выбранного адаптера требуют закрытых путей результатов. Явно задавайте повторы, крайние сроки или отмену лишь там, где такие пути есть; изменение этих правил может включить новые обязанности.

Эти поиски живут дольше вызовов, которые их начали, поэтому [статус операции](spec/core/09-asynchrony-and-delivery.md#911-operation-status) уже обязателен. Привязка к среде исполнения предоставляет запрос к одному зафиксированному источнику статуса с ревизиями, независимому от живого канала ответа. Этот источник можно разместить рядом с владельцем поиска; отдельный сервис не нужен. До принятия исходной операции или выхода зарезервируйте всю новую достижимую ограниченную ёмкость статуса, включая ожидающие наблюдения, аспекты статуса и маркеры хранения, где они применимы. Если ёмкости нет, отклоните работу до принятия и отправки. Объявите срок хранения и границы гарантий при потере процесса: привязка `Transient` хранит статус лишь в пределах заявленного времени жизни процесса; сохранение после потери процесса требует механизма долговечного хранения и подтверждений. Устаревший результат A не должен заменять текущее представление B, но устаревание не разрешает удалять данные статуса, обязательные для принятой операции A.

Трасса объясняет правило состояния, но не задаёт полную асинхронную реализацию. Изучите [принятый запрос Catalog](spec/core/examples/15-catalog-search.md#154-first-decision), [адаптер Resources](spec/core/examples/15-catalog-search.md#155-resource-adapter-and-safe-sink) и [трассу устаревшего результата](spec/core/examples/15-catalog-search.md#157-stale-result). Полный пример также содержит отмену и сигналы — это дополнительные сценарии. Требования к идентичности находятся в [исходном разделе о причинности](spec/core/09-asynchrony-and-delivery.md#91-causal-identity).

<a id="take-a-slice-toward-production"></a>

## Подготовьте один срез к эксплуатации

По [руководству по оценке](EVALUATION.md) сравните затраты на реализацию, поведение при сбоях и трудоёмкость изменений той же функции с текущим подходом проекта. Подтвердите на конкретной привязке к среде исполнения гарантии, которые нужны проекту. Если принятая работа должна переживать потерю процесса, следуйте [пути внедрения долговечности](spec/core/reference/21-adoption.md#214-when-to-add-durability); учебный пример с временным состоянием эту гарантию не доказывает.

Следующая функция приложения должна повторно использовать уже созданные механизмы привязки к среде исполнения и точные применимые правила проекта. Её автор пишет новые доменные решения и затронутые тесты, затем пересматривает только новые условия применимости, локальные отличия и подтверждения, которые изменение сделало недействительными.
