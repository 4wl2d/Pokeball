# Problems Ballarch addresses, and problems it does not

Ballarch was designed against concrete, recurring failures of today's architectures. This page lists each problem with three things:

- the mechanism that addresses it;
- the rule that makes the mechanism mandatory;
- the evidence in this repository.

Several mechanisms are established practice, and the table says so. The last section lists what Ballarch does not solve.

## Problems addressed

| # | Problem in today's architectures | Typical symptom | Ballarch mechanism | Rule | Evidence here | New in Ballarch? |
|---|---|---|---|---|---|---|
| 1 | Error handling is two-valued: a timeout is mapped to "failed" or "succeeded" at each call site | A charged customer is told the payment failed; a retry charges twice | Three outcomes. The runtime chooses `Done`, `NotDone` or `Unknown` from the call's phase relative to the send horizon and from the port's effect class. `NotDone` is never produced without evidence. | R7 | [Benchmark](../benchmark/results/RESULTS.md): naive layered, actor, MVU and saga versions, which share an author-chosen policy that maps a timeout to "failed", violate a requirement in 11.7–73.4% of crash-free runs. Careful versions of the four styles and Ballarch violate none in any Stress or Mild run or at any crash point swept under those profiles; Ballarch's feature code has no exception handler, against 3–5 in each careful version. New: the runtime derives outcomes from it, not only retries, and the same classes apply to firmware and hardware interfaces (contribution 2) |
| 3 | Dual writes: state goes to the database, messages to a broker, and a crash in between loses one of them | Lost or phantom events | The decision's state and all its outputs are committed in one atomic operation, and nothing leaves before that commit | R4, R5 | Alloy P1 and P6; trace property T5; the C exploration over torn and failed NVM writes; the Kotlin `FileStore` test that kills a writing process | Not new: the transactional outbox and output commit. | 4 | Recovery is an afterthought: restart code re-runs whatever was in progress | Double effects after a crash or a deploy | Restart rules per call phase. A call that was never sent is sent. A possibly-sent call committed as NonIdempotent is not re-sent although its port is now Idempotent, and one committed as Idempotent is not re-sent on a port now NonIdempotent: it ends `Unknown`. A runtime refuses to start on records the new code cannot serve. | §3.7, §6.1, R8 | In the benchmark, the naive designs send a possibly-sent charge again after a restart, and under Mild with one crash 1,866 of 2,000 runs of each charged an order twice; the careful versions' hand-written recovery and Ballarch's runtime recovery charged none twice. Durable-execution engines also record when a step was scheduled and dispatched, but retry it under a policy set per step, not by phase and effect class |
| 5 | Shared mutable state, races, re-entrant callbacks | Heisenbugs; lost updates | One owner per fact; one step at a time per instance; no synchronous waiting between components | R1, R3, §3.4 | Architecture rules; the runtime guard and trace property T3; Yosys single-driver check in RTL | Not new: actors, aggregates, single-driver discipline in hardware |
| 6 | Workflows and sagas report a composite operation as succeeded or failed after a partial or uncertain effect | "Booking failed" while the flight is booked | Knowledge algebra over Kleene's three-valued logic; absorbing compensations. ## Problems Ballarch does not solve

- **Distributed consensus and replication** of one owner across nodes. Use a consensus system or a database for that.
- **Invariants that span owners.** They need a coordinating Ball, a reservation or a storage constraint (Core §10).
- **Hot keys.** One owner is one sequential writer.
- **Exactly-once external effects.** Ballarch guarantees at most one send of a non-idempotent call and an honest `Unknown`. Effectively-once behaviour needs an idempotent destination or reconciliation.
- **Knowledge across a Transient crash.** Under the Transient profile a crash erases a Ball's calls, so its knowledge covers only calls made since the runtime last started. A composite whose calls have effects that outlive a crash needs the Durable profile (Core §7.4). In the trip example's Transient exploration, a client that books again after a restart gets a false settled claim in 608 of 3,073 settled runs, and a flight is booked twice in 152 runs. The RTL composite block is Transient too: its status register covers only operations since its last reset.
- **Evolution under open obligations: solved in part, in the service reference.** Under the Durable profile the Kotlin reference runtime stores a state version with each record and the effect class with each call, and classifies every call by its recorded class. It converts old states with the Ball type's `migrate`, and refuses to start, naming each offending record, if the new composition cannot read or serve what the store holds: an unregistered Ball type, a state version it cannot migrate, an open call on a port it no longer binds, or a notice owed to a removed subscription ([Core §6.1](../spec/ballarch-core-2.0.md#61-evolution)). It does not detect a new decider that no longer handles completions of a port that is still bound: such a completion quarantines the instance when it arrives. A migration needs a codec that still reads the old classes. Nothing prevents two runtimes from owning one instance during a rolling deploy. The firmware reference does not implement Core §6.1: a firmware update that changes a port's effect class or the port table must be applied with an empty call ledger, or bump `schema` so that a committed record quarantines the instance instead of being misread (Core §10).
- **Ending lost attempts.** The reference runtime has no timeout per attempt: an attempt ends when its adapter reports, or at the call's deadline. For retries of a Safe or Idempotent port to help, the adapter must end each attempt itself (Core §10). In the benchmark's scenario B, Ballarch with an adapter whose attempt ends at the call's deadline, like the reference HTTP adapter, sent 0.98 charge requests per order under Stress against 1.69, and reported charged orders as failed in 4.2% of crash-free runs beyond the delivery horizon, where an adapter with a 1 s attempt timeout had none.
- **A wrong delivery horizon.** Reconciliation reads a status after the destination's declared delivery horizon as final. If a request takes effect later, Ballarch reports a charged order as failed, as careful hand-written code does: in the benchmark, all five reconciling designs did so in 3.5–4.2% of runs beyond the horizon without idempotency keys.
- **Choosing good ownership boundaries.** This is guidance and review (Core §8.1), not a check.
- **A production durable store.** The reference runtime's `FileStore` commits by atomic rename and is tested against killed processes, not power loss. It has no replication and serves one runtime per directory.
- **Performance.** The reference runtime adds a thread hand-off per request and at least three durable writes per effectful call. On the benchmark's machine, a 4-processor Linux VM, a request through its thread scheduler took a median of 46 µs, against 0.04 µs for a direct call of the same decider ([RESULTS.md §14](../benchmark/results/RESULTS.md#14-runtime-overhead-machine-dependent)).
- **Team productivity and the cost of the extra concepts.** These are unmeasured. Against careful hand-written versions, the benchmark shows more code, more framework types and larger patches for four change requests.
